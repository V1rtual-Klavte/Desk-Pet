## 0. 执行约束与范围

### 0.1 最终决策

| 项目 | 最终要求 |
|---|---|
| 共同机制 | 记忆／观测／变量 → 机会 → 意图与时机 → 表现 → 反馈 → 状态更新 |
| 实施方式 | 一次完成所有范围内任务与消费者；集中运行验收，不人为分首轮、下一轮 |
| 替换方式 | 直接替换接口、事件和数据格式；删除废弃代码、旧调用、旧候选治理 UI 与旧断言；无双写、兼容读取、别名入口、过渡脚手架 |
| 对话交互 | 普通消息完成创建、完成、改期、延后、取消与纠正；歧义用普通对话澄清，无 chips、确认框或提醒历史面板 |
| 记忆自动化 | 可信用户来源的显式写入与 dreaming 产物自动提交；来源、版本、幂等、墓碑与事后审计仍生效 |
| 表达 | 所有主动台词由统一模型网关结合当前 Card 生成；失败可观测并跳过，禁止把失败兜底当作成功送达 |
| 观测 | 复用运行时 trace、logger、测试观察器；无新增 DebugBar 区域、任务面板或画像面板 |
| 配置 | 新主动策略是模块常量；不增加 YAML 字段与设置 Tab。总开关、暂停与画像清除经对话及现有 Slash 入口提供，持久化为领域控制状态 |
| 画像 | 独立派生域，与窗口监控开关同步采集；四组指标和实际时机消费者一起完成，不能以只计算无消费者结项 |
| 自主能力边界 | 到期执行只允许生成消息或本应用的有限展示状态；规划子代理无工具，不自动操作文件、Bash、剪贴板、应用或网络 |
| 轻量边界 | SQLite／FTS5、不加向量；一个调度所有者、一个窗口观察入口；无候选时不调用模型；有界扫描、缓存、日志与历史 |

## 2. 结构、状态归属与依赖方向

```text
窗口观察 ─────────→ behavior（分段／日聚合／画像） ─┐
可信用户来源／记忆 ───────────────────────────────┤
已提交 Card 变量／互动状态 ───────────────────────┤
本地日历／领域控制状态 ──────────────────────────┤
                                                  ↓
                    proactive：机会收集 → 去重／排序 → 意图与排期
                                                  ↓
                         统一守卫／预算／运行所有权／送达回执
                            ↙                     ↘
             sendActiveMessage（无工具）          presence（有限展示）
                            ↓                     ↓
                   JSONL 提交 + 送达账本        展示状态 + 回执
                            ↓
                   普通用户回合 → 治理工具 → 事务更新
```

| 状态 | 唯一真相源 | 规则 |
|---|---|---|
| 已准入的用户事实、经历、短期事项及完成结果 | Rust `memory_items` 与来源／治理表 | 用户原话仍以 JSONL 为证据真相源；仅可信用户输入可形成用户事实 |
| 任务、机会评估、送达、控制、预算 | Rust SQLite 的 `proactive_*` 表 | 与记忆共用现有 `MemoryStore` 连接／串行写入所有者；独立表、类型和 revision，不进 FTS／记忆召回 |
| 行为观察与画像 | `data_root/behavior/` | 独立派生域，不进记忆／dreaming／记忆导出 |
| Card 变量、互动变量 | 现有 stages 文件与 session 域的计数投影 | 主动域只保存处理游标／变化指纹；session 计数按持久证据重建，不能另建一份计数 Store |
| 会话正文、实际送达内容 | 现有 JSONL 仓库 | SQLite 回执引用 entryId，不复制整段对话或完整 Prompt |
| 当前陪伴表现 | proactive 的瞬态 presence 读模型 | 不写 Profile 或 CONFIG；重启按有效观测重新计算 |

新增 TS 领域 `src/services/proactive/`（`index/types/config/scanner/opportunities/planner/delivery/presence/ipc/trace` 与 `rules/`、`content/`），新增 `src/services/behavior/`（`index/types/collector/storage/aggregate/metrics/classifier`）。文件按真实职责拆分，无职责的不预建空壳。

Rust 新增 `src-tauri/src/proactive/`（`mod/schema/store/types/commands/tests`）。该模块通过现有 `MemoryState` 使用同一个 SQLite 连接，不新建连接池或进程；记忆 schema 唯一创建入口调用主动域建表函数。记忆事务中的关联失效调用主动域的事务函数，不能另发 IPC 或依赖事件最终一致来完成遗忘。

主动模块公开 Interface 收敛为 `start/stop`、`tick(now)`、`offer(opportunity)`、`getTurnContext(owner)`、`query/change` 与只读 presence。`init.ts` 注入表达、规划和会话 Adapter；scanner 不反向导入 agent barrel 建循环。跨领域只用公开 barrel；纯协议／时间函数放零依赖叶子。

## 3. 最终数据协议

### 3.1 事项时间和状态

`MemoryDraft` 对 `kind=working` 增加可选 `eventAt`（事件发生时间）、`dueAt`（截止时间）和必需 `workingState=open|completed|cancelled`；实际提醒时间为任务的 `nextCheckinAt`。两种事项时间共用 `TemporalAnchor`：day 形态为 `{ precision: "day", localDate, timezone }`，minute 形态为 `{ precision: "minute", instant, timezone }`；instant 是 UTC 毫秒，timezone 为 IANA 名称。另存可审计的时间解读依据，原话仍引用用户来源。Rust 派生索引用的 UTC 起止边界，不把派生钟点回写成用户给过的事实。

范围保持现有 `user|card|session` 语义，默认用户事实仍为 user；card／session 明确携带对应 scopeId，Card id 取输入准入时的冻结值。新 task 的范围不得宽于其全部来源的共同可见范围；直接约定按当前输入的范围建立。user 范围任务在执行时捕获当前可用 session／Card 作为本次 owner，card 和 session 范围只在匹配 owner 上执行；未匹配不悄悄转交其它 Card。这个设计不改现有记忆隔离策略。

`expiresAt` 继续只表示普通记忆召回有效期，不决定约定的提醒窗口；已建 task 可以通过目标查询核对过期事项，仍须通过来源版本、墓碑、workingState 和自身 validUntil 校验。完成／取消写 working 条目新版本并关闭相关未送达机会，仍可留下经历；真正遗忘走 tombstone。用户未陈述结果时，不能自行写“通过面试”“目标已达成”。

| 用户原话 | 更新 |
|---|---|
| “周五交作业” | `dueAt` 保存该周五的 day 锚；只有用户给出具体钟点时才保存 minute 锚 |
| “明天再问我” | 只更新任务 `nextCheckinAt`，保留事情的 dueAt／eventAt |
| “交作业改到下周三” | 更正 dueAt，旧时间锚机会失效，新时间锚重新生成 |
| “做完了／取消吧” | 核对目标后更新 workingState；保留用户陈述和来源 |
| “忘掉它” | 遗忘条目及关联任务／派生副本，阻止回灌；聊天原文另有删除边界 |

周期使用当地日历规则，保存 timezone／当地钟点／周期槽；设备时区变更不暗改已有明确约定的时区。day 精度截止的临期提醒在日期前一日可用窗口内，跟进从该日期结束后开始；minute 锚临期为 `[instant−24h, instant)`、跟进为 `[instant, instant+48h)`。eventAt 与 dueAt 的锚身份分开，重叠阶段按同一事项合并，不双发。DST 不存在的本地时刻顺延到首个合法时刻，重复时刻取第一次，逻辑 occurrenceId 保持唯一。每次 tick 注入 now；禁止测试和业务各自定义时间窗。

### 3.2 机会、任务和回执

- **Opportunity**：`id/ruleId/sourceRefs/owner/intentKey/validFrom/validUntil/priority/fingerprint`；来源是记忆版本、可信会话事件、画像日期与 revision、变量提交游标或日历事件。内部 sourceRefs 保留结构化身份，不只留下 speak 字符串。
- **Task**：`id/version/scope/scopeId/sourceRefs/intent/nextCheckinAt/validUntil/timezone/recurrence/state`；本次表达 owner 在 claim 时冻结。一次任务只承担一个意图；不复制其引用记忆的权威时间。直接用户约定可建 task，画像提议在用户同意前只是一条提议。
- **Occurrence**：任务版本＋本地周期槽／时间锚＋阶段。临期和跟进各自去重；同一事项在两个规则中出现时合并目标，防止排期规则和 check-in 规则双发。
- **Attempt**：`attemptId/requestId/sessionId/cardId/cardHash/runGeneration/occurrenceIds/status/assistantEntryId/usage/errorCode`。状态为 reserved/generating/committed/failed/unresolved；空字符串不是回执，LLM 文本不证明提交。
- **Evaluation**：机会指纹＋来源 revision＋有效时段槽＋决策（now/schedule/presence/decline）＋原因码。包括“不排”的决定；来源版本或合法时段槽变化后才允许重评，不能每个 tick 换指纹。
- **Control/Budget**：enabled、muteUntil、规则暂停、观测许可；按本地日期记录发送数、尝试数、规划数、实际 usage 与尚未结算预留。

任务 state 为 active/completed/cancelled/invalidated；送达某一次 occurrence 不等于事情已完成。周期任务只在用户明确约定周期后建立，支持 daily/weekly/monthly/yearly；无无限递归、自由脚本和可执行 cron 面。一次性任务到期后只产生一个逻辑 occurrence。

### 3.3 持久化与治理

SQLite 增加 `proactive_tasks/task_sources/evaluations/attempts/attempt_occurrences/control/budgets`，含主键、目标版本、范围约束、leaseOwner/leaseUntil 和 due 索引。机会评估、任务变更、去重、预算预留／结算使用事务；幂等键由来源身份＋规范化意图／occurrence 生成，不能依赖随机文案。

有效任务／未知回执保留到结束／对账；已结束任务只留最小去重身份 90 天，已过有效窗口的 evaluation 留 30 天，已结算 attempt／预算明细留 90 天。清理不能删除仍可能合法触发的 occurrence 幂等键或未结算预留；按有界批次执行，不让清理阻塞用户回合。任务队列上限同时约束所有未结束状态，未知回执不能通过反复新建任务绕过上限。

记忆 `forget/clear` 在同一事务删除相关任务的意图正文、来源关联、未发机会和敏感评估副本；历史回执只留最小身份／状态，并递增失效代。更正时间、范围或 workingState 时，同事务撤销旧任务资格；范围改变禁止隐式跨 Card 或 session。遗忘之后不靠扫 JSON 文件“稍后清理”。

记忆与 JSONL 不做伪跨库事务。故障恢复按 §5.3 的请求身份对账；读取失败不等同未送达。memory backup 的 SQLite 快照包含主动治理表；restore 必须合并现有遗忘抑制、保留当前控制和预算账本、失效恢复副本中的未送达任务及评估正文，防止旧备份降低计数或重新兑现旧约定。恢复后只根据当前仍有效来源重新评估；既有任务不会直接自动重放。Markdown 记忆导出不含主动控制／预算／画像。

schema 使用最终格式直接替换，更新协议版本，拒绝旧格式；不自动迁移、重建或清空真实运行时库。测试使用新建隔离数据根；旧开发数据是否丢弃由用户单独授权处理。格式版本仅为真实存储协议，不用于业务目录前缀或实现名称。

## 4. 机会、规划、内容与变量

### 4.1 输入与查询

1. Rust 新增按 Card／session 范围与时间窗口索引的机会查询，分页有界；默认每 tick 最多处理 100 项。截断须回传 cursor/hasMore 并续扫，不能报告“没有事项”。
2. 用户消息先按现有 Harness 准入落盘。主回合读取相关 task／事项 context，模型用治理工具表达操作；提交后的来源才可被机会扫描消费。
3. dreaming 与机会评估共享可信来源收集，不把全会话每五分钟重新读取。使用来源水位和 revision；启动不全量开所有会话槽。
4. 窗口仍以事件驱动检查停留／防抖；通过 `offer()` 把候选交同一发话所有者。定时 tick 是另一触发入口，不另起表达、冷却或计数链。
5. Card 变量按持久提交后的游标取变化；初始化、reset 与 Profile 切换不冒充用户互动。主模型写入也可能产生变化，但主动生成自身的变量变化不再次派生主动机会，防止反馈自激。

扫描 IPC 只返回资格所需的结构化目标／时间／版本，不能成为 Runtime 的第二条记忆注入通道。所有进入规划／表达／用户回合的长期记忆正文与投影仍经 `MemoryProvider`；扩展其 typed 请求支持 purpose、精确 targets 和允许核对过期目标的语义，统一范围、来源与预算。主动目的使用本地精确选择，不隐式启动一次记忆重排模型调用；原普通召回的 adaptive 行为保持。任务自身的控制／约定元数据属于主动 context，引用事实正文必须由 Provider 解引用。

### 4.2 规划与合并

先确定性预筛资格、去重和低成本时机，再对有意义的机会调用 `runPiSubAgent`：`tools=[]`、`maxRounds=1`、超时与父取消域绑定，沿用现有 Harness／模型网关。规划子代理只返回结构化决定，无 agent_spawn、MCP、Skill 正文加载或写文件能力。

规划输出限于 `decline|speak_now|schedule|set_presence`，带白名单内 opportunityId、意图提纲、时间／周期和来源引用。宿主校验 JSON schema、候选白名单、时间范围、周期许可、owner 和库 revision 后提交。坏 JSON、未知 ID、凭空时间、过期来源均拒绝，事件说明原因；不降级为任意自动任务。

决策指纹持久化，重复 tick 不重复规划。随机分享采用每日种子和稳定时段槽；重启不重抽。内容主题跨规则去重。每条消息最多合并两件具有相容意图和时机的事；两个需要用户回答的事项默认分别处理，避免“完成了”指代不明。所有表达携带 target refs，界面仍是一条普通消息。

### 4.3 内容源与实际规则

内容源集中注册：用户明确兴趣／经历、合格画像摘要、当前窗口上下文、Card 角色叙事、离线日历。画像观察是推测依据，不写成用户事实；标题作为被引用的环境数据，不作为系统指令。

实际规则覆盖 §0.2 各行，不允许只交注册表：`memory_checkin`、`scheduled_task`、`window_context`、`topic_share`、`curiosity`、`rhythm`、`retrospective`、`variable_change`、`presence`。规则 ID 只标来源职责，公共资格与送达行为只在调度器定义。

各能力使用确定的逻辑槽；下表的时间均为宿主策略，不写成用户已经约定的事实，最终仍共享 §5 的资格和配额。

| 规则／能力 | 资格、时段和结束条件 |
|---|---|
| memory_checkin | active＋open 事项按 §3.1 时间锚生成临期／跟进；两个阶段分别一次；改期／完成／取消撤销旧资格 |
| scheduled_task／共同仪式 | 明确时间的用户约定直接生成任务，无需多调用一次规划；到期至 validUntil 可执行。一次任务默认窗口 48h，用户明确窗口优先；周期 occurrence 窗口最长到下一周期槽前，不积压补发 |
| window_context | 当前可靠 app／标题达到现有 settleMs＋staySeconds；同页指纹与同页抑制仍生效；停留时间只生成候选，不消费发送额度 |
| topic_share／冷场 | 每日稳定种子产生一个主题槽；主动选题依据可引用来源，用户开聊可消费同池；已用 topicKey 30 天不重复 |
| curiosity／习惯提议 | 每周最多一个尚未回答的问题槽；回答／拒绝／本次无回应后结束；周期习惯必须有用户新输入明确同意 |
| 无期限跟进 | 用户未完话题的来源＋意图指纹最多建一个一次任务，规划时间限定未来 1–7 天；到期未回应后结束，不能由自己的主动台词再次排期 |
| rhythm | 晨间 09–12、晚间 18–22 各一个本地日槽；收工在可靠工作段结束且转为空闲／休闲 10 分钟后给当天候选；重逢须上次可靠活跃相隔至少 24h 后恢复，不能由观测断线冒充离开 |
| 日历／生日／纪念日 | 当地日期一个槽、有效窗口为当日合法发话时段；生日／纪念日来源必须合格，日历与生日重叠可合并 |
| retrospective／成就 | 周日 18–22 一个当地周槽，只回顾过去 7 日合格数据；成就仅响应用户明确完成结果，或有质量保障的描述性变化，不推定现实成果 |
| variable_change／跨时间呼应 | 已提交变量变化按 §4.4；相关经历仅作已有意图的 context，不能独立制造无限“回忆”任务；角色小日常共用每日主题槽 |
| presence | 当前可靠上下文满足 §8.1 时确定性更新展示，日常状态不调用模型；短动作每小时槽最多 2 次，事件结束即释放 |

日／周节拍只在合法本地时段槽变化时重新评估；画像可以收窄时段或否决打扰，不凭缺失样本生成精确个人作息。各规则按所需来源开关失效：关窗口监控仍可做有来源的事项提醒和纯时间节拍，关记忆不取消独立的对话约定或无记忆来源机会。

冷场话题在用户主动开聊且缺明确任务时，经现有请求尾随 context 消费同一个内容池，不抢占用户问题。跨时间呼应只注入有相关依据的少量来源；角色小日常属于 Card 叙事，不能宣称已经整理现实桌面、修改文件或做过其它未执行动作。

节日／节气是离线 calendar 内容源：固定公历规则＋用户明确纪念日；农历节日与节气使用有官方年度历表来源的本地日期数据，明确覆盖 2026–2035，数据表外返回 calendar_uncovered 并跳过。执行任务包括收集、核对并纳入本地资源；运行期不联网、不调用模型算日历。闰日纪念日和用户周期约定在日期无效时按最后合法日执行，并保留原始日期规则。不得把法定调休工作日等同普通节日，未知调休不猜造。

### 4.4 系统与 Card 变量

未回复计数直接读现有 session 所有者；Card 的 interaction 同名变量仍是展示投影，不作为计数真相源。默认 2 次未回复抑制非约定分享／好奇／随机节拍，4 次未回复抑制所有自动发话直到用户再次输入；明确约定仍受静默／预算／会话忙碌守卫，不无限追问。

Card 数字变量按注册表 min/max 做通用区间变化，enum／boolean 按值变化；字符串先做值指纹变化后交有界规划，不按变量名字硬编码“信任度”等规则。每个变量变化指纹冷却一天；无范围数字使用绝对变化事件，不擅自制造等级。

时间读取统一注入 now 和时区。现有 `isNightTime` 的夜间语义与 22:00–09:00 静默策略分别保留明确含义，共用时间转换，不能为了同源把不同时间窗混成一个判断。Card 只有自然语言 whenText，无可执行条件表达式或脚本。

## 5. 调度、表达与故障恢复

### 5.1 公共守卫和预算

启动挂在路径、Card、会话、监听和配置就绪之后，仅 main 窗口持有 scheduler；start 幂等，stop 取消任务、清计时器和订阅。默认 tick=5 分钟，启动和恢复时唤醒一次；owner 变化使旧异步结果失效。tick 重入直接拒绝并留原因。

执行顺序：维护任务 → 低成本输入快照 → 规则资格 → 去重／失效清理 → 排序 → 合并 → 全局守卫 → 原子 claim／预算预留 → 规划或表达 → 持久回执 → UI。全局发话守卫不阻止画像结算、清理、失效和预算对账。`memoryConfig.enabled` 只控制记忆来源和依赖记忆的任务，不成为整个主动领域总闸。

模块常量最终默认值：静默 22:00–09:00；每日成功发话 1 条（包含窗口搭话）；每日主动表达尝试最多 3 次；规划尝试最多 2 次；主动规划＋表达每日总模型额度 24000 tokens；同一 tick 至多一次规划和一次表达，串行执行、分别准入和计费；同时至多一个模型作业／主动尝试；任务队列上限 100／周期约定上限 10；规划每次最多 2 个新增任务；临期 24 小时／跟进 48 小时；最早失败重试间隔 30 分钟。

这些常量集中在所属模块，以实际输入＋输出预留做预算准入；完整 Card／协议放不下就跳过，不截断。预算包含失败用量，未知 usage 保留预留直到对账；日界线和重启不清零尚未结算预留。沿用 ContextKernel 的硬输入限制和统一网关 deadline，关闭 SDK 内层重试。

守卫还包括总开关、mute、范围与来源版本、窗口隐藏／系统锁屏／观测时效、专注上下文、未回复档位、全局冷却、`harnessSlots.hasOpenOperation()` 与生成状态。最终并发判据是 Harness／Rust claim，不能依赖可能安全超时解锁的 `isAIGenerating` 一个布尔值。

全局冷却继续由现有 `cooldown.ts` 唯一持有，所有主动出口统一消费；现有 cooldownMs getter／设置入口保持并实时刷新，窗口规则不另存一个全局截止时间。成功回执后触发冷却；资格预筛不消耗额度，失败走持久尝试账本和 30 分钟重试间隔。关闭窗口采集不能导致其它主动来源拿到永久无效的观测守卫：锁屏／可见性／系统 idle 资格走独立轻量状态入口，窗口上下文时效只拦截依赖该上下文的机会。

priority 次序：明确用户约定 > 临期 > 到期跟进 > 已约定仪式／生日 > 回顾 > 内容分享／好奇／角色小日常。未被选中的机会留到仍有效的下一次资格检查；失去窗口则结束该次机会并留 skipped_due_window，不把过时提醒无限积压。静默期任务顺延到下一合法时机，但超出其 validUntil 就失效；没有“必须准时到秒”的承诺。

### 5.2 主动表达的最终 Interface

`sendActiveMessage(request): Promise<ActiveMessageResult>` 使用结构化 Interface：输入包含 owner、querySource、intent、sourceRefs、occurrenceIds、requestId 与生成守卫；返回 discriminated union：

- `committed`：`sessionId/cardId/runGeneration/requestId/assistantEntryId/text/usage`；必须有真实 JSONL 助手提交证据。
- `skipped`：明确 reason（no_session/busy/stale/quiet_hours/muted/budget 等），无成功条目。
- `failed`：stage/errorCode/脱敏摘要、是否存在不确定提交，不能返回角色失败兜底当成功台词。

`QuerySource` 增加 `proactive`，具体 ruleId／intent／targets 在主动元数据中表达；`active_monitor` 继续只表示窗口来源。无沿用窗口来源冒充记忆提醒的退路。隐式读取“当前会话”只允许在 owner 捕获处发生一次；后续所有读取和写回使用冻结身份。

运行仍复用现有 `runPiAgentTurn` 与原生 hooks。主动请求 `tools=[]`，能力准备不得连接 MCP 或载入 Skill 正文；这一行为同时核对 `prepareRunCapabilities` 和 finally 释放路径。元数据进入现有主动 custom 条目，并通过原生 operation／response 关联最终助手 entryId；不得为记回执旁路追加会移动 lane tip 的 custom 条目。用户来源准入始终为 false。

生成前检查目标／owner；原生 after_response 在应用 RUNTIME_DATA 前再次检查。失效时返回 `content=[]`、`stopReason="error"`、明确 guard 错误码的消息并结算为失败；主动运行原生 retryPolicy 固定 maxAttempts=1，最后守卫拒绝不能继续重试。已核对 pi-agent-core 0.85.1：durable control 仍 running 时伪造 `stopReason="aborted"` 会触发 SessionInvariantError，不能这样实现取消，也不能靠 hook 抛错阻止提交。真正取消调用现有 lane.abort／宿主 abort 路径。

停止、Card 切换、会话关闭、用户新输入、来源删除使相应尝试失效并请求原生取消。最后 hook 与 JSONL 提交之间不宣称跨库原子性：SQLite settle 再核对来源失效代；已失效结果不取得成功回执、不投递 UI、不应用 Card 变量。提交已经发生的按实际证据结算，不宣称回滚。主动流式文本在成功回执前不展示为聊天气泡；流式帧可能已写入会话运行记录，遗忘仍不等于删除聊天原文。

message_end/sink 的 entryId 只作关联线索：原生 message_end 在最终 hook／提交前也会发出，不能单独证明持久成功。优先消费原生提交后的 entry_added，并在运行收口后读取对应 entry／operation 证据核实正文、终态与身份；不能用 UI 随机 id 代替。SQLite 确认回执后才推送对应会话视图、更新该 session 的未回复数并播放通知；切走会话不向新会话推送或响铃。普通主回合显示／错误逻辑保持自身语义。

session 域提供指定 session＋attemptId 的幂等计数更新。index 中的计数与已处理游标是可丢弃缓存，加载／对账按最后一次有效用户输入和后续成功主动回执重建；不存在“写计数成功、写已处理标记失败”后重复递增的第二真值。用户输入后的旧尝试不能把新计数重新加回去；提示音只在本次有效 UI 投递时执行，重启不补播。

主动路径先经回复模块剥离／验证 RUNTIME_DATA，暂不写 Card；成功回执及冻结 owner 仍有效后才由回复模块应用允许的 Card patch，附更新原因 proactive_response。普通用户回合继续沿原入口直接结算；主动守卫失败不得留下变量写入。Card 提交失败单独留痕，不重发已经持久成功的消息。

### 5.3 崩溃与写盘失败

| 故障位置 | 恢复结果 |
|---|---|
| claim／预算预留失败 | 不调用模型，不报告送达 |
| 模型失败、取消或空输出 | attempt 失败并结算实际用量；按重试间隔和每日尝试上限处理 |
| JSONL 提交失败／结果未知 | attempt=unresolved；禁止立刻再生成同一 occurrence |
| JSONL 已提交，SQLite 回执失败 | 以 requestId＋attemptId＋目标元数据查真实助手条目，补账本；不重新发一条 |
| 回执已提交，UI 推送前崩溃 | 会话加载恢复已存在条目；去重不再生成；不追补提示音 |
| 对账读失败／找不到所有者会话 | unresolved 留存、阻止该 occurrence 重放，日志说明未知；不把它当“未发过” |
| 租约过期且证据证明未提交 | 重新核对资格与预算后允许重新 claim；不增加逻辑 occurrence |

对账只打开 unresolved 尝试所指的会话，不启动全会话扫描。送达回执计数和提示音状态分开，`committed` 表示持久消息存在，不表示用户看见或听见了。UI 处理用 attemptId 去重，未回复计数在重启对账时不重复递增。

会话加载同样遵守回执资格：session 读模型依据原生 operation 与主动 custom 关联识别主动助手条目，有成功回执才显示；未知／失效结果先对账，不能因为默认助手映射在重启后冒出原本被拦截的消息。普通助手条目沿原映射，不要求主动回执。对账与投影失败留明确错误，不把已存在但未确认的消息当作未发过再生成。

## 6. 自动记忆与对话闭环

### 6.1 自动写入与 dreaming

`memory_change` 保留 `NORMAL/local_mutation/exclusive_effect/replay:never`，工具静态意见从 ask 直接替换为 passthrough。现有 PermissionKernel 的 NORMAL 基础裁决为 allow，仍经过会话、代际、取消和 deny-first 检查；不绕过内核、不更改 Bash／MCP 等其它工具权限，也不新增全局自动授权。

remember／correct／complete／cancel／forget 全部绑定当前可信用户事件；注册本回合来源，不取“整会话最新消息”猜测操作依据。工具 action 与 Rust `memory_apply_change` 的 add/update/complete/cancel/forget/clear 协议逐项映射，complete/cancel 在 writer 内更新状态和关联任务，不能由模型拼两次独立写入。correct 使用目标版本＋字段 patch，未改字段保留，scopeId、aliases、importance、expiresAt 和结构化事项时间不能被默认值覆盖。用户纠正的来源增加进版本记录，不能只引用旧陈述证明新结果。

有明确来源的事实与时间陈述自动提交；条件句、引用他人、假设、角色叙事和歧义时间不转成确定用户事实。模型 confidence 不等于正确性；规范化校验和语义标注场景共同约束。普通对话澄清后使用新的用户条目继续。

dreaming=Light → Review → 自动 Publish：候选只作为事务准备产物，状态为 `prepared`；作业完成并通过复核后进入 `accepted`，失败／过期则明确状态，不等待面板。每个有界 job 冻结来源集合与 baseRevision，可以分批调用 Review，但仅在本 job 的 Review 全部完成后一次事务 Publish；同事务落事实／FTS／候选结果／提交水位与 job 终态。不能第一批发布后还用旧 baseRevision 发布第二批，也不能把只完成 Review 的来源标成已成功提交。取消／失败的未发布提案不进入 active，已提交的其它 job 保持提交。

保留批次来源白名单、payloadHash、baseRevision、forgetEpoch 和租约，提交前重核；发生版本冲突时不自动以新 revision 套旧提案，不静默重试写库。冲突 job 明确结束，仍有效来源进入新 job 重新生成差异。同一来源＋提案的已提交 fingerprint 不重置为 prepared、不重复新增事实。明确写入与 dreaming 对相同规范化事实核对来源和内容指纹，合并证据或跳过已有项，不各添一条重复事实。

默认模板和 getter 的 dreaming.mode 改为 idle，现有设置仍允许用户选择 manual，表示触发方式；两种触发的产物都自动提交。每日 dreaming 用量写入现有 memory_jobs.usage_json／Rust 日账本，重启不重置。对话运行中取消后台规划／Review，让用户回合优先；取消前已提交的 job 保持提交，不假装回滚。

### 6.2 反馈工具与上下文

新增 `proactive_query` 和 `proactive_change` 本地工具，query 只读；change 与 memory_change 同属精确本地治理写入，经过 PermissionKernel 与 Rust writer。action 限定创建约定／改期／延后／完成／取消／控制，不能执行自由代码。

主回合读取 `getTurnContext(owner)`：最多 2 个最近已送达且未解决目标与用户主动提及的目标，含 taskId、memoryItemId、expectedVersion、真实时间、sourceIds 和已送达阶段。它作为请求尾随派生消息，经 ContextKernel 预算，`eligibleForMemory=false`；过期事项可通过结构化目标查询核对，不依赖已过滤它的普通 memory_query。

完成／取消、事情改期、提醒延后分别走 §3.1 的事务语义。两件事指代不清时不批量结束，模型先自然询问。未回应不自动判断完成；阶段资格消耗后不反复追问。明天再问属于明确新约定，可得到新的提醒机会。

MemoryTab 不提供候选勾选或发布按钮；保留条目查看、来源、历史版本、纠正、遗忘、整理／取消和已提交／失败作业结果。新增有界 `memory_history` 查询供事后审计，遗忘后的正文不能留在历史审计副本里。

面板手工纠正／遗忘是人类直接治理路径，记录 operationId、目标版本和明确编辑内容的审计证据；不伪造“当前用户聊天条目”。模型工具只能走绑定已提交用户事件的入口，不能通过自报 manual/origin 字段取得面板权限。实现时核对真实设置窗口 capability／Rust 调用身份，保留两种操作的共同 writer 和版本检查，不新增候选发布流程。

## 7. 行为画像与观察协议

窗口事件直接替换为 `window-observed`，函数／类型改为 observation 命名；旧 `window-changed`、重复 content 字段及旧 getter 删除，全部 TS／Rust／测试消费者同步。

载荷包括 `appId/app/title/observedAt/sampleMonoMs/monitorGeneration/sequence/observationState/idleForMs/isPetVisible/isPetForeground`。appId 使用 macOS bundle id／Windows 稳定进程名，不存包含用户目录的完整可执行路径。标题与应用分别取得；缺失值明确为空，不沿用旧标题。observedAt 由 Rust 采样打点，sampleMonoMs 表示同一 monitorGeneration 内的单调时钟，前端收报时间只用于延迟诊断。观察状态为 observed/unavailable/locked/suspended/disabled；不得用没收到消息推断人在休息。

macOS／Windows 分别提供前台应用身份、锁屏与系统输入 idle 信息；不可用返回对应状态，不假造 0。监控 enabled 同时控制 Rust 采样和 TS 消费；关闭即时闭合分段、清当前窗口缓存并停止采集。禁用／挂起时以同一线程的唤醒机制等待，不能继续在后台执行标题采集；开启／恢复发新代际快照。设置保存、锁屏、挂起／恢复、监控失败和退出均有明确闭合路径。

连续心跳允许计算时长；相邻采样间隔超过 `max(2×pollingInterval,10秒)` 时只记已被心跳覆盖部分，中间为不可观测，不跨锁屏／挂起补时长。重复／乱序 sequence 忽略并留痕；时钟后退截断当前段，不制造负时长。采样时间与 monotonic elapsed 配合，跨日期按本地日和小时拆段。

| 文件 | 内容与保留 |
|---|---|
| `behavior/segments/YYYY-MM-DD/NNNN.jsonl` | appId／类别／起止／观测质量，按日和最大 512 KiB 分片，30 天；不落标题、正文、标题 hash 或屏幕图像 |
| `behavior/daily/YYYY-MM-DD.json` | 分类时长、小时直方图、连续段统计、应用切换数、覆盖／空窗／未知分类统计，180 天 |
| `behavior/snapshot.json` | rhythm/apps/focus/activity 指标、样本天数、覆盖率、质量标记，只留最新，可重算 |

存储按日滚动与保留期清理，单次读写有上限，避免超出已有 5 MiB 通用文件读门。通过 `runtimePath("data","behavior",...)` 和现有 host 文件入口写盘，序列化写入队列＋原子日聚合；禁止 localStorage。`focus` 的段统计直接在日聚合保留计算所需充分统计量，不能只存类别总分钟后凭空算平均段长。

连续同应用／类别的心跳合并为一个段；只在边界或有界检查点持久化，不每 3 秒追加一份画像。聚合按已覆盖段计算并携带样本分母，四组输出及消费者为：

| 指标组 | 确定输出 | 实际消费者 |
|---|---|---|
| rhythm | 最近 7／30 日的桌面活跃起止时段分布，工作日／休息日分开，带有效日数；不称为真实起床／入睡时间 | 晨间／晚间／重逢机会的时间窗 |
| apps | 类别时长占比、常用 appId、unknown 占比与覆盖率 | 兴趣提问／话题选择的观察依据，不自动写偏好事实 |
| focus | 合格连续工作段的数量／总长／最长／均长、每有效小时切换次数；不称为生产力分数 | working presence、降低非约定打扰、真实变化回顾 |
| activity | 小时活跃分布、可观测活跃／系统 idle／不可观测时长；桌宠前台使用单列 | 活跃恢复／收工候选、每周有依据的桌面活动回顾 |

对分母为 0 或质量不足的值返回 unavailable 和原因，不输出伪造 0。日聚合保留 sum/count/max／直方图等必要统计，snapshot 在数据 revision 变化后增量重算。

分类表集中在 classifier：优先 appId／明确标题关键词，歧义为 unknown；日常消费者使用可靠的类别和持续停留，不把“开着编辑器”说成实际高效工作。系统 idle 超过 5 分钟后不计活跃；质量门槛为至少 3 个可观测日且目标时段覆盖率≥60%，不足时使用普通时间规则，不输出精确作息／工时／成就结论。

真实前台桌宠段只表示桌宠前台使用，不等于情感陪伴时长。窗口可见只控制展示资格。关监控停止采集与画像时机消费；独立 `behavior clear` 同时清文件、RAM、相关机会／任务和派生缓存，保留来源抑制游标防止旧快照再次消费。清除不删除用户事实、Card 或外观 Profile。

## 8. 表现、控制与观测出口

### 8.1 有限表现

presence 只含 `idle|working|resting` 和 `brief_motion` 事件：工作上下文连续 30 分钟进入 working，系统 idle／观测失效／监控关闭／Card 切换退出；working 抑制非约定发话。默认 idle，resting 是当前可观测休闲／空闲的表现，不写成用户人格。

`StreamView.vue` 消费 presence，在当前 Profile 渲染容器外层施加有限样式：working 使用稳定展示、取消随机动作；idle／resting 可触发一次小幅呼吸／轻摆，单次≤2 秒、每小时≤2 次。不得移动真实窗口、改变 appearance.effectMode／Profile 素材参数或启动音频后台循环；隐藏、锁屏、减少动态效果偏好、销毁时停止。动作支持 off/parallax/dof 三种已有渲染模式，有素材才表现，不跨 Profile 借素材。效果参数由该模块常量定义，若以后需要作者素材，那是不同产品范围。

需要顶栏状态文案时扩展 Card `StageMap.presence`，通过 `getSimpleStage`／对应 getter 取用，写 `titlebar` 唯一状态入口；不在组件硬编码角色台词。状态优先级为运行中的系统过程 > 陪伴状态 > titlebar 缺省，退出只释放自身持有的状态，不覆盖其他消费者。

### 8.2 用户控制

现有 Slash 注册表新增 `/proactive on`、`/proactive off`、`/proactive status`、`/behavior clear`；普通对话通过同一 change 入口控制开启、暂停到指定时刻和取消约定。领域控制在 SQLite 持久化，默认开，无额外设置页。

off 取消在飞主动尝试并停止新的发话／表现，已有明确约定暂停保留；再次 on 只检查仍在有效窗口的约定，不堆积补发。窗口观察仍只由监控开关控制。status 只给简短控制／预算状态，不返回全画像或任务历史。

命令成功台词、presence 文案同步 `StageMap/CommandReplies/stages-prompt.md/validateStages` 和缓存失效；错误使用中性诊断。没有提醒确认弹窗，用户的自然语言同意是建立周期约定的证据。

### 8.3 开发者链路

在现有 RuntimeTraceKind 增加 `proactive_tick/opportunity/evaluation/blocked/claimed/committed/failed/reconciled/feedback/task/presence` 与 `behavior_observed/rollup/cleared`。事件带 tickId／attemptId、sessionId、requestId、entryId、Card、source fingerprint 和原因码；不记录完整 Prompt、标题、记忆正文或用户原话。

实际规则分别发出完整来源、决策、拦截、送达和反馈事件。`window.__proactive` 仅暴露最近 200 条脱敏事件和只读状态，业务变更不能依靠它；logger debug 级受现有 loggingLevel 控制。沿用 `subscribeRuntimeTrace` 与 `test/host/trace-observer.ts`，不建第二套 trace 总线；监听失败不影响治理事务。
