**实施前必读**：本页所有文件:行号基于 `source_base` 快照（HEAD `05bd0c1` + 本会话未提交工作树，约 60 文件改动积在工作树）。执行者开始每个工作包前重查 HEAD、工作树与相关消费者。**`crates/` 已纳入 git 跟踪**（2026-10-05 起）。

## 背景与证据

- 触发事件：一轮「猜歌」里 AI 连发 5 次工具（3×bash + 截图 + bash 探测音乐播放器）后触发 `ai.loop.maxToolCallsPerTurn: 5` 计数上限被掐断，收尾台词是 Card 的 `toolLoopMaxRounds` 文案——用户判定「这不太行」，并要求先答「主流 harness 怎么做的工具调用上限，为什么能一直调」。
- 相邻已修：同批次已修幽灵消息（`providerAdmission`/`disableAutomaticCompaction` 被对象字面量展开静默丢弃 + 子运行 sinks 泄漏 UI 气泡）与 usage 偏差口径（`totalInputTokens`）；本契约是随后的治理重做。
- 用户原始诉求（2026-10-06 原话）：「都不够啊，主流harness怎么做的工具调用上限，为什么能一直调？超时30s这个也要改。然后截图200张的上限得取消，就留删会话自动删截图。但是ai调工具（不出现在聊天记录的那种），给个机制，过期时间或者读完就删的什么机制。ai生成锁也要调整，这根本不行。冷却锁，这个现在不是靠主动消息那边的机制来搞吗，这个也得改，我们讨论下」。

## Part 1 · 工具循环上限重做（用户定界：对齐主流）

### 1.1 调研结论（2026-10-06；官方文档 + 开源仓库源码 + 本机 Claude Code v2.1.267 二进制实证）

| harness | 回合内次数上限 | 真正的停止条件 | 防死循环手段 |
|---|---|---|---|
| Claude Code | **无**（官方 "No limit by default"）；`--max-turns`/`CLAUDE_CODE_MAX_TURNS` 仅 print/SDK 模式，可选 | 模型不再调用工具；用户随时中断；上下文将满 → 自动压缩续跑 | 主循环无重复检测证据；stop-hook 连续 block ≤ 8；上限一律下沉到范围/工具（WebSearch 200/会话、子代理并发 20/深度 3、子代理各自 maxTurns 15/200/500） |
| Codex CLI | **无**（全仓源码检索为证，非文档承诺） | `needs_follow_up=false`（模型无待续工具调用）；Esc 中断；ContextWindowExceeded → auto-compact（默认 90% 窗口）续跑 | 未发现重复检测；压缩重试单次护栏；可选 rollout token 预算（feature flag，默认关，超限报 `SessionBudgetExceeded`） |
| Cline | **无**——「Max Requests」（曾默认 20）已在 v3.35 删除（官方 blog 明写；源码留 `maxRequests: 20 // Legacy field`） | 模型完成；或病理检测命中 → 问用户（交互）/ 停止（yolo） | **同工具 + 同参数（键排序签名）连续 3 次警告 / 5 次中止**；**连续错误 3 次 → 询问/停止**（CLI 默认）；可选 `maxIterations`，不设 = 无限 |
| aider | 无工具循环（非 agentic） | 单次用户消息 → 请求结束 | 编辑失败 reflection 上限 3（类属性硬编码） |

共同原则（可复用）：① 默认不限次数，正常出口是「模型不再调工具」；② 用预算（token/钱）而不是次数当边界；③ 上下文满了压缩续跑而不是掐断；④ 检测病理模式（重复调用、连续失败）而不是总量；⑤ 硬上限只作可选、且只在无人值守场景启用；⑥ 上限下沉到范围/工具；⑦ 到顶要优雅收尾/可继续，不要固定台词；⑧ 计数单位是 API 往返（turn），一条 assistant 消息可并行多个工具调用。

### 1.2 现状（本仓）

- 主回合硬上限：`src/services/engine/harness/runtime.ts:1321-1324` `toolCallsUsed >= options.maxToolCalls → block("工具调用次数达到上限 (N)") + terminate`；调用点 :1981、:2837 传 `loopConfig.maxToolCallsPerTurn`（`CONFIG.yaml:67` = 5，`CONFIG-DEV.yaml.example:36`）。**这是主流唯一不设的那类硬上限。**
- 终止后收尾：`runtime.ts:2663` `getFallbackReply("toolLoopMaxRounds")`（台词由 Card 持有）。
- 无人值守子运行各有封顶（保留）：计划步骤 `plan.stepMaxRounds`（config.ts:461）、主动规划 `PLANNING_TOOL_ROUNDS`（planner.ts:188）、agent 子代理 `sub-agent.ts:45` 取 `maxToolCallsPerTurn`。

### 1.3 目标设计

1. **主聊天回合取消计数硬上限**：删 `runtime.ts:1321-1324` 的 block 逻辑与 `maxToolCalls` 选项（:1267），删 :1981/:2837 两处接线。回合的自然出口 = 模型不再调工具（对齐 Claude/Codex）；兜底护栏保留：上下文预算 + 压缩、用户取消、`maxRetry`。
2. **新增病理检测**（Cline 默认值，每回合重置）：
   - **连续失败**：连续 3 次工具失败 → 软提示；连续 5 次 → 优雅终止回合。
   - **重复调用**：同工具 + 同参数（键排序 JSON 签名）连续 3 次 → 软提示；5 次 → 优雅终止。
   - 软提示走 `annotateToolResultText`（`src/services/context/tool-output.ts`）同一通道，中性文案、不建第二处出口；硬终止复用既有 `block + terminate` 机制（同参连击在调用门），**失败连击在结果侧经 `after_tool` 的 `terminate` 立即生效**（本批工具全部带该标记时上游在当前批次后结束运行、不再发下一次请求）；收尾仍取 `getFallbackReply("toolLoopMaxRounds")`（**Card 格式零变动**；触发语义变为「病理检测命中」，建议用户自行把卡里该条文案改得如实——卡是用户数据，本批不改）。
   - **子运行同样吃病理检测**（guard 实例按 spec 新建，子运行与主回合共用同一接线）：无人值守子运行除了 `maxRounds` 计数封顶，还会被病理硬阈值提前收口 —— 比 `subAgentRounds` 更早停，属收紧不是放宽。
   - 落位：新建纯逻辑模块 `src/services/engine/harness/tool-loop-guard.ts`（喂入工具名/参数/成败，输出 none|soft|hard + 原因），L2 可直测；接线在 runtime 的 `createTurnSpec` 工具钩子区。
3. **子运行封顶不动**（无人看着，对齐主流「上限下沉到无人值守范围」）：计划步骤 5、主动规划 3、agent 子代理 5。
4. **配置改名**：`ai.loop.maxToolCallsPerTurn`（删掉主回合消费后唯一剩余消费者是 `sub-agent.ts:45`）→ `ai.loop.subAgentRounds`，语义 = agent 子代理工具轮上限，默认 5 不变。

## Part 2 · AI 生成锁 → 由回合状态推导（用户定界：改成由回合状态推导）

### 2.1 现状与问题

- `src/services/cooldown.ts:59-80`：`aiGenerating` 布尔 + 30s `setTimeout` 强制解锁（`ai.lock.safetyTimeoutMs`，`CONFIG.yaml:115-116`、`CONFIG-DEV.yaml.example:65`、`config.ts:805-807` 的 `aiLockConfig`）。
- 起止：`runner.ts:396/599/738` 回合受理后 `setAIGenerating(true)`，三个 finally（:438/:707/:842）`setAIGenerating(harnessSlots.isAnyRunning())` 释放。
- 问题：① 布尔是**第二真相源**，与槽状态并存；② 30s 定时器不认长回合——超时强解后 `isAIGenerating()` 变 false，**主动扫描可在回合进行中启动**（与「回合中不打搅」的原意相反）；③ 定时器本身就是「锁可能卡死」的补丁。
- 消费者（语义不变，只换真相源）：`proactive/scanner.ts:254`（门禁 `ai_generating`）、`observation/scheduler.ts:142、159`、`agent/memory/dreaming.ts:371`。

### 2.2 目标设计

- **`isAIGenerating()` 改为计算值**：`harnessSlots.isTurnActive()` =「有受理中的回合（admission 计数 > 0）或任一槽运行中（`isAnyRunning()`，harness-slot.ts:2056）」。
  - `HarnessSlots` 新增 `admit(): token` / `endAdmission(token)`：覆盖**「运行槽已结束、但 runner 尚未交回」的收尾窗口**（`end()` 到 `endAdmission()` 之间）—— 槽在回合收尾前被释放/重建（dispose、空闲回收、测试重置）时 `isRunning()` 已为 false，光看槽状态会把在途回合当成空闲放行主动扫描；L4 场景在回合在飞时调 `harnessSlots.reset()` 正是走这个窗口。三个 runner 入口在 `begin()` 成功后、该回路首个 await 之前 admit，现有三处 finally 里 `endAdmission`（替代 `setAIGenerating` 的置位与释放）。
  - **结构性守护**：释放与回合的 finally 同流、无定时器，卡死在结构上不可能；长回合期间锁恒为 true（这正是不打搅的语义）。正常路径下受理计数与槽运行状态同时在场（互为冗余覆盖），受理计数单独支撑的是「槽被抽走但回合仍在飞」这段窗口 —— 新增的 L3 白盒断言（回合在飞时 `harnessSlots.reset()` 后锁仍为 true）钉住的就是它：`isTurnActive()` 退化成只看 `isAnyRunning()`、或 `admit` 调用被移除，该断言都会变红。
- **删除**：`aiGenerating` 布尔、`aiSafetyTimer`、`ai.lock.safetyTimeoutMs`（整节 `ai.lock`）、`aiLockConfig`、`window.__cooldown` 调试对象（cooldown.ts:83-90）。
- **落位**：`isAIGenerating` 移居 `@/services/engine/harness`（`harness-slot.ts` 导出，barrel 透出）；`src/services/cooldown.ts` **整模块删除**（其冷却半边由 Part 3 接管）。消费者改 import：`scanner.ts`（已从 harness 导 `harnessSlots`，顺路）、`scheduler.ts`、`dreaming.ts`、`runner.ts`。
- 测试设施同步：`test/host/standard-setup.ts:208-209` 的 `resetCooldown/setAIGenerating` 清理改为 harness 侧重置；`test/unit/cooldown/全局冷却与AI锁.test.ts` 按新语义重写（落位到 harness 相关目录）。

## Part 3 · 冷却锁 → 保留概念、搬进账本（用户定界：保留概念，搬进账本）

### 3.1 现状

- 内存态：`cooldown.ts` 的 `cooldownMs/globalCooldownUntil/setCooldown/isCoolingDown/remainingSeconds/triggerCooldown/resetCooldown`；档位同步在 `scanner.ts:96、193`；门禁在 `:254`（reason `cooldown`）；唯一触发点 `:366`——**只在 `result.status === "committed"`（送达回执确认）后触发**。
- 档位值（真相源 `proactive/protocol.json` tiers）：`cooldownMs` 低 15000 / 中 5000 / 高 3000；`samePageCooldownMs` 低 20000 / 中 7800 / 高 5000（后者是窗口机会的租约时长，与投递无关，**不动**）。
- Rust 侧已具备：`ProactiveLimits.cooldown_ms` 随 13 字段投影下发并逐字段校验（`proactive/mod.rs:29/154`、`commands.rs:82`）；claim 门禁（`proactive/store.rs:1229-1241`）已同处执行配额/随机间隔/token；settle（`store.rs:1378-1490`）已写 `next_success_after`；scan 响应 `budget`（`store.rs:776`）已携带 `nextSuccessAfter`。

### 3.2 目标设计

- **真相源 = Rust 账本**：冷却起点 = `proactive_occurrences` 中 `kind='expression' AND status='committed'` 的 `MAX(updated_at)`（occurrence 口径；账本已有，**不新增列、不升 schema**）。理由：`proactive_attempts.updated_at` 会被清空记忆 / 遗忘单条 / 恢复备份三条治理路径改写，不再是严格 settle 时刻。
- **Rust**：
  - scan 响应的 `budget` 增 `cooldownUntil`（= 该 occurrence 时间 + `limits.cooldown_ms`；无记录/已过期给 null）。
  - claim 门禁在 `store.rs:1235` 同处增一条 `denied_claim("cooldown")`（权威执行面）。
- **Node**：
  - `scanner.ts:254` 门禁把 `isCoolingDown()` 换成 `scan.budget.cooldownUntil > now → "cooldown"`（与 `success_interval` 读 `scan.budget.nextSuccessAfter` 完全同款，:257）。
  - 删 `setCooldown` 两处调用（:96、:193）、`triggerCooldown()`（:366——Rust settle 时间自动成为冷却起点，无需 Node 再触发）。
  - 删 cooldown 五件套（随 `cooldown.ts` 模块删除；`remainingSeconds/getCooldownMs` 已无生产消费者）。
- **效果**：跟随档位（投影已含 cooldownMs）✓ 重启不丢（账本）✓ 跨规则全局最小间隔 ✓ 单一真相源（Rust 记账 + 门禁，Node 只读 scan 快照）✓。
- TS 侧同步：scan 响应的 `budget` 类型（`HostCommandMap` 的 proactive_scan 消费侧，`src/services/proactive/`）加 `cooldownUntil`。

## Part 4 · 截图与托管图片生命周期

### 4.1 取消 200 上限（用户定界：就留删会话自动删截图）

- 删 `screenshot_cmd.rs:34` `SCREENSHOT_RETENTION`、`:234` 的 prune 调用、`:255` `prune_managed_images`（`screenshots/` 与 `pasted/` 共用同一 helper，一删两清）；同步注释（:147/:187）与单测（:356 常量断言、:421 prune 用例）。

### 4.2 不展示的截图不落盘（用户定界：干脆不落盘）

- `src/services/tool/local/screenshot.ts:65-77`：`show_to_user !== true` 时**跳过 `save_screenshot`**（模型仍通过 `contentParts` 的内嵌图片查看，:73）；`details` 不带 `screenshotPath`（形状变更同步 `src/services/tool/local/screenshot-details.ts` 的读取器与 `runtime.ts:1237` `collectScreenshotResult` 的判据——它本就只认 `showToUser=true`，:1241 才把路径并入条目，非展示型路径从源头消失）。
- `capture_screenshot` 不动（隐私总闸、尺寸/编码口径、取消语义照旧）。
- 效果：**这类文件归零**——「AI 调工具（不出现在聊天记录的那种）」从此不产生任何落盘垃圾，不需要过期或读完就删机制。

### 4.3 粘贴草稿当场回滚（用户定界：粘了没发的当场回滚）

- 现状链路：`paste.rs:155` 落盘（`pasted/<ts>.png`）→ `add_pending_images` 入待发送区；发送成功 → `ui.rs:961` 清空（**所有权转移**，路径已进 `deskpetImagePaths` 条目）；切会话 → `model.rs:585` 清空（草稿丢弃）；撤选 → `ui.rs:1045` 单张移除。
- 目标设计：
  - `model.rs:412` `ImagePlaceholder` 增 `managed: bool`（仅粘贴入口置 true；文件选择器/拖入是用户自己的文件，**永不删**）。
  - 清空语义参数化：**发送**清空 = 只清（保留文件）；**丢弃**（切会话/退出）= 对 `managed` 项删文件（失败只 `warn` 留痕，不阻塞切换）；**撤选** = 同上删单张。
  - **退出回滚**：真退出走 `supervisor.shutdown()` 关停序列（`main.rs`）——在 UI 主线程仍可用的时点对当前草稿执行同一回滚。关窗不等于退出（`main.rs:19` 注释：关主窗只收起），收起时草稿保留、不删。**精确挂点已核对**（见文末「未验证项与风险」首条：`ServiceExitHook::run` 首步，两平台均先于 teardown）。
  - 崩溃/强杀不回收（接受残量：单文件级；不做全盘扫描——用户明确否掉「全盘扫描」路线）。
- 与会话删除的关系：已发送的粘贴图是条目引用 → 删会话时由 `chat_delete_session_images` 连带删除（已实现）；本契约只补「未发送即丢弃」这一段。
