  - **修复的致命缺陷（本次迁移引入）**：`captureSnapshot` 在 Harness hook / 事件处理器内 `await` 对同一 lane 的写入命令，与 drive 持有的命令锁循环等待 —— 每个 production 回合都会在 usage 事件后永久卡死（`lane.prompt` 不返回、`abortAgentRuns` 不生效、scene 超时无法推进）。改为宿主只入队（`queueAuditEntry`），drive 结束后在 `execute` finally 里 flush。
  - **修复的宿主记账缺陷**：`collectPendingDelivery` 无条件清空宿主 inbox 镜像，使 `snapshot().queued` 与 lane 持久 inbox 分叉（`runtime-nextrun-inbox` 失败）。镜像改为只由 `queue_update` 事件更新。
  - **修复的测试缺陷**：`harness-storage/执行环境文件树` 新增断言用 `createTempDir()` 未规范化返回值拼字符串比对，macOS temp 在 `/var`→`/private/var` 符号链接下必然失败；改为与 canonical root 比对。同一批按审查结论修掉 4 条高危（`tools.mcp.enabled` 读写值与派生值拆开、`waitForIdle`/`dispose`/`abort`/`discardInterrupted` 不再吞错或伪装成功、SessionTabs 历史加载错误态）。
  - **同轮修复的结算缺陷**：`afterResponse` 在提交前剥离 RUNTIME_DATA 并返回新消息，事件里的最终助手消息因此已无标签；结算却直接解析该文本，导致 emotion 映射与 RUNTIME_DATA 变量写入整条链路失效（`emotion-runtime-effect`、`variable-affection-praise` 共 4 个用例失败）。改为在剥离前记录「原始正文 ↔ 剥离后正文」配对，结算按配对取回原文。
  - **压缩检查点的空切点（已解决）**：`memory-compaction-checkpoint` 此前 T3 报 `没有产生 compaction 条目: declined`。上游 `findCutPoint` 只对消息本体做 `chars/4` 估算，且必须"从尾部往回累加、在中途越过 `keepRecentTokens`"才存在可摘要范围；越过点落在首条消息上时切点就是第一条，整个会话都算最近 → `messagesToSummarize` 为空、hook decline。离线复算（直接调用上游 `prepareCompaction`）与实测一致：载荷 repeat 224 / 420 / 476 时"首条之后"的估算为 1690 / 3160 / 3580，均 < `keepRecentTokens=3648`；486（3654）起才出现切点。单纯加大载荷会先撞宿主硬预算：repeat 525 时消息 23643 字符加静态 ≈2.3 万字符超过 `hardInputLimit`，该轮被 `ContextBudgetError` 拦下（报告记为 `errorKind: unknown`），压缩断言反而通过——机制本身没问题，缺的是自洽的窗口。修复：载荷按当前配置的 `contextBudget(aiConfig.contextMaxTokens).keepRecentTokens` 推导（首条之后的正文合计 1.25 倍保留窗口），并补第 4 条 fake 脚本响应专供摘要请求；窗口下限由下面的「窗口下限落地」保证，场景不再自己声明窗口。
  - **同轮修复的场景前提**：`memory-followup-after-turn` 原先在工具执行期投递却期待 followUp——旧内核用 `agentSlots.markDeliveryPhase` 强行置位 settling，该入口已随迁移删除，settling 窗口只存在于 turn_end 与 run_end 之间、场景无法稳定命中。改为用显式 kind 走同一条 `lane.followUp` 通道验证通道语义，并断言工具期投递模式必须是 steer；契约 ar-03 的描述同步改为不声称验证 settling 自动路由。
  - **环境注意**：macOS 锁屏时 WebKit 会把窗口判为遮挡并挂起页面 JS（实测每个 scene 约 6 秒后整体停摆，任务管理器无 CPU、进程存活）。跑 Live 门禁前必须解锁屏幕并保持点亮；`always_on_top`/`caffeinate` 无效。
- **已知断链与剩余待办**：`nextRun` 未消费输入暂无 UI 展示；`/compact` 忙时有排队消息只保守拒绝；宿主本地硬预算超限以报错代替 Harness 溢出恢复；usage purpose 单列（PI-4）、插话双模式 UI（PI-1）、工具策略/只读并行（PI-2）未实施；开发数据根残留孤立的旧 `pi-sessions/` 目录（旧数据可弃，未清理）。
- **窗口下限落地（2026-09-18，用户决策：默认 128k、最低 64k、再低报错）**：静态提示词与工具 schema 实测 ≈2.3 万字符，16k 窗口下占 `hardInputLimit`（11680，本仓估算口径）的 78%，留给消息的仅 ≈6.5k 字符，而上游切点要求"首条之后的正文" ≥ `keepRecentTokens × 4 = 14592` 字符（chars/4 口径）——该窗口下压缩不可达。落地为 `DEFAULT_CONTEXT_WINDOW = 131072`（CONFIG.yaml、示例、getter 缺省）与 `MIN_CONTEXT_WINDOW = 65536`：`contextWindowError()` 是唯一定义点，[SettingsPanel](../../../src/components/SettingsPanel.vue) 保存时拒绝低于下限的值，`resolvePiTurnModel()` 在解析处报错；开发副本 CONFIG-DEV.yaml 已按授权同步为 131072。压缩检查点场景不再声明窗口，载荷直接按 `contextBudget(aiConfig.contextMaxTokens)` 推导，随配置自适应。

## P6 最小实施顺序

1. 定义 SQLite schema、迁移与导入/导出，并保留 Markdown 的人工可读投影边界。
2. 建立候选记录、来源/版本/置信度、冲突与撤销模型；默认不自动写入。
3. 实现按 scope 和 token 预算受控的 recall，再把只读 projection 接入 Runtime。
4. 设计画像写入确认、纠正/遗忘与 dreaming 的后台调度。
5. 为提取、召回、污染隔离、压缩恢复、冲突和撤销补 Contract/Scene；最后集中执行类型、模块和严格 Live 门禁。
