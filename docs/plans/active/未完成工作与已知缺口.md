### 1.1 PI-1 余项边界（2026-09-21 定）

现状事实（本轮源码核对）：证据链只到 `context_committed`——inbox 条目持久、投递回执（steered/followup/deferred）、消费后正文成为带 `deskpetEventId` 的条目；**`request_prepared` 起证不出来**。根因是持久化的 `deskpet.prompt_snapshot` 里 `agentMessages[].id` 写的是位置号 `agent:${index}`、正文只留 hash，无法从正文反查「这条输入进了哪个请求」。同时**用户侧没有停止入口**：全仓 UI 无停止按钮，`abort` 只被超时/释放/退出调用，`abortedByStop` 无消费者。

**A. 停止入口**

1. ChatPanel 运行中显示「停止」（与「发送」并存）；运行态经宿主 `deskpet-run-state { sessionId, running }` 事件下发，真相仍是 `harnessSlots`，不在前端建第二份运行状态。
2. 新增按会话的停止入口（现 `abortAgentRuns()` 是全局的，只服务测试与退出），返回本次归还清单。
3. 停止的结算修正：`abortedByStop` 单独分支，**不写兜底失败回复、不标 failure**，落一条如实提示（不暗示撤销已发生的写入）。
4. 归还项（`kind === "nextRun"`）在排队面板标「已暂停」，提供 **[继续处理]** 与 **[全部丢弃]**；「全部丢弃」复用逐条撤回。
5. 「继续」走宿主新入口：读 nextRun 项 → 逐条取出正文 → 以这些消息作 `prompt(AgentMessage[])` 驱动一次标准宿主回合（权限/结算/快照钩子齐全）；投递未被接受时把消息按 `nextRun` 放回，不丢输入。
6. 中断恢复（`getInterruptedRun` / `continueInterruptedRun` / `discardInterruptedRun`）复用同一决策条的继续/丢弃——内核入口已实现，但**当前没有任何场景覆盖**，缺的不只是 UI；本批要给继续与丢弃各补场景，无法稳定制造中断态时如实记入 §4 而不是降级成人工看一眼就报通过。
7. **不改 nextRun 内核语义**（ar-06 契约不动）：用户发新消息仍会顺带消费暂停项，文案如实说明这一点，不假装拦住了。

**B. 逐项证据状态**（可审计证据，不建账本、不加逐条 UI 徽章）

1. `captureSnapshot` 的 `agentMessages[].id` 改用消息自带的 `deskpetEventId`（缺省回退位置号）——三档快照（transform_context / provider_payload / provider_usage）由此可证明「该输入在该请求的投影里」。
2. 新增只读查询按输入推导阶段（queued / offered / context_committed / request_prepared / responded / settled），证据来源为 inbox 快照、会话条目、快照记录与操作记录；零新持久结构、零新状态机。
3. 撤回文案经该查询说得更准（已进入请求 / 已回复），不虚构一对一。
4. 其余阶段沿用既有产物，不新增阶段枚举（§3.2 明确不要求把每个阶段扩成全局枚举）。

**C. 完成条件**

- Contract/Scene 至少覆盖：生产入口停止 → 归还为已暂停 → 「继续」按序恰好消费一次 / 「丢弃」不再进入对话；`abortedByStop` 不产生兜底失败文案；中断恢复的继续与丢弃；`request_prepared` 按 `deskpetEventId` 可从落盘快照核对；批量模式下「一批输入 → 一条回复」不虚构一对一。
- 门禁：`pnpm run test:release`（严格 Contract + 三次 trial）；新增按钮与决策条属 UI，需人工查看后补 §4 记录。
- 文档同步：`DES.md`（停止入口从"建设"改为已实现）、`current/runtime-contract.md`、本表与相关导航。

**实施时核实**（现无证据，不作为已定事实）：取出正文到投递之间的毫秒级窗口只有进程被杀才丢项，回滚路径覆盖可控失败；`deskpet-run-state` 的事件命名与既有 `deskpet-*` 通道对齐。

## 3. 已知代码缺口

2026-09-20 review 发现的四条缺口已同日修复并通过严格门禁：摘要输入投影绕过 `resultProjection`（现在与主请求同口径，preserve 结果完整进入摘要素材）、许可释放/取消缺少借用者校验（Rust 侧拒绝非借用者的释放与取消）、Windows 提层定时器可能静默空转（改为轮询等待窗口就绪并留日志）、Live Test `classifyError` 的无边界状态码匹配（三档数字锚词边界）。门禁证据见 §6。

## 4. 验证缺口

以下均已实现，缺的是验证手段；完成前不得宣称已发布就绪：

- **Windows 运行时行为**：本机 macOS 只能证明 cfg 隔离与类型正确，不证明运行时行为；P8、托盘与窗口生命周期均无 Windows 实机记录。
- **跨进程重启的人工冒烟**：`app_restart` 的进程级重启链路未在真实应用里点过。
- **UI 未经人工查看**：ChatPanel 排队面板与投递意图选择、设置页新增控件（对话投递 / 只读并行 / 工具策略声明区）、`DebugBar` 的 Σ 用量面板、`effectMode` 门控后的光标跟随；Live Test 宿主不渲染 UI。设置页「修改 → 保存 → 文件回读 → 关闭重开」的往返未执行。
- **main 窗口关闭路径**：改为隐藏到托盘后，macOS ⌘W / 红点与 Windows Alt+F4 的实际行为未实机复核（Live Test 宿主不建 main 窗口）。
- **长期记忆质量评测**：P6 未实施，不适用。
