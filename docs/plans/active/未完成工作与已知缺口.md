## 4. 已知代码缺口（未修）

以下是实现问题；§5是尚缺证据，§6是已接受的边界，不能一并当成发布阻塞。

- **折叠改变会话排序时间（P3）**：rename 更新 mtime，`JsonlStorageMetadata.modifiedAt` 会把旧会话显示成“刚改过”，折叠后旧会话跳到列表顶部。**协调者判断（2026-10-04）**：会话列表应表示**用户活动时间**，不是文件 mtime —— 折叠是维护操作，用户并未“使用”该会话；mtime 是存储层事实，拿它当产品层活跃度是把两个概念混在一起。**建议修法**：从**正文里最后一条用户条目的时间戳**取活动时间（不放 `sessions/index.json` —— 契约写明它只存可丢弃 UI 状态），只读文件尾部、成本低；**维护类写入（折叠/重命名）一律不更新时间戳**。**待用户裁定的一点**：边界算“只算用户消息”还是“用户+助手”——协调者倾向**只算用户消息**（助手的主动消息不该把会话顶到列表顶部）。
- **计划与主动反馈上下文仍在 system prompt（P3，缓存优化先决策）**：**仓库里已有先例且已做一半**（2026-10-04 复核）：①**当前时间**已从 `buildPrompt` 的块里迁出，改由 `createTurnNoteMessage` 作**尾随瞬时消息**贴在最末 —— `src/services/context/builder.ts:130-133` 把理由写死了：「system prompt 整体排在会话正文之前，时间片段每回合都变，留在 system prompt 里就会把缓存断在正文上游，使整个会话正文每轮重新计费」；②**长期记忆**已走尾随数据块注入。**plan/proactive 未迁**，仍经 `ephemeralText` 进 `buildPrompt` 的 `ephemeral` 块（内核对非 `active` 的 origin 不排除）。**修法即照当前时间那条先例走（同一个 helper）**，但下列前置条件必须先满足，不能无闸追加：[runtime.ts](../../../src/services/engine/harness/runtime.ts) 将planStepContext及普通对话的proactive turnContext传入ephemeral，内核只排除origin=active，故plan/proactive仍改变system前缀。真实memory已通过尾随数据块注入。将现有plan/proactive块移到请求尾部前，必须保留“放不进就整块淘汰”的可选块预算与审计，并用真实回合量缓存收益；不能无闸追加。无生产者的hook/recovery枚举清理由消费者检查后决定。

- **行为采集的目录分段清理分支不可达（P3，W3a 发现）**：[collector.ts](../../../src/services/behavior/collector.ts) 按 `{name, isDir}` 读 `file_list` 的条目，但 Rust `FileEntry` 的线格式是 `{name, path, kind, size, mtimeMs}` —— `isDir` 运行期**恒为 undefined**，因此「按目录分段清理旧档」那条分支永远不执行（日文件的过滤靠文件名正则仍成立，不影响当日采集）。修法是把判据改成 `kind === "directory"`；属独立修复，不在迁移范围内，W3a 已就地留注释保留现状。

- **会话膨胀的真因：可回收块与「永不删除的 key」同行 ⇒ 折叠的行粒度丢不掉（P2，2026-10-06 实测取证）**：
  折叠只做**整行纯删除**且**保留行逐字不变**（S-2），因此一行里只要有**一个**保留元素，整行的可回收大块就一起活下来。实测（真机 dev 那个 13.25 MB 会话）：
  - `reclaimed` 只有 **0.24 MB / 13.25 MB（约 2%）**，与折叠器自报的 268 KB / 11,352,979 B 对得上（先前一次分析说「68% 可回收」是错的，已更正）；
  - 三条各 **2.4 MB** 的 `pi.op.preparation`（压缩准备快照，其 key 已被 delete、本可回收）**全部与一个 `pi.lane.state/main` 的 set 同行** —— 而 `lane.state` 从不 delete ⇒ 整行保留 ⇒ 7.2 MB 钉死；
  - 一条 **1.33 MB** 的 `pi.pending.entry` 与一条 `pi.pending.tool_output` 的 `value/delete` 同行 ⇒ delete 行永不可丢 ⇒ 同样钉死；
  - 占地最重的两个 key 本身也是「从不删除」类：`pi.lane.state/main`（128 次 set）与 `pi.branch.tip/main`（118 次）。
  **两个候选修法（择一，都要用户拍板）**：①把折叠规则扩成「同一 key 只保留最后一次写入」（模块文档早已认可这条扩展，replay 等价性证明与摘要校验都不变）——按上面的账面，它会同时解锁那 7.2 MB 与 lane.state/branch.tip 的历史，是收益最大的一刀；②允许折叠**部分重写保留行**（只留行内活元素），收益更大但**破坏 S-2「保留行逐字不变」不变量**，等价性证明与摘要校验需要重做。**判据**：`foldSessionFile` 的 `reclaimed` 与 `bytesBefore` 之比；真机复现只需看 `SessionFold` 的「可回收量未过闸门 2」日志。
- **折叠对「结果仍 >5 MiB」的会话无能为力（P3，2026-10-06 折叠守卫修复时登记）**：本轮修掉了「文件 >5 MiB 就永久跳过折叠」的失效守卫（读守卫改为 `FOLD_POLICY.maxFileBytes = 64 MiB`），但仍有真实约束：折叠结果经 `file_write` 落地，写侧单次上限是 `MAX_TOOL_FILE_BYTES = 5 MiB`（`src/services/tool/pi/native-execution-env.ts`），所以**折叠结果仍超 5 MiB 的会话保持不折**（截图多的会话会碰到：单张截图 base64 ≈1.2 MB，且在暂存与提交条目里各写一遍）。要解需要放开会话写入上限（会话专用写入路径放宽 `maxBytes`，只限会话根）——那时要一并核对 IPC 大载荷承载与安全边界。判据：`foldSessionFile` 的「结果守卫」分支 `skipped: too-large`。
- **Node 崩溃重启耗尽后仍无可见提示（P3，2026-10-06 登记）**：本轮已让**首次拉起失败**在顶栏显示中性文案（`ui/titlebar.rs` 的 `SERVICE_UNAVAILABLE_TEXT`，由 `main.rs` 的 `on_ui_ready` Err 分支宿主自推）。但监督器的**崩溃重启**在重试次数耗尽后只 `set_status(NodeStatus::Crashed)` + 日志（`host/supervisor.rs`），界面仍无可见提示。修法：给监督器的状态变化加一个可订阅出口，把终态推到同一顶栏通道（不要新建第二条提示通道）。
- **删会话清理托管图片未做跨会话引用检查（P3，2026-10-06 登记）**：`chat_delete_session_images` 按「该会话条目引用到的托管根内文件」删除。会话 fork 会复制条目从而**共享**同一份引用，届时会误删另一会话仍在用的图片。当前 `session-repo.ts` 的 `fork` 只是包装、全仓无生产调用者（已实测），因此暂不实现检查；**开放 fork 前必须先加跨会话引用检查**（否则 fork 出来的会话会丢预览）。
