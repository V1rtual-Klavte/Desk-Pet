## 4. 已知代码缺口（未修）

- **`file_read` 的 5 MiB 整文件门**（既有缺陷，只登记不修）：会话文件超过 `MAX_TOOL_FILE_BYTES`（5 MiB，[tauri-execution-env.ts:35](../../../src/services/tool/pi/tauri-execution-env.ts)）后连会话头都读不出 ⇒ 该会话打不开，且**会话列表会整体失败**（上游 `harness/session/jsonl/repo.js:194` 用 `readTextLines` 读头，而本仓的 `readTextLines` 走整文件 `file_read`；Rust 侧是读之前的整文件大小门 [tool_exec/mod.rs:686-691](../../../src-tauri/src/commands/tool_exec/mod.rs)，`file_read_binary` 同口径 `:993-996`）。
- **日志折叠残余（有意接受）**：折叠只降体量与重放行数，打开会话仍是 **O(全文件)**，残量主体是正文条目（真相源本身）；另有一类未被折叠规则覆盖的可回收对象——被反复覆盖但从未 `delete` 的 `value/set`，其可回收量可能恒小于 `minReclaimBytes`，闸门 2 永久拒绝折叠。真要解只有「快照 + 增量」或上游支持增量打开；`readTextLines({maxLines})` 对 open 无效，能受益的 `list` 已在用 `{maxLines: 1}`。**成功折叠不可逆**：被删行的原字节随 rename 消失，不保留 `.bak`、无回滚路径。
- **旁路写入不在 lane tip 链上**（归 session 层）：回合进行中经 [session/repo.ts](../../../src/services/session/repo.ts) 的 `appendPiSessionCustomEntry` 写审计条目会移动持久 `branch.tip`，但 Harness 的提交面只用内存 `state.tipId` 当 `parentId` 并覆盖 `branch.tip`（`pi-agent-core@0.85.1` 的 `harness/runtime/drive/boundary.js:51/76`、`tool-placement.js:98/151`），旁路条目因此被挤成孤立分支——条目在会话文件里可读、seq 正常，只是不在从收尾 tip 回溯的证据链上。`harness-branch-tip-bypass` 场景钉住真实现状并当回归守卫（条目回到链上时该场景会失败，并要求同步更新本登记、场景注释与 hs-04 描述）。
- **设置页阶段文案表（`stageRows`）只渲染 `executing`/`done`/`blocked` 与 4 个标量**：`commands`/`fallbacks`/`greetings` 三段 20 余条文案只在 JSON 编辑器里可见。编辑往返本身完整（`startEditStages` 序列化整个 `stages` 对象，不丢段），缺的是可读展示；补展示由后续 UI 批次承担。
- **`session-fold.ts` 的脆弱依赖**：`DataRootSessionRepo` 经**运行时字段访问**上游 `JsonlSessionRepo.fileSystem`（[session-repo.ts:72-74](../../../src/services/engine/harness/session-repo.ts)，锁死 `pi-agent-core@0.85.1`）；`open` 路径安全（`maybeFoldBeforeOpen` 的 try/catch，折叠失败不阻断），但**直调 `foldSession()` 会抛而非 skipped**。
- **折叠会更新 mtime** ⇒ `JsonlStorageMetadata.modifiedAt` 会让历史列表显示「刚改过」。
- **上下文分配账目里的名义份额没有消费者**（既有缺口，只登记不修）：`CONTEXT_RATIOS` 的 static 12% / tools 8% / dynamic 10% / ephemeral 5%（[budget.ts:14](../../../src/services/context/budget.ts)）只写进分配账目的 `assigned`（[kernel.ts:93-99](../../../src/services/context/kernel.ts)），全仓无读取点——内核注释自述是 audit/soft quota。真正被消费的只有两处：memory 15% 作召回 `tokenBudget`（[runtime.ts:1265](../../../src/services/engine/harness/runtime.ts)）与 `L0_TOOL_RESULT_SHARE` 10%（[tool-output.ts:9](../../../src/services/context/tool-output.ts)，是**单条上限**不是份额——总量判据另取 `normalInputTarget`）。真实回合对照（128k 窗口，名义 `assigned` / 实际 `used`）：static 12,522/744、tools 8,348/1,606、dynamic 10,435/201、memory 15,653/0、ephemeral 5,217/95；transcript 名义 0 / 实际 4,663（占该回合 63.8%），合计 7,309 对 `hardInputLimit` 124,354。**文档漂移**：[memory.md 的预算章节](../../current/memory.md)称这些比例是「可借用空闲容量的软配额」，但借还机制已删除（[kernel.ts:50](../../../src/services/context/kernel.ts) 注释「不再有第二轮借用计算」+ `memory-context-budget` 场景断言账目不得含 `borrowed`）。**已定判决**（未实施）：四个名义份额与其 `assigned` 字段一并删除，`L0_TOOL_RESULT_SHARE` 改名 `_CAP`，上述文档表述改口径。**memory 的 15% 暂不动**：注入时检查（`hardInputLimit`，[kernel.ts:78](../../../src/services/context/kernel.ts) / [model-gateway.ts:422](../../../src/services/engine/harness/model-gateway.ts)）只回答「能不能装」，分配回答「该不该装」，两者正交——反例：召回 50k + transcript 60k = 110k 过得了硬上限，却已越过 `normalInputTarget` 触发压缩。更合适的基准是 `normalInputTarget − 固定块估算 − 当前 transcript 估算`（记忆与 transcript 抢同一块地，长会话里后者更值钱），但它需要 `HarnessSlot` 新增当前视图估算 API，且当前召回实际用量为 0、无数据支撑，留待 P6 接入后按真实 `used` 再定。

- **system prompt 里仍有两类易变块没搬走**（第二刀；时间戳已在 `d54969b` 完成）：`ephemeral:plan`（计划步骤结果，[runtime.ts:1295](../../../src/services/engine/harness/runtime.ts) 是全仓**唯一**的生产 `ephemeralOrigin`）与 `memory:recall`（今天恒为空，MemoryProvider 默认空实现）仍落在 system prompt 里，会让前缀缓存断在会话正文上游 —— 与时间戳同一个机制，见[运行时契约的 `transform_context` 段](../../current/runtime-contract.md)。`ephemeral:active` 早已走 custom 消息（不在 systemPrompt 里），不需要动。
  **前置决策未定**：这两块现在是**可选块**，放不进硬上限时被内核整块淘汰并记入 `budgetDrops`；搬到 `createRequestViewHook` 的尾随消息之后，内核看不见它们，**这条闸会消失** —— 计划结果过大就从「被丢弃」变成「把整轮顶过硬上限」（多烧一次溢出恢复）。搬之前必须先决定要不要在追加点重建「贴不进就整条不贴」的语义（代价是多一次 `estimateRequestTokens` 测量）。
