## 1. 背景与目标

长期记忆已落地（SQLite + 准入判据 + dreaming），但记忆目前只被动参与对话。本设计让 `kind = working` + `expiresAt` 的短期事项**第一次有用武之地**：她到点主动来提一句、来问一句。

目标：

- **G1 按时说话**：临期（deadline 前）提醒、到期后跟进；多件事合并成一句话，一次 LLM 调用。
- **G2 能闭环**：做完了 / 明天再问 / 不用了——按钮走用户级写入口，事项真的能被关掉。
- **G3 立起插座**：扫描器 = 规则收集 → 统一守卫 → 去重 → 表达 → 事件；新能力只写一条规则（发话）或一个任务（不发话）。
- **G4 先造链路**：全链事件可观测（tick → 候选 → 拦截原因 → 送达 → 闭环），期望链路先以场景形式造出来，行为慢慢调。
- **G5 画像地基**：从她的日常观测算出「你的作息与习惯」——独立派生域、只算不消费（见 §6 与决策记录）。
- **蓝图在后**：扫描器上还能挂什么、各自想要的效果，见 §13（大致设计，细节另排）。

非目标（本期不做）：

- 窗口监控搭话**不迁移**进扫描器（事件驱动 ≠ 扫描驱动，且稳定工作）。
- 不做 Card 模板文案路径（已选全 LLM）。
- 不做「她自动判断你完成了」；不做提醒历史面板；不做跨阶段重复追问。
- 不做任何用户可见的链路 UI（DebugBar 不加区）。

### 规则接口（插件缝）

```ts
interface ScanContext {
  now: number                          // 注入时钟：测试直接传，不受墙钟摆布
  // 规则按需自取数据（如 memory_list），拿不到就返回空候选并自行留痕
}

interface ProactiveRule {
  id: string                                    // "memory_checkin"
  enabled(): boolean                            // 规则自带开关（如 memory.checkin.enabled）
  scan(ctx: ScanContext): Promise<ProactiveCandidate[]>  // 只产候选，不做说话决策
}

interface ProactiveCandidate {
  ruleId: string
  key: string                      // 去重身份，如 "memory:<itemId>:<expiresAt>:dueSoon"
  priority: number                 // 临期 20 > 跟进 10；跨规则按数值降序
  speak: string                    // 情境行（喂给 LLM 的一段说明）
}
```

### scanner 职责（规则不重复这些）

1. `tick(now)` —— **纯入口**：可被调度器定时调用，也可被测试直接调用（确定性）。
2. 逐条启用规则收集候选 → 合并排序（priority 降序）→ 取前 `MAX_ITEMS_PER_MESSAGE = 2`。
3. 守卫链（共享，全部带原因码，拦截也发事件）：
   - 静默时段（默认 22:00–09:00）
   - 每日上限（默认 1 条消息/天，按 state 的 lastMentionAt 计算）
   - 记忆总开关（`memoryConfig.enabled`）与各规则自带开关（`enabled()`）
   - 生成中（`isAIGenerating`）/ 全局冷却（`isCoolingDown`）→ 跳过本 tick
4. 去重（见 §3「去重」小节）。
5. 组装情境文本 → `sendActiveMessage`（唯一表达入口，见 §4）。
6. 成功：写 state → 推送消息 → 发 `proactive_sent` 事件；失败：静默跳过（与窗口搭话同待遇），发 `proactive_failed`。
7. 调度器：`startProactiveScanner()` 挂进 [init.ts](../../../src/services/init.ts)（与 idle dreaming 调度器并列，仅 main 窗口）；每 5 分钟调一次 `tick(Date.now())`，启动时立刻 tick 一次。并发保护：tick 重入直接跳过（上次未跑完）。

### 数据流

```text
每 5 分钟 tick ─→ 守卫链 ─→ memory_checkin.scan() ─→ 候选
                                                     │
            去重（state） ─→ 排序取 ≤2 ─→ 情境文本 ─→ sendActiveMessage（LLM，无工具）
                                                     │
                          成功 ─→ 写 state + pushAssistantMessage + 未回复计数 + 提示音
                          失败 ─→ 静默（事件留痕）
```

## 3. 第一条规则：memory_checkin

### 扫描来源

`memory_list(undefined, undefined, 500)`（[ipc.ts:60](../../../src/services/agent/memory/ipc.ts#L60)），TS 侧过滤。选它的理由：store 的 list 只筛 `status='active'`（[store.rs:271](../../../src-tauri/src/memory/store.rs#L271)），**过期但未清的事项仍在结果里**——一次调用同时够临期与跟进两个阶段用，零 Rust 改动。

过滤条件：

- `kind === 'working'` 且 `expiresAt` 为数字（无时间锚的事项不参与）。
- scope 只取 `user` 与当前 Card 的 `card` 范围；**排除 `session` 域**（check-in 落当前活跃会话，session 域事项跨会话提及会串味）。

### 两个阶段

| 阶段 | 窗口 | priority | 口吻 |
|---|---|---|---|
| 临期 `dueSoon` | `now < expiresAt ≤ now + leadHours`（默认 24h） | 20 | 「快到点了」提示可行动 |
| 跟进 `followUp` | `now − followUpHours ≤ expiresAt ≤ now`（默认 48h） | 10 | 「那件事怎么样啦」问结果 |

- 边界取闭开明确：`expiresAt === now` 归跟进；`expiresAt === now + leadHours` 归临期（含）。
- 同一事项两阶段**各自最多提一次**：临期提过没回应 → 到期后仍获得一次跟进机会（事件性质变了，不算追问）。
- 补课：跟进窗口按「过期时刻」回看 48h，应用关闭几天再开，窗口内的事项照样被问。

### 去重（state）

记录键 = **事项 × 期限值 × 阶段**（`mentioned["<itemId>@<expiresAt>@<phase>"] = { at }`）。

- 提及资格：事项处于该 phase 窗口内，且该键无记录。提过即翻篇（没回应不追问，低打扰）。
- 跨阶段互不阻塞：临期提过没回应，到期后 followUp 按自己的键独立获得一次机会。
- **改期即重新入列**：事项被更新出新 `expiresAt`（你回「改到下周三」）后键自然变化，新的期限获得新的临期与跟进机会——不需要独立的「顺延」状态。
- 记录惰性清理：超过 30 天，或事项已不在库（被遗忘/删除）时剔除。

## 4. 表达（LLM）

- 唯一入口 `sendActiveMessage(request)`（[runner.ts](../../../src/services/agent/runner.ts#L635)）：输入携带 owner、来源、目标与守卫，返回结构化 `committed/skipped/failed` 结果；统一网关、无工具（主动回合冻结工具集为空）、落真实会话。无活跃会话或结构操作在飞时返回明确 skipped/failed，扫描器直接跳过未提交结果。
- 情境文本（与窗口搭话「主人正在使用: X」同模式，自包含）：

  ```text
  现在时间：2026-10-02 21:30
  你记着主人的这些短期事项：
  - 快到点了：「明天要交作业」（截止 10-03 09:00，还有 11 小时）
  - 刚过去了：「周五的面试」（原定 09-30）
  请用你的角色口吻自然地提一句（可合并，别罗列，别提「记忆/系统/数据」字样，最多两三句）。
  ```

  指引是提示词不是用户可见台词；台词仍由当前 Card 人格生成。
- 来源标记：`querySource` 新增 `"memory_checkin"`（[types.ts:55](../../../src/services/engine/runtime/types.ts#L55) 枚举本就是身份维度；实现时若牵动面超预期，退路是沿用 `active_monitor`）。
- 红线沿用：`eligibleForMemory=false`（[runtime.ts:2443](../../../src/services/engine/harness/runtime.ts#L2443)）——她的话永远不会成为用户事实；记忆准入仍只认 `origin=user`。
- 送达与窗口搭话同款：`pushAssistantMessage` + `incrementUnanswered()` → `playNotificationByBoundary`（[listener.ts:62](../../../src/services/window/listener.ts#L62)）。
- **小改**：`sendActiveMessage` 需回传本次 `ingress.requestId`（返回值或可选回调）——链路事件要靠它和运行时 trace 事件对上号。

## 5. 闭环（对话式，无按钮、无确认框）

**她发消息 → 你回消息 → 她更新**——就是全部交互；不做 chips、不做弹窗、不做确认框（已拍板）。

- 你在 check-in 消息下自然回复（「做完了」「还没，改到下周三了」），模型在该回合按回复更新记忆：
  - 完成 → `forget` 对应事项
  - 改期/新情况 → `update`（新 `expiresAt` 等）——**改期即重新入列**（去重键含期限值）
  - 其他或不回应 → 不动作（该阶段已提过即翻篇，不追问）
- 记忆写入**全自动、不再要用户确认**（决策记录）：库的版本冲突（`MEMORY_CONFLICT`）与幂等账本照常兜底；写库失败按既有工具错误口径如实呈现，不静默重试。
- 想被再提醒就说新期限（同一 `update` 路径的自然用法）；没有独立机制、不承诺自动再问。
- 没有消息级交互状态：check-in 与她的话都是普通会话条目。

## 6. 行为画像（挂在扫描器上的第二条线）

从窗口监控事件流算出「你的作息与习惯」。独立派生域：**不进记忆库、不是用户事实**；与记忆核心画像分层治理，「合体」已否决（决策记录）。

### 采集（事件驱动）

- 监听 `window-changed`，**仅当 `windowMonitorConfig.enabled`**（监控开关 = 观察总开关，已拍板）。
- **Rust 小改**：`WindowChangePayload` 增加 `app` 字段——现在标题与应用名是二选一返回（[capture.rs](../../../src-tauri/src/monitor/capture.rs)），macOS 改为标题与应用名都取，Windows 主路径同时取进程名。
- 分段：标题/应用变化即闭合上一段、开新段；空窗（应用关闭、搭话后约 7 秒暂停、锁屏）用段间空隙表达，不单独记录；`is_pet_visible` 的段单独归类（她自己的窗口，算陪伴时长、不进应用榜）。

### 存储（数据根 `profile/`）

| 文件 | 内容 | 保留（常量） |
|---|---|---|
| `segments.jsonl` | 原始分段：应用名 + 类别 + 起止时间戳（**不存文档标题**，标题只用于当场分类） | 30 天 |
| `daily/YYYY-MM-DD.json` | 日聚合：每类分钟数、小时直方图 | 180 天 |
| `profile.json` | 最新画像快照（派生、可重算、丢了不心疼） | 只留最新 |

写入走 host 文件入口（与 `proactive/state.json` 同策略）。

### 指标（注册表，保留扩展）

每条指标 = 纯函数 `compute(日聚合) → 值`，按 key 进 `profile.json` 分区；新增指标只加函数，不动存储与消费方。第一批四组（已拍板全上）：

| 指标 key | 产出 |
|---|---|
| `rhythm` | 典型开始/结束时段、夜间活跃比例（夜猫子指数） |
| `apps` | 常用应用/类别榜、工作 vs 娱乐比例 |
| `focus` | 平均专注段长度、每小时切换次数（坐得住指数） |
| `activity` | 每日活跃总时长、与往常对比 |

应用分类表（关键词 → 类别）为代码常量，集中一处、可扩。

### 装配

- 采集器随主窗口启动挂进窗口监听初始化处（不改监听本身）。
- 结算 `profile_rollup` 挂到扫描器新增的**任务槽**：`ProactiveTask { id, enabled(), due(ctx), run(ctx) }`——不发话的周期性维护，随扫描器 tick 顺带跑、事件照发；任务只做「该结算了吗 → 调画像服务结算」的薄壳。

### 治理

- 不进记忆库、不进 dreaming 采集（准入判据本就只认用户输入，此处双保险）、不进任何导出。
- 用户不可见（本期）；**遗留缺口（登记）**：默认开 + 无 UI ⇒ 真实用户目前没有清除画像数据的入口，上架前必须补（关监控即停采已定 + 清除路径）。
- 可观测：采集与结算进主动链路事件流（§7 的 `proactive_task`），无 UI。

v1 不接消费者（已拍板）；消费候选（后补）：check-in 时机、台词层流露、专注搭档。

## 7. 观测链路（本设计的硬需求）

### 事件

往现有运行时 trace 总线（[trace.ts](../../../src/services/engine/runtime/trace.ts)，非阻塞观察者总线）**加一组主动链路事件**，一处发射、三方消费：

| kind | 时机 | payload 要点 |
|---|---|---|
| `proactive_tick` | 每次 tick 进入 | `now`、启用规则数 |
| `proactive_candidates` | 规则收集完 | 每候选 `{ruleId, key, priority}` |
| `proactive_blocked` | 守卫拦截 | `reason: "quiet_hours" \| "daily_limit" \| "generating" \| "cooling_down" \| "no_session"` |
| `proactive_dedupe_skip` | 去重剔除 | `key`、原因（已提过 / 静默中） |
| `proactive_sent` | 送达成功 | `keys`、`requestId`（与运行时事件对号）、消息条目 id |
| `proactive_failed` | 生成/送达失败 | `stage`、错误摘要 |
| `proactive_task` | 任务槽执行（如 profile_rollup） | `taskId`、是否 due、结果摘要 |

每次 tick 建一个 trace context（tick id 作为 `runId`），链路事件全程带上它。

### 调试可见（无用户 UI）

- **控制台钩子**：`window.__proactive`（仿 `__debug` / `__testAI` 先例）暴露最近 200 条链路事件的环形缓冲（只读），devtools 随手可查。
- **日志**：事件同时走 `@/services/logger`（debug 级，受 `generalConfig.loggingLevel` 控制），落数据根日志文件。
- **测试**：经现有 `test/host/trace-observer.ts` 机制断言，不另建订阅设施。
- **不加**：DebugBar 不发新区域；不做任何界面渲染。

### 期望链路与 eval 数据集（先造链路，再补功能）

「期望链路」= 三层场景（沿用 [test/README.md](../../../test/README.md) 的分层与证据强度口径），第一批草案：

| # | 层 | 链路 | 判据要点 |
|---|---|---|---|
| 1 | L2 | 窗口边界 | 正好临期/正好过期/过期 48h 外各自的归属 |
| 2 | L2 | 去重与改期 | 提过不再提；改期后按新期限重新入列；无回应翻篇 |
| 3 | L3 | 完整链 | tick → 消息入 JSONL（带来源标记）→ state 落盘 → **二次 tick 静默**（核心不变量） |
| 4 | L3 | 闭嘴链 | 静默时段/忙碌中不发，事件流里有 `proactive_blocked` + 原因码 |
| 5 | L3 | 补课链 | 过期 30h 的事项在下次 tick 被跟进 |
| 6 | L4 | 对话闭环链 | 回复「做完了」→ 自动写库 forget 生效；回复「改到下周三」→ 更新生效并按新期限入列；她的话不进记忆（无候选产生） |
| 7 | L4 | 记忆自动化链 | dreaming 整理一次 → 候选自动进入 active（无批准门）；`memory_change` 写入无确认直达提交（版本冲突照常报错） |
| 8 | 观测轨 | 质量 | 真实 Provider 观察语气/相关性（**观测性证据，不设阈值**，与记忆「真实模型质量对照」同轨，报告分开统计） |

## 8. 状态与文件

新增 `数据根/proactive/state.json`（TS 管理、**可丢弃**）：

```json
{ "version": 1, "lastMentionAt": 0,
  "rules": { "memory_checkin": { "mentioned": { "<itemId>@<expiresAt>@dueSoon": { "at": 0 } } } } }
```

- 写入走 host 文件入口（`file_read` / `file_write_atomic`，与 Skill 保存、V1RTUAL 写入同一路径；同目录 rename 原子替换）。
- 丢失/损坏 → 从空开始，最坏后果 = 重复提一次；写入失败 → 仍送达（已花的 LLM 调用不浪费）+ error 留痕 + 接受低概率重复；不备份、不进导出。
- **零 schema 改动**：记忆库当前版本校验是「不符即拒」（[schema.rs:161](../../../src-tauri/src/memory/schema.rs#L161)），没有迁移机制；为去重加列会让老库直接打不开，代价远大于收益。

## 13. 主动能力蓝图（大致设计 · 效果级）

本节只定「想要的效果」与依赖关系，**机制细节下一步再排**。所有能力都表达为同一模型：

**时机器 × 内容器 × 人格器**——时机器 = 画像桶（活跃 / 空闲 / 休闲）＋ 随机 ＋ 守卫；内容器 = 内容源注册表（画像派生 / 记忆 / LLM 知识 / 将来的检索）；人格器 = 当前 Card 口吻。新想法 = 给三个器各加一件东西。

### 13.1 内容投喂（随机分享 + 冷场话题）

- **效果**：她像个知道你最近在忙什么的朋友，偶尔随口递来一句有意思的；不是推送流。
- **时机**：每日随机抽 1–2 个时刻，只落在三个桶：活跃（画像工作时段）/ 空闲（一段时间无输入但人还在）/ 休闲（娱乐类应用活跃中）；静默与深度专注不抽。
- **内容池**：常用软件相关（画像 Top 应用）/ 你的领域与兴趣（记忆 + 画像）/ 前沿知识（LLM 自有知识，有陈旧风险）/ 新闻（**需要检索通道：MCP 或后续内置，v1 不上**）；分享过去重，不反复安利。
- **她的生活感**：她也有自己的小日常可以说（「今天给你把桌面理了理」那种）——零事实成本、纯人格内容，是内容池的常备来源。
- **冷场话题**：同池复用，改成「你主动开聊时的备用话题」。
- **依赖与护栏**：画像数据先跑起来（这是画像的第一个消费者）；频次上限、静默时段、专注段闭嘴、宁可不发。

### 13.2 主动了解（好奇提问 + 习惯提议 + 话题跟进）

- **好奇提问**：她主动问小问题（「你平时用什么写代码呀？」）——了解从「我偷看」变成「你告诉我」；答案自动进记忆（写入已全自动）+ 补画像。
- **习惯提议**：从画像看出规律后提议（「你每天 15 点都犯困，要我提醒你起来走走吗？」）——你回「好」就落成一件 working 事项，check-in 系统自动接手：**观察 → 约定 → 提醒**一条链。
- **话题跟进**：没聊完的事过几天自然来问「后来呢？」——check-in 的「无期限版」。

### 13.3 日常节拍（晨 / 晚 / 收工 / 节气）

- **效果**：陪伴的「呼吸感」——晨间问候（带上今天到期的事项）/ 收工小结（今天在 X 上待了 Y 小时，画像出品）/ 晚安 / 深夜还在干活的轻关心；有节奏但每天不完全一样。
- **节气与节日**：冬至、腊八、生日（记忆里的）、纪念日——本地可算、零联网；零/极低 token 的传统仪式感。
- **重逢问候**：你几天没理她，她不闹；下次见面才轻轻提一句「你三天没来啦」——低成本的「关系感」。

### 13.4 陪伴细节（不说话也在陪）

- **成就观察员**：「连续 5 天专注破 40 分钟，好厉害」——只夸不盯，避免监视感。
- **专注陪伴模式**：你专注时她不说话，但换成「陪你工作」的形态（状态 / 音效 / 小动画）。
- **桌面小动作**：不时的小动画，不说话的那种「她活着」。
- **周报回顾**：每周一次——时间去哪了 + 记忆大事记，她的口吻。

### 13.5 自主排期（机会预筛 → 规划子代理 → 定时任务队列）

- **效果**：她知道一些「已知但没安排」的事——记忆里的生日、偶然会话里说好要一起做的事——并**自己给未来派活**：规划一条定时任务，到点来兑现。13.3 的生日/纪念日、13.2 习惯提议同意后的约定与话题跟进，都由这条链托底。
- **三段链**：
  1. **机会预筛**（轻量，可确定性）：找「带时间锚或约定语义、但没有任务覆盖、且未评估过」的记忆/会话信息；已评估的记档（含「不排」的决定），不反复规划。
  2. **规划子代理**：判断该不该排、排成什么（到期时刻、意图、要说什么的提纲）、一次性还是周期（周期从严）；**结构化产出交回宿主**——子代理不直接写文件（沿用「编排入口不自行执行写入」）。
  3. **定时任务队列**（持久化，数据根 `proactive/`）：任务 = 到期时刻 + 意图 + 来源引用（哪条记忆 / 哪次会话）+ 状态；扫描器 tick 顺带查到期。
- **执行**：到期任务成为**又一条规则**的候选，走完全共享的守卫 / 去重 / 表达 / 事件——恰好验证「时机器 × 内容器 × 人格器」的插槽模型。
- **信任边界（先按这套记，要放开随时说）**：
  - 任务到期**只发消息、不跑工具**（无人值守的副作用面为零；将来要放开单独定）。
  - 自动入队、不确认（承接「记忆与写入全自动」的拍板）；来源可追溯；队列对用户不可见（本期）；事件流全留痕。
  - 规划频率、每日任务数、周期任务上限都是代码常量。
- **将来**：对话里的显式约定（「明天再提醒我」这类顺延/嘱托）也可以落成队列任务——本期 check-in 不依赖它。

### 13.6 变量池接线（从「只是提示词」到「真的起作用」）

现状：Card 变量只经提示词影响表达（值进请求视图、模型读数写数）；系统行为对它们无感。目标：把变量接成**第三个状态源**（与记忆、画像并列），三层消费：

1. **提示词（已有）**：语气与表达受影响——不动。
2. **系统变量的行为绑定（代码级，稳定名字）**：平台维护的变量直接驱动扫描器行为。第一批例子：
   - `unansweredCount` 高（她连喊你几次没回）→ 主动频率**降档**——低打扰的真实语义：你不理她，她就少说。**这个变量今天已存在（yuki 卡 interaction 域、系统维护），扫描器却对它无感**。
   - 时间类系统变量（vars 里的 `isNightTime` 等）与静默时段同源，复用不重复定义。
3. **Card 变量的迁移 → 机会（通用机制，不按名字硬编码）**：扫描器在 state 里存变量的上次快照，tick 时 diff——值变化 / 跨过区间段（如 `信任度` 3→7）/ 语义变化 → 记一条「变量迁移」机会（带冷却与去重，防高频变量刷屏），交给**规划子代理**（13.5）判断：要不要发一条、或排一条定时任务（例：「信任度跳档」→ 她有所表示；「当前目标」从有到空 → 收个尾）。

- **红线复核**：Card 侧依然只有 `whenText` 自然语言、不给作者可执行脚本面；条件判断全部在系统代码里、基于**通用迁移**而非卡片脚本。AGENTS.md「不恢复可执行 When DSL」的措辞需细化（禁的是 Card 数据里的可执行条件；系统侧允许代码级变量消费），实施时同步。
- **依赖**：第 2 层几乎零依赖（可早做）；第 3 层依赖 13.5 的规划子代理与队列。

### 13.7 排期轮廓（细节另排）

- 下一批候选：13.1–13.6——13.1–13.4 依赖画像先产出数据（正合「先造链路，慢慢调」）；13.5 依赖记忆数据与队列机制；13.6 第 2 层（系统变量降档）几乎零依赖、可早做，第 3 层依赖 13.5；新闻与检索类内容等检索通道到位后再上。

## 14. 已知边界与开放项
