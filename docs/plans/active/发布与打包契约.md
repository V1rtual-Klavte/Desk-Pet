# 发布与打包：目标契约与执行计划

> **状态：待实施。** 本文定发布流水线的设计口径与验收标准；实施后正文保留，另在
> [未完成工作与已知缺口](未完成工作与已知缺口.md) §2 更新「发布」条目。

## 0. 交付目标与现状

目标：把「打 tag → 双平台安装包 → GitHub Release → 客户端自动更新」做成一条可复现的流水线，
并让平时的 push/PR 能低成本发现打包配置腐化。

现状（2026-10-02 核对）：

| 项 | 现状 |
|---|---|
| CI | 只有验证（双平台 类型/编译 · Rust 单测 · L2 · L3 · 纪律扫描 · FLAKY 棘轮），**无打包** |
| `bundle.targets` | `["nsis"]` —— NSIS 是 Windows 目标，在 macOS runner 上会被平台过滤，**macOS 出不了包** |
| `bundle.icon` | 未列 `icon.icns`（文件存在但未引用） |
| 签名/公证 | 零配置 |
| updater | 未接入 |
| 版本号 | `tauri.conf.json` 0.1.0 / `Cargo.toml` 0.1.0 / `package.json` 0.7.1，**三处不一致**；最新 Release 为 `v0.14.5` |
| 打包体积 | 随包资源 61 MB，其中 **57.4 MB 是同一份 `zpix.ttf` 被三个 Profile 各存一份** |

## 1. 关键决定

| # | 决定 | 理由 |
|---|---|---|
| D1 | 打包与发布放**独立 workflow** `release.yml`；`ci.yml` 只加一个配置校验 job | PR 门禁与发布是两种语义；混在一起会让 tag 触发的构建污染每 PR 必过的门禁 |
| D2 | Apple/Windows 代码签名**先不做**，步骤写成可选 | 签名是外部依赖（账号 + 年费），不应阻塞流水线落地；写成条件步骤后补账号零改动 |
| D3 | 平时 push/PR 只做**配置校验**，不做构建 | Release 模式 Rust 构建在 macOS runner 上按 10 倍计费；配置校验秒级且能抓最常见腐化 |
| D4 | 版本号走**显式脚本 + CI 校验**（方案 Y），不做 CI 注入 | 注入会让仓库里的版本号永久失真（永远 0.1.0），本地 `tauri build` 出包版本也不对；Y 保持仓库版本可读、可审计 |
| D5 | 产物取**最小集**：macOS `.dmg`(arm64) + Windows `.exe`(NSIS) | 覆盖个人用户；多出 `.msi`/universal 的收益当前不成立 |
| D6 | **本次不做**字体去重 | 字体随 Profile 走是设计如此（Profile 可导入导出）；去重要动 Profile 模型或做子集化，属独立议题。已记入未完成总表 |
| D7 | 用官方 `tauri-apps/tauri-action@v0` | 构建 + 建 Release + 上传 + `latest.json` 一把梭；社区标准，坑已被踩过 |
| D8 | updater 用 **GitHub Releases 当端点** | 零服务器、零运维：端点指向 `releases/latest/download/latest.json` |

## 2. 版本号策略（D4）

**唯一真相源是 Git tag。** 发版流程：

```bash
pnpm run version:set 0.15.0     # 一次改三处
git commit -am "chore(release): 0.15.0"
git tag v0.15.0 && git push --follow-tags
```

- 新脚本 `scripts/set-version.mjs <x.y.z>` 同时改 `src-tauri/tauri.conf.json`、
  `src-tauri/Cargo.toml`、`package.json`；只接受 semver，否则非零退出、不写任何文件。
- 改完 `Cargo.toml` 后 `Cargo.lock` 会过期，跑一次 `pnpm run test:types`（含 `cargo check`）同步；
  脚本在结尾提示这一步。
- **CI 校验**（`bundle-config` job）：`GITHUB_REF_NAME` 形如 `v0.15.0` 时，
  其后的版本必须等于 `tauri.conf.json` 的 `version`，否则失败并指出该跑 `version:set`。
  非 tag 触发的运行跳过这一项。
- 本次落地时把三处统一到当前 Release 的 `0.14.5`，并补齐本地缺失的 tag（`git fetch --tags`）。

## 3. 工作流结构（D1、D3、D7）

### 3.1 `ci.yml` 新增 `bundle-config` job

单平台（`ubuntu-latest`）、不装 Rust、不跑构建，秒级：

| 检查 | 失败意味着 |
|---|---|
| `src-tauri/tauri.conf.json` 是合法 JSON | 配置被改坏 |
| `bundle.icon` 每个路径指向的文件存在 | 图标缺失（打包才炸太晚） |
| `bundle.targets` 是 `"all"` 或合法目标集合 | 写出了平台不认的目标 |
| `identifier` 非空且形如反向域名 | Tauri 构建直接拒绝 |
| `productName` / `version` 非空、version 是 semver | 安装包元数据不合法 |
| `plugins.updater.pubkey` 非空 | updater 装好了却永远验不过 |
| tag 与 `tauri.conf.json` 的 version 一致 | 见 §2 |

校验逻辑放 `scripts/check-bundle-config.mjs`，本地可跑（`pnpm run check:bundle`）。

### 3.2 新增 `release.yml`

```yaml
on:
  push:
    tags: ['v*']          # 不匹配历史里的 Ver0.0.x（大写 V）
  workflow_dispatch:
    inputs: { tag: { required: true } }
```

- `concurrency`：同 tag 只跑一次。
- 矩阵：`macos-latest` → `.dmg`；`windows-latest` → `.exe`(NSIS)。
- 步骤：checkout → pnpm（版本由 `packageManager` 裁定）→ node 22 → rust stable → rust-cache
  → `pnpm install --frozen-lockfile` → **可选签名步骤** → `tauri-apps/tauri-action@v0`。
- `tauri-action` 入参：`tagName: ${{ github.ref_name }}`、`releaseName: ${{ github.ref_name }}`、
  `releaseDraft: false`、`prerelease`（tag 含 `-` 时为 true，如 `v0.15.0-rc.1`）、`includeUpdaterJson: true`、
  `args: --bundles <平台目标>`。
- 两个矩阵 job 都会尝试建同一个 Release，`tauri-action` 自身幂等，先到的建、后到的复用。

### 3.3 可选签名步骤（D2）

GitHub Actions 不允许在 `if:` 里直接读 `secrets`，用 env 中转：

```yaml
env:
  HAS_APPLE_CERT: ${{ secrets.APPLE_CERTIFICATE != '' }}
steps:
  - if: env.HAS_APPLE_CERT == 'true'
    ...
```

将来补账号时只加 secrets，工作流不动。

## 4. 打包配置与产物（D5）

`src-tauri/tauri.conf.json`：

```jsonc
"bundle": {
  "active": true,
  "targets": "all",                 // 平台中立：由 host OS 决定候选集
  "icon": ["icons/32x32.png", "icons/128x128.png", "icons/icon.icns", "icons/icon.ico"],
  "createUpdaterArtifacts": true,
  "resources": { "resources/defaults": "defaults" }
}
```

- `targets` 用 `"all"` 而不是写死某平台的目标列表 —— 写死 `["nsis"]` 在 macOS 上会被平台过滤成空集
  （就是本次要修的问题），写死 `["app","dmg"]` 同样会在 Windows 上失效。
  **CI 侧再用 `--bundles` 把产物裁到最小集**：macOS `--bundles app,dmg`、Windows `--bundles nsis`。
- `icon.icns` 补进 `bundle.icon`（文件已存在，只是没被引用）。
- 打进包的内容只有三部分：`resources/defaults`（61 MB）、Rust release 二进制、Vite 产物（2.2 MB）。
  `data/` 是开发数据根，不进包。
- 估算：`.dmg` ≈ 37 MB、`.exe` ≈ 32 MB（压缩后）。**这是估算，首次真实构建后回填实测值。**

## 5. 自动更新（D8）

### 5.1 密钥

```bash
pnpm tauri signer generate -w ~/.tauri/v1rtual-desk-pet.key
```

- **公钥** → `tauri.conf.json` 的 `plugins.updater.pubkey`（明文入库）。
- **私钥 + 密码** → GitHub Secrets `TAURI_SIGNING_PRIVATE_KEY` / `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`。
- ⚠️ 私钥丢失 = 已安装用户永久收不到更新（客户端验签失败且无法追认）。生成后必须另存备份。
- 这是 Tauri updater 自己的密钥，与 Apple/Windows 代码签名无关，免费、无需账号。

### 5.2 配置

```jsonc
"plugins": {
  "updater": {
    "pubkey": "<公钥>",
    "endpoints": ["https://github.com/V1rtual-Klavte/Desk-Pet/releases/latest/download/latest.json"]
  }
}
```

### 5.3 接线

| 侧 | 改动 |
|---|---|
| Rust | `tauri-plugin-updater` 依赖 + `lib.rs` 注册 |
| JS | `@tauri-apps/plugin-updater` 依赖 |
| capabilities | `default.json` 加 `updater:default` |
| 服务 | 新增更新检查模块，接入 `initApp()` 的启动链 |

### 5.4 交互（复用既有入口）

发现新版本时：

1. `pushSystemMessage(...)` 落一条**中性**系统消息留痕 —— 不做成角色台词
   （AGENTS.md：系统消息与错误诊断保持中性，用户要能分清「角色在说话」和「出问题了」）。
2. `showDialog({ kind: "info", ..., confirm: { okLabel: "下载并安装" } })`
   —— [src/services/dialog](../../../src/services/dialog/index.ts) 的 `DialogRequest` 已自带 `confirm` 字段，
   与 safety 确认同一模式，**不新写交互组件**。
3. 用户确认 → 下载安装 → 提示重启。

检查时机：启动流程完成后延迟 30 秒检查一次（避开启动竞争与首屏渲染）；**同一进程内不重复提示** ——
用户选「稍后」后本次启动不再打扰，下次启动重新检查。不为此新增 CONFIG 字段
（新字段要走完整配置同步链，收益不成立）。

### 6.1 文档同步口径

**AGENTS.md —— 保持简短，不新增章节**，只在既有位置补几行：

- 「运行与验证」的命令清单加 `pnpm run check:bundle`（秒级配置校验）与
  `pnpm run version:set <x.y.z>`（发版改三处版本号）。
- 同节补一条口径：**CI 分两条线** —— push/PR 走 `ci.yml`（双平台验证 + 配置校验，不含构建）；
  tag `v*` 走 `release.yml`（打包并发布）。L4 仍不进 CI 的既有约束不变。
- 「文档维护与提交」里既有的「发布版本以 Git tag 为准」补半句：tag 版本与
  `tauri.conf.json` 的 `version` 由 CI 校验一致，发版前先跑 `version:set`。

**README.md —— 按读者分两段，源码与打包产物不混在一起**：

- 新增靠前的「下载安装」段（面向**用户**）：去 Releases 页取对应平台的 `.dmg`（macOS，Apple
  Silicon）或 `.exe`（Windows）→ 安装 → 说明首次打开会被 Gatekeeper / SmartScreen 拦（当前未签名，
  给出具体放行步骤）→ 说明应用会在启动后自动检查更新并弹确认框。
- 现有的开发段改为面向**源码开发者**：`pnpm install` / `pnpm tauri dev` / `pnpm tauri build`，
  并在段首用一句话点明「这与上面下载安装的产物是同一份代码的两种获取方式」。
- 现有的命令表保留，但 `pnpm tauri build` 一行注明「本地构建，产物在 `src-tauri/target/release/bundle/`」，
  与 Releases 页的产物区分开。

**docs/current/development.md**：补打包与发布的中断排查入口（工作流在哪、产物在哪、签名失败的常见原因），
篇幅控制在一小节内。

## 7. 验证与验收

| 层 | 验什么 |
|---|---|
| 本地 | `pnpm run check:bundle` 通过；`pnpm run version:set 0.0.0-rc.1` 后三处一致、再改回 |
| CI（普通 push/PR） | `bundle-config` 在双平台 verify 之外独立通过 |
| CI（tag 冒烟） | 打一个 `v0.0.1-rc.1` 预发布 tag，确认双平台产物出现、Release 生成、`latest.json` 含两平台条目 |
| 真机（**必须实测，不可推断**） | 装 v0.14.5 → 发新 tag → 客户端收到系统消息 → 确认后下载安装 → 重启后版本已更新 |
| 真机风险项 | **macOS 未公证下的自替换能否过 Gatekeeper 未验证**：Tauri 的更新是替换 `.app` 包，隔离属性是否传播未经证实。若不通过，需回头补公证（转 D2） |

## 8. 完成定义

- `release.yml` 在真实 tag 上产出的双平台安装包可下载、可安装、能启动。
- 客户端能从旧版本自动更新到新版本（双平台各实测一次）。
- 普通 push/PR 的额外耗时 < 30 秒。
- 版本号三处一致，且与 tag 一致；发版只需 `version:set` + commit + tag。
- 未验证项与未同步项在交付说明中写明，不把估算写成实测。
