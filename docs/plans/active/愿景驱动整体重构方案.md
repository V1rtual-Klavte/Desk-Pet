# 愿景驱动整体重构方案

## 1. 目标与决策

Desk-Pet 的最终形态不是固定 VTuber 模拟器，也不是套着桌宠皮的 Coding
Agent。它是一个轻量、常驻、可组合的桌面角色平台：用户自由选择或导入
外观 Profile 与行为 Card，角色以陪伴为主，在需要时成为有工具、有记忆、
可处理桌面和编码任务的助手。

本方案允许重写现有任意实现；兼容旧实现不是目标。必须保留的是用户最终
得到的能力和可迁移的数据，而不是旧目录、旧循环或旧对象模型。

已经确定的决策：

1. Profile 与 Card 独立、自由搭配；前者定义表现，后者定义行为和人格。
2. 长期记忆的唯一持久化介质是 Markdown 文件；允许启动后构建仅内存存在的
   倒排/BM25 索引，不引入 SQLite、向量库或隐藏索引文件。
3. Pi Core 是统一 Agent Loop 的候选实现；轻量和助手模式最终优先共享它，
   是否采用由真实 Tauri PoC 决定。
4. Pi Coding Agent 不进入 WebView；若项目级编码体验证明有不可替代价值，
   仅作为按任务启动、可终止的侧车候选。
5. Rust 是受限平台能力和路径安全的权威实现；业务策略、Agent 编排和 UI
   状态放在 TypeScript。

尚未确定的数值包括轻量模式的 RSS、首答延迟和包体阈值。它们必须先以当前
版本为基准实测，再由用户确认，不在本文中伪造指标。

## 2. 产品不变量

| 不变量 | 含义 |
|---|---|
| 桌宠第一 | 视觉常驻、快捷召唤、窗口感知、低打扰主动互动是第一层体验；Agent 对用户应当透明。 |
| 可组合 | 一个 Profile 可搭配任意 Card；切换任一项不得污染另一项的资源或状态。 |
| 轻量默认 | 未打开聊天时不加载模型运行时；未进入助手模式时不初始化 MCP、Skill、编码侧车或重工具。 |
| 人格可控 | Card 能影响 Prompt、阶段文案、情绪和允许写入的角色状态，但不能获得平台权限。 |
| 文件可读 | 用户可用编辑器阅读、备份、版本管理和迁移记忆；记忆无隐藏持久化状态。 |
| 安全内建 | 路径、工具、确认、信任和外部内容来源由确定性代码约束，不能交给模型决定。 |
| 跨平台 | Windows/macOS 行为经过同一 Capability Module，平台差异仅留在 Rust Adapter 内。 |

## 3. 目标架构

### 3.1 按资源分层，而非按功能开关分层

```text
Presence Runtime                 始终存在
  Profile renderer / parallax / window monitor / hotkey / minimal state

Conversation Runtime             首次聊天或主动互动时动态加载
  CompanionKernel / CardRuntime / MemoryKernel / PiAgentAdapter

Assistant Runtime                进入助手模式且实际需要时动态加载
  advanced capabilities / MCP / Skill / Planner / confirmation workflow

Coding Worker                    仅项目级编码任务期间启动
  optional Node/Bun sidecar, restricted IPC, task end => process exit
```

轻量与助手不是两套产品、也不是两套对话 Loop。两者共享 Conversation Runtime
与 Pi Core；区别是 Capability Module 给模型可见的工具集、权限策略、上下文
预算和可加载的附加 Module。动态导入可以降低冷启动和未使用功能的成本，但
ES Module 缓存不能保证模式降级后的代码立即回收；只有 MCP 和 Coding Worker
等独立进程可要求操作系统级回收。

### 3.2 核心 Module 与 Seam

```text
Vue UI
  -> CompanionKernel
       -> ConversationKernel
       -> ContextKernel <- MemoryKernel + CardRuntime + Capability snapshot
       -> AgentRuntime (PiAgentAdapter)
       -> ResponseKernel
  -> PresentationRuntime (Profile renderer + effects)

AgentRuntime -> CapabilityKernel -> PlatformAdapter (Tauri/Rust)
MemoryKernel  -> Markdown workspace
```

每个 Module 对外只暴露小 Interface，把复杂实现留在内部：

| Module | Interface | 实现责任 |
|---|---|---|
| `CompanionKernel` | `send`、`cancel`、`switchSession`、`activate`、`setMode`、`subscribe` | 编排会话、Agent、记忆、表现事件；UI 不直接调用各子系统。 |
| `AgentRuntime` | `execute`、`abort`、`dispose` | Pi 消息、流、工具循环、超时和错误归一化。 |
| `MemoryKernel` | `prepare`、`capture`、`consolidate`、`forget` | Markdown 解析、内存索引、召回、提炼、审计和数据迁移。 |
| `CapabilityKernel` | `list`、`request`、`approve`、`revoke` | 工具声明、权限决策、会话信任、超时、审计和结果截断。 |
| `CardRuntime` | `activate`、`context`、`applyResponse` | Card 加载、变量规则、阶段文案、情绪映射和回退。 |
| `PresentationRuntime` | `activateProfile`、`applyEffect` | 素材、主题、音效、灵动图层和窗口表现。 |
| `PlatformAdapter` | 受限的文件、进程、窗口、监控与剪贴板操作 | Rust 路径校验、条件编译、OS 差异和子进程生命周期。 |

`AgentRuntime` 有 Pi 和测试 Fake 两个 Adapter，因此 Seam 是真实的；不保留
长期 Legacy Loop。`CapabilityKernel` 是唯一允许跨越到 Rust 副作用的 Module，
这样安全和审计不会分散到 Tool、MCP、Skill、Coding Worker 中。

### 3.3 用户消息主链路

```text
用户输入 / 前台窗口主动事件
  -> CompanionKernel (并发、来源、会话有效性)
  -> ConversationKernel (追加用户事件)
  -> CardRuntime.refresh()
  -> MemoryKernel.prepare() + CapabilityKernel.list()
  -> ContextKernel (严格 token 预算)
  -> PiAgentAdapter.execute()
       -> CapabilityKernel.request()
       -> Safety decision / user confirmation / PlatformAdapter
  -> ResponseKernel (DeskPetEnvelope)
       -> CardRuntime.applyResponse()
       -> ConversationKernel.persist()
       -> MemoryKernel.capture()
  -> typed CompanionEvent -> Vue / PresentationRuntime
```

主动搭话仍使用同一链路，但带 `origin: active`：更小上下文、无工具或只读工具、
严格冷却和更短的回复预算。它不能借由主动事件启动高权限能力或产生长期记忆。

## 4. Profile、Card 与表现层

### 4.1 可组合的桌宠模型

Profile 是自包含的视觉和感官包：角色帧、主题、字体、音效、遮罩和灵动图层。
Card 是行为包：角色设定、输出规则、行为语气、情绪映射、阶段文案和变量定义。
运行时只保存一个组合选择：

```text
CompanionSelection = { profileId, cardId, sessionPolicy, mode }
```

Profile 不包含 Prompt 规则，Card 不包含素材路径；二者用通用情绪键和效果键
协作。Profile 缺少某个效果时回退到无效果或默认 Profile，不修改 Card。
Card 缺少某个情绪映射时回退中性表达，不修改 Profile。

### 4.2 ResponseKernel

模型最终输出需要同时携带用户可见文本与受限的角色状态更新。将现有
`RUNTIME_DATA` 重命名为内部 `DeskPetEnvelope` 契约：

- 用户文本和内部数据必须可分离；内部数据永不显示。
- 首期兼容 `<RUNTIME_DATA>` 传输格式；支持 JSON Schema 的 Provider 可以走
  结构化输出，但最终都归一为同一 Envelope。
- `CardRuntime.applyResponse()` 只接受 Card 注册、允许 LLM 更新、类型和范围
  合法的字段；`system`、`interaction`、`session` 仍由系统维护。

这使 Pi、Provider 和 UI 都无法绕开变量校验。Card 仍是角色状态，不承担用户
长期记忆。

### 4.3 前端结构

```text
src/
  app/                 composition root、路由、窗口初始化
  ui/                  Vue 纯展示与交互
  core/                companion、conversation、context、memory、card、capability、agent
  adapters/            pi、provider、tauri、mcp、filesystem、clock
  presentation/        profile、effects、audio、parallax
  shared/              schemas、事件、错误、token 预算、日志
```

Vue 只订阅 `CompanionKernel` 的 typed event 和只读状态快照。组件不再直接 import
Provider、Memory、ToolRouter 或 Tauri 命令；这样窗口表现、聊天面板和设置页不会
成为 Agent 生命周期的隐式控制器。

## 5. Pi Agent 与 Coding 能力

### 5.1 Pi Core

Pi Core 负责统一的多轮模型/工具循环、事件流、取消、steer/follow-up、上下文
转换和工具前后钩子。`PiAgentAdapter` 必须：

- 使用 `toolExecution: "sequential"`，直到 Capability 并发、确认与会话信任
  都完成单独验证。
- 在 `beforeToolCall` 调用 `CapabilityKernel.request()`；被拒绝、取消或超时的
  工具结果以标准结果回注，不产生旁路。
- 用事件映射 generation/tool 阶段，不让 Pi 直接修改 Vue、Card 或文件。
- 从 ContextKernel 接收现成 Prompt；Pi 不自行读取 `AGENTS.md`、Profile、Card
  或 Desk-Pet 的记忆文件。
- 每个活动 Desk-Pet session 只保留一份内存 transcript；重启时由会话 Markdown、
  摘要和 MemoryKernel 重建，不采用 Pi Harness 的 session 存储。

### 5.2 Coding 路线

助手模式先使用“Pi Core + CapabilityKernel”完成代码阅读、搜索、编辑、命令、
Git、MCP 和 Skill。能力是 Tool Contract，而不是 `pi-coding-agent` 包的专利。

`pi-coding-agent` 的 CLI/TUI、Node 文件系统、项目配置发现、JSONL 会话、扩展
包和原生依赖不能进入 WebView。只有当 POC 证明现有工具加 Pi Core 无法覆盖
项目级编码工作流时，才启动独立 Coding Worker：

```text
Assistant task -> CapabilityKernel approval
  -> spawn restricted coding-worker process
  -> LF JSONL RPC over stdin/stdout
  -> normalized events/results -> CompanionKernel
  -> task finish / cancel / timeout => kill worker
```

Worker 没有直接写入 Desk-Pet 的 Profile、Card、Memory 或 session 文件的权限；
所有写入回到 CapabilityKernel 审批。这保证重能力按任务存在，而非永久占用。

## 6. MemoryKernel：纯 Markdown 记忆系统

### 6.1 文件与分层

```text
data_root/
  memory/
    CANDY.md                 人类指令，只读自动写入
    USER.md                  稳定用户模型，受控更新
    MEMORY.md                精炼的长期事实、关系和决策
    daily/YYYY-MM-DD.md      事件层：观察、会话要点、候选
    projects/<project>.md    项目工作知识
    DREAMS.md                consolidation 审计、冲突和回滚摘要
  sessions/*.md              完整会话与压缩摘要
```

所有持久化内容均为 Markdown。每条长期条目携带可读的 HTML 注释元数据：稳定 id、
类型、来源会话、来源可信度、观察时间、重要性、状态、触发词、项目键和可选
过期时间。注释在注入 Prompt 时可剥离，在维护操作中可完整保留。

```md
- 用户希望技术说明直接、中文、先给结论。
  <!-- id: mem-01; kind: preference; source: session-20260907-x;
       origin: owner; importance: 9; status: active;
       trigger: 汇报, 技术说明, 中文 -->
```

### 6.2 写入路径

```text
用户明确“记住” -> validated candidate -> USER/MEMORY (可要求确认)
普通对话或工具结果 -> daily/session candidate (含 provenance)
会话结束、压缩前或空闲 -> deterministic gate -> bounded LLM consolidate
通过 -> 原子替换 USER/MEMORY + DREAMS.md 审计
不通过 -> 保留 event 层，不污染长期层
```

写入规则：

- 外部网页、MCP、文件和工具输出默认 `untrusted`，不可自动晋升。
- 主动搭话、定时任务、子代理和已召回的记忆不产生长期候选，避免记忆自我复制。
- 模型负责语言层面的提炼和冲突建议；来源、类型、阈值、允许提升范围、原子
  写入和回滚由确定性代码强制。
- consolidation 是低优先级任务：轻量模式只做本地整理和显式写入；助手模式可在
  空闲时批量调用低成本模型。失败绝不阻塞用户回复。
- 修改前比较内容 hash，写入使用临时文件加原子 rename；人工编辑冲突时放弃本轮
  改写并留下审计。

### 6.3 召回路径

启动时解析 Markdown，在内存建立中文字符 n-gram、英文词元、标题、trigger、
项目键和来源字段的倒排/BM25 索引；该索引不落盘。每轮不调用模型的召回顺序：

1. 预算内 bootstrap：`CANDY.md`、`USER.md` 与极短 `MEMORY.md`。
2. 对当前消息做 lexical/hybrid score：相关性、重要性、时间衰减、项目匹配、
   可信度和显式 trigger。
3. 只自动注入 curated 层的少量强命中条目，并注明来源。
4. 当用户出现明确回忆意图、时间问题、多跳项目问题，或快速召回低置信度时，
   扩展搜索 daily 与 session Markdown；必要时由助手模式作一次受预算限制的深度
   检索。

MemoryKernel 输出固定 token 预算的 `MemoryContext`，ContextKernel 无权无限
拼接文件。每次注入、命中 id、token 数、是否进入深度检索都记录到调试审计中。

### 6.4 参考与取舍

OpenClaw 的分层、来源可信度、写入门槛、召回双通道和 dreaming consolidation
值得借鉴；它本身采用 Markdown 加 SQLite 索引，因此不作为依赖。
[其记忆架构](https://github.com/openclaw/openclaw/blob/main/docs/concepts/memory-architecture.md)
明确指出写入质量比复杂检索更重要。Basic Memory 的 Markdown/wikilink 思想可
借鉴，但其 SQLite/vector 依赖与 AGPL-3.0 许可证不适合直接嵌入。Mem0 的实体、
时序和评估思路可参考，但 embedding/向量存储不符合本方案。

## 7. Capability 与平台安全重建

工具必须先经过 Capability，再有 Provider/Pi/MCP/Worker 看到它。每项能力定义：

```text
id, schema, read/write effect, scope, platform support,
required approval, timeout, output cap, provenance tag, audit formatter
```

CapabilityKernel 的决策顺序固定为：模式许可 -> 工具存在 -> 参数校验 -> 路径和
平台校验 -> 风险分级 -> 会话/单次确认 -> 执行 -> 输出截断与来源标记 -> 审计。

- 轻量：只读和低风险工具；NORMAL/DANGER/NOWAY 直接拒绝并人格化反馈。
- 助手：显式确认、细粒度会话授权、可撤销信任和完整审计。
- Rust：所有业务路径经 `AppPaths` 和 `validate_path()`，不存在的目标校验父目录；
  profile/card/memory/file 工具使用同一受限文件 Module。
- MCP：仅助手模式动态连接；工具描述、调用结果和 server 生命周期都经
  CapabilityKernel，外部结果默认不可信。

这同时解决当前“某些 Rust 命令和某些前端路由各自决定安全”的结构问题。安全
确认本身不由 Pi 或 Coding Worker 实现。

## 8. 数据、配置与会话

| 数据 | 真相源 | 所属 Module |
|---|---|---|
| Profile 资源与 YAML | 内置只读或用户 Profile 文件夹 | PresentationRuntime |
| Card 定义与角色变量 | Card 文件与 `personality/stages/` | CardRuntime |
| 用户设置和功能配置 | 类型化配置与用户覆盖 | AppConfig |
| 对话和压缩摘要 | `sessions/*.md` | ConversationKernel |
| 长期/事件记忆 | `memory/**/*.md` | MemoryKernel |
| Pi transcript | 仅当前进程内存 | PiAgentAdapter |
| MCP/Coding Worker | 活跃任务进程 | CapabilityKernel |

配置不是记忆；Card 状态不是用户事实；Pi transcript 不是会话真相源。这三条
禁止跨 Module 写入，是重构后的核心数据规则。

旧数据通过一次性 importer 迁移：保留原文件只读备份，解析旧 `MEMORY.md`、
`User.md`、`Project.md`、sessions、Card variables 和 Profile；生成可预览的迁移
报告。失败不覆盖任何旧文件，用户可重试或导出。

## 9. 测试与验收

### 9.1 测试面

| 测试面 | 必测内容 |
|---|---|
| Card/Profile 组合 | 随机组合、缺少素材/映射、切换回滚、变量隔离、灵动图层性能。 |
| Agent Runtime | 纯聊天、工具循环、取消、超时、重试、会话切换、主动消息、Provider 失败。 |
| Capability | 路径逃逸、敏感文件、确认取消、会话信任撤销、MCP 不可信输出、Worker 终止。 |
| MemoryEval | 事实召回、干扰项、修正、过期、删除、来源追溯、提示注入、token 上限。 |
| 数据迁移 | 旧 Profile/Card/会话/记忆导入、幂等、失败回滚。 |
| 资源基准 | 冷启动、首次聊天、轻量工具、助手工具、MCP、模式降级、侧车退出。 |
| 跨平台 | Windows/macOS 路径、窗口监控、快捷键、进程与 shell 分支。 |

MemoryEval 同时运行确定性检索测试和真实 Provider 场景。验收至少要求：目标
记忆可在预期 Top-K 内召回；更正与删除不会残留 active 条目；不可信内容不会
自动提升；Prompt 注入始终不超过预算。不能承诺模型永远理解正确，但可以
承诺存储、召回、来源与预算行为可重复验证。

### 9.2 切换门槛

新 Runtime 只有在以下条件全部满足时才替换旧路径：

1. P0 Pi/Tauri 资源基准完成，且用户确认数值取舍。
2. MemoryEval、Capability 和现有 Live Test 的当前契约全部通过，合同 hash
   与源码一致。
3. 导入器在真实旧数据副本上完成无损预演。
4. Windows 和 macOS 的关键路径经过实际桌面验证。
5. 旧 Loop、旧 MemoryService 和分散 ToolRouter 不再有生产调用方后才删除，
   不永久维持双实现。

## 10. 实施顺序

### Phase 0：基线与 POC

- 建立当前资源、token、会话恢复、Profile/Card 组合和工具安全的基线。
- 在 `experiment/pi-agent-runtime` 验证 Pi Core 的产物、RSS、首答、Provider
  兼容和顺序工具循环；不接入 Coding Agent。
- 定义 MemoryEval corpus 和 Markdown metadata schema。

### Phase 1：核心契约与平台收口

- 建立 `shared` schema、typed `CompanionEvent`、错误模型和 token budget。
- 重建 PlatformAdapter/CapabilityKernel，先收口全部文件、进程、MCP 和窗口调用。
- 不迁移 UI 外观，先让旧界面通过新 Capability 运行。

### Phase 2：MemoryKernel 与会话

- 实现纯 Markdown parser、内存索引、分层写入、召回、审计和 importer。
- 让 ConversationKernel 成为 session 真相源；删除 Pi/Provider 对持久化的直接写入。
- 完成 MemoryEval、迁移预演和回滚流程。

### Phase 3：Pi 统一 Conversation Runtime

- 落地 PiAgentAdapter、Model Adapter、ContextKernel、ResponseKernel。
- 先用轻量工具集跑完整聊天/主动互动链路，再用同一 Loop 启用助手工具集。
- 旧 Agent Loop 只作为短期对照 Adapter；通过验收后删除。

### Phase 4：表现与设置重组

- 将 Profile/Card 组合、素材预览、图层编辑、音效和主题收敛到 PresentationRuntime
  与 CardRuntime。
- 重新组织 Vue，只保留展示和交互，不保留业务单例。
- 更新导入导出，确保用户可以打包 Profile、Card，并迁移数据。

### Phase 5：Coding 与生态

- 先验收 Pi Core + Capability 的代码工作流。
- 只在明确缺口存在时建设 Coding Worker RPC POC；MCP/Skill 以 Capability
  Contract 接入，不重新创造另一套权限系统。

### Phase 6：切换和删除

- 用 importer 迁移真实用户数据，保留只读备份与报告。
- 默认切到新 Kernel，监控资源、记忆命中、错误与安全拒绝事件。
- 删除旧运行路径、旧兼容配置和过期文档；更新 README、AGENTS、DES 与当前模块
  契约，将本计划移入历史。

## 11. 明确不做的事

- 不把桌宠表现、人格状态或用户记忆交给 Pi/Coding Agent 的私有存储。
- 不让向量数据库、SQLite、云记忆服务成为 Markdown 记忆的隐式依赖。
- 不直接运行第三方 Extension、Skill 或 MCP 的任意代码来获得“更聪明的记忆”。
- 不以永久 Feature Flag、长期双 Loop 或双记忆系统代替完成迁移。
- 不以“模型应该知道”替代路径校验、来源、权限、token 预算和数据迁移验证。
