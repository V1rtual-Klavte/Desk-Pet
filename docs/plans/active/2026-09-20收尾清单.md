| 编号 | 状态 | 当前边界 | 完成条件 |

| L3 | **开放问题** | 启动脚本按声明 `sourceFiles` 算 hash，未审计依赖闭包 | 闭包差异清单已出（见下）。**加不加门禁、豁免怎么划，须先决策** |
| 场景无法表达"期望失败" | 待实施 | `scene-runner.ts` 把带 `output.failure` 的回合记成 trial error，因此"期望失败"的回合不可能出现在通过场景里；溢出恢复的两条失败路径只有手工证据 | 让 Scene 能声明「本回合预期以某类失败结束」并计入通过 |

**L3 决策输入**：从 `sourceFiles` 出发做静态 import 图 BFS，闭包外共 92 个文件，其中 **89 个被 ≥5 份契约共享**（成因是 barrel re-export 把整个模块拖进闭包 + `CONFIG.yaml`／`config.ts`／`logger`／`error` 一类共享骨架）。真正的"漏声明"只有 1 条（`personality-card` 经 `personality/registry.ts` 可达 `engine/pi/runtime.ts`）。按共享骨架 + type-only 边豁免的话，全闭包门禁几乎只剩这一个发现；要让它"有牙"则每份契约需额外声明 30–40 个文件，hash 维护成本显著上升。

## 5. 验证缺口

以下均在实现范围内已完成，但**缺的是验证手段**，完成前不得宣称已发布就绪：

- **Windows 分支与 Windows CI**：本机 macOS 只能证明 cfg 隔离成立、类型正确，不证明运行时行为。
- **跨进程重启的人工冒烟**：`app_restart` 的进程级重启链路未在真实应用里点过。
- **UI 未经人工查看**：本轮的 ChatPanel 排队面板与投递意图选择、设置页新增控件（对话投递 / 只读并行）、`DebugBar` 的 Σ 用量面板，均只过了类型检查与 Live 场景（Live Test 宿主不渲染 UI）。设置页「修改 → 保存 → 文件回读 → 关闭重开」的往返未执行。
