## 3. 工程加固待办

### 3.1 测试基础设施

| 编号 | 状态 | 当前边界 | 完成条件 |
|---|---|---|---|
| Rust 单测不在门禁内 | 待实施 | `cargo test --lib` 现有 37 个测试（含许可回收的 3 个），但 `pnpm run test:types` 只跑 `cargo check`，CI 同样只 check——**新写的 Rust 单测永远不会被执行**，等于写了没人跑 | 把 `cargo test --lib` 接进 `test:types` 或独立门禁脚本，并确认 CI 也会跑 |
| `classifyTurnFailure` 的分类正则 | 待实施 | 用 `/5\d\d/` 判 provider，会命中预算判定文案里估算值的数字片段——估算值形态一变，本地预算失败就会被误分类成 provider 失败（当前表现为 T3 只能声明一组 kind 来兜） | 收紧为 `\b5\d\d\b` 或改用结构化判据；注意该文件在 6 份契约的 sourceFiles 里，改它会连带触发 hash 重算 |

**「场景无法表达期望失败」已完成**：`TurnDef` 增可选 `expectFailure`（kind + message 匹配器，空匹配器在数据集预检被拒），判定走普通断言通道，因此预期之外的失败、回抛异常、跳过与超时仍照旧判失败；未声明 `expectFailure` 的回合行为完全未变。溢出恢复的两条失败路径（恢复用尽、无摘要范围 declined）已从手工证据变为门禁内场景，负向探针实测「给正常回合加声明」与「文案改错」都会 FAIL。

**L3 已决策：不加门禁。** 审计结论存档于此——从 `sourceFiles` 出发做静态 import 图 BFS，闭包外共 92 个文件，其中 **89 个被 ≥5 份契约共享**（成因是 barrel re-export 把整个模块拖进闭包，加上 `CONFIG.yaml`／`config.ts`／`logger`／`error` 一类共享骨架）。真正的"漏声明"只有 1 条（`personality-card` 经 `personality/registry.ts → stages-cache.ts → engine/pi/index.ts` 可达 `engine/pi/runtime.ts`），而那条也只是经 barrel 的偶然可达，补进去只会让 `runtime.ts` 每次变动都连带作废该契约的 hash。按共享骨架与 type-only 边豁免后门禁近乎空转，要让它"有牙"则每份契约需额外声明 30–40 个文件、hash 维护成本显著上升；**收益不抵成本，故不引入**。该审计的价值是一次性的：它证明了"闭包差"几乎全是 barrel 噪声，而不是契约普遍漏声明。
