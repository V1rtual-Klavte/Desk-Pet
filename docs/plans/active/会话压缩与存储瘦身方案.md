# 会话压缩与存储瘦身方案

本页是**需求真相源**（为什么改、证据、改法论证）。**执行真相源**见[会话压缩与存储瘦身执行方案](会话压缩与存储瘦身执行方案.md)（改哪个文件、什么顺序、怎么验收、覆盖矩阵、待裁定清单）。

本页是**尚在实施的目标契约**。它同时解决两件**必须一起完成**的事：

1. **压缩分级重构** —— 把会话压缩从「一次性整段摘要」改造成**成本递增的分级阶梯**，核心判据是「**这条结果还能不能捞回来**」，并把回读地址无条件暴露给模型。
2. **会话存储瘦身** —— 解决会话 JSONL 的**体积膨胀**与**写入频率**（实测 124.8 次/秒）。

**为什么必须一起做**：模型频繁回读原文是压缩方案的收益来源，而回读要先打开会话文件（全量读 + 逐行重放）。存储层不解决，压缩方案的收益会被读取与写入成本吃掉。

实施完成后正文与证据归档到 `docs/history/implementation/`，本页随之撤销。

**硬约束：不改依赖。** 全部改动落在本仓可控制的层——`DataRootSessionRepo` 包装层、注入的 `FileSystem` 装饰器、请求投影层。不 patch `node_modules`、不改 `package.json` 的依赖集合。

## 1. 背景与实测问题

### 1.1 现状分工

压缩由 `@earendil-works/pi-agent-core@0.85.1` 的 AgentHarness 调度（阈值 / 手动 `/compact` / 一次性溢出恢复），切点与单事务提交也在上游；**摘要内核在宿主**（[compactor.ts](../../../src/services/engine/compactor.ts) 的 `summarizeCompaction`）。

会话正文以数据根 `sessions/` 的 JSONL 为真相源（`JsonlSessionRepo`，commit 事务写入）；`sessions/index.json` 只保存可丢弃 UI 状态。

### 1.2 文档声称 vs 代码事实（压缩三层对账）

`docs/current/memory.md` 把压缩描述为 L0/L1/L2 三层。逐条对账：

| 层 | 文档声称 | 代码事实 | 判定 |
|---|---|---|---|
| L0 阈值/执行/接线 | 按 `normalInputTarget × 10%` 缩短大工具结果 | [tool-output.ts:10,26-28,59-71](../../../src/services/context/tool-output.ts)，`transform_context` 钩子已接线 | **真实** |
| L1 切分 | 「最旧的连续完整用户意图轮」 | **宿主零代码**，切点全在上游 `findValidCutPoints` | **归属错**：是上游行为，被叙述成本仓设计 |
| L1 工具批次不拆 | 本项目保证 | 上游 `case "toolResult": break` | **真，但属上游** |
| L1 最后一轮保留 | 硬保证 | 上游允许切进当前回合（`isSplitTurn`），宿主只换指令文案 | **部分真** |
| L1 大历史分多次有界提交 | 有实现 | **全仓零命中**，超限直接抛错 | **话术** |
| L2 硬预算/溢出/可解释错误 | 判定→一次性恢复→可解释失败 | [runtime.ts:657-661](../../../src/services/engine/pi/runtime.ts)、[model-gateway.ts](../../../src/services/engine/pi/model-gateway.ts) | **真实** |

### 1.3 必须解决的六个问题

**问题 A：判据缺失，导致「能捞回来」这件事没人用。**

[tool-output.ts:61](../../../src/services/context/tool-output.ts) 的 `if (estimateContextTokens(text) <= budget) return text` —— **没过阈值的结果原样返回，一个 id 都不给**。于是摘要覆盖区里只有「当初被 L0 缩短过」的结果留下了地址；**小结果（数量最多的一批）一旦被摘要吃掉，模型既没有内容也没有地址**，甚至不知道自己有过这条结果。

**问题 B：高危洞 —— 会话可永久无法压缩。**

```
compactor.ts:86-88   摘要素材超硬上限 → throw ContextBudgetError
runtime.ts:590-598   catch → 一律 decline
上游 structural.js   见 declined 即放弃（不回退、不重试）
```

L0 单条上限约 10435 tokens（128k 窗口），硬上限 124354 → **约 12 条满额工具结果**即可让摘要素材独立超限。此后阈值 / 溢出 / `/compact` **全部走同一条路 decline，会话永久压不了**，只能换更大窗口的模型。`preserve` 的结果完全不缩短，会加速触发。

**问题 C：只有一档手段，没有阶梯。**

当前零成本手段只有「缩短」一档（保留约 `normalInputTarget × 10%`）。对可捞回的结果而言这是**浪费**——清空到占位串可再省约 200 倍空间，而信息并未真正丢失。

**问题 D1：会话 JSONL 体积膨胀（实测）。**

| 指标 | 实测值 |
|---|---|
| 文件行数 | **2187 行** |
| 文件大小 | **792,898 字节（约 793KB）** |
| 真实对话时长 | **16.5 秒** |

`pi.pending.assistant_frame` 一个命名空间占 **2056 / 2187 = 94%**：

```
list/append              2056   ← 94%
value/set                 214
entry                      47
value/delete               23
usage                       9
list/delete                 9
```

它不是 entry——**每个流式增量（delta）都落一行**：

```
thinking_delta   1398   67%
text_delta        570   28%
toolcall_delta     41    2%
（start/end 边界）   47    2%
```

**9 个 assistant 帧 → 2056 行**，单帧最多 **663 行**。这条会话只聊了**几轮、16.5 秒**。

**问题 D2：写入频率（实测）。**

用「帧的 `responseEntryId` 对应的 assistant 条目时间戳」减去「帧最小 seq 之前最近一条条目的时间戳」作为响应时长：

| 帧 append 数 | 响应时长 | 速率 |
|---:|---:|---:|
| 663 | 3.9s | **168.1 /s** |
| 495 | 3.3s | 149.9 /s |
| 223 | 1.9s | 118.8 /s |
| 209 | 1.2s | 171.0 /s |
| 184 | 1.4s | 136.0 /s |
| 114 | 1.3s | 86.9 /s |
| 64 | 1.3s | 50.5 /s |
| 62 | 1.2s | 52.2 /s |
| 42 | 1.0s | 41.8 /s |

> **合计 2056 次 append，总时长 16.5 秒，平均 124.8 次/秒，峰值 171 次/秒。**

机制（上游 `harness/runtime/progress.js` 的 `openProgress`）：**每个 delta 一次 `lane.command`** → 一次 `{ kind: "commit" }` → 一次 Rust `file_append` IPC。

而 Rust 侧每次 append 都要重做一整套（`src-tauri/src/commands/tool_exec.rs` 的 `file_append`）：IPC 往返 → `validate_new_file_path` → `symlink_metadata` → `ensure_regular_file` → `create_dir_all` → open + append。**外加**每次 commit 的状态机投影、seq 分配与内存状态更新。

按单次 2ms 估算，125 次/秒 ≈ **一个核心的 25%** 持续用于写进度；单次 5ms 则约 62%。**这是确凿的性能问题，不是理论担忧。**

**问题 D3：读取成本随文件线性增长。**

会话打开时**全量读 + 逐行重放**（上游 `harness/session/jsonl/storage.js`）：

```js
const content = await options.fileSystem.readTextFile(options.path, context);   // 无 maxLines
const { lines, torn } = splitCompleteLines(content);
for (let index = 1; index < lines.length; index++) {
    storage.replayCommitted(parseTransaction(line));   // 逐行 JSON.parse + 重放
}
```

**对比**：同一个包里读 header 时用了 `{ maxLines: 1 }`——按需读的能力存在，只是 open 时没用。且**文件只增不减**（无任何 trim / compact 机制）。

### 1.4 三条澄清（避免后续误判）

**① 帧的逻辑状态是干净的，问题纯在物理层。**

上游**确实会删除**帧（`deleteList` 在 `drive/response.js`、`drive/terminal.js`、`drive/deferred.js` 三处触发）。实测那 9 个帧**全部有对应的 `list/delete`**。

**但 delete 只是往日志追加一行 `op: "delete"`——旧的 2056 行 append 永远留在文件里。** 这是 append-only log 的本质。

**结论：「帧 = 在飞的助手响应的持久暂存区」这个设计是对的**（支撑崩溃恢复、满足「正文以 commit 事务写入」的纪律、崩溃最多丢最后一块）。缺的不是存法，是**回收机制**。

**② UI 不受影响，但成本照付。**

UI 走 `src/services/session/read-model.ts` 的 `messagesFromEntries()`，从**同一批 session entries** 投影（`compaction` / `branch_summary` 等控制 entry 不进聊天视图）。**帧不是 entry**，所以 UI **不会显示**它们——但**它们在同一个文件里，open 时必须一起读进来**。

**UI 显示的历史走的是同一条真相源。** `messagesFromEntries()` 消费 session entries，与压缩、回读同源——**没有第二条历史路径**。存储层做的任何改动都会同时影响这三者，不存在「只坏 UI 不坏正文」或反之的情形。

**③ 「提交」不请求 LLM。**

「提交」= 一次事务写入会话 JSONL（上游 `JsonlStorage.commit` → `prepareCommit` 校验并分配 seq → `appendFile` 追加一行 → 更新内存状态）。压缩的先后关系是：**先花 LLM 算摘要 → 再提交**。

「提交成功前不报告完成」的意义在于：LLM 成功与 commit 成功会分开失败；若 commit 失败却报「压缩完成」，UI 的 epoch 会前进而盘上什么都没变，造成 **UI 与真相源分叉**。

## 2. 核心判据（本方案的地基）

> **唯一判据：这条结果还能不能捞回来。必要动作：告诉模型去哪捞。**

这条判据把「哪些能压」一次性解决——不需要判可重建性、不需要判关系价值、不需要读 `effect` / `replay`。

**判据的落点**：`toolResultAddress(message)` 能否取到 `details.deskpetEntryId`。

| 结果 | 能捞回来吗 |
|---|---|
| 成功的工具结果（有 `details.deskpetEntryId`） | ✅ |
| 失败 / 中断的结果（**地址只在成功分支写**） | ❌ |
| >5MB 的结果（`MAX_TOOL_FILE_BYTES` 落盘失败） | ❌ |
| 跨会话回读 | ❌（回读工具只认当前会话） |

### 2.1 兜底边界

只有数据根 `sessions/` 下的会话 JSONL 是真相源。**Bash 的 spill 文件不算**——它由 Rust 侧 `evict_old_spills()` 淘汰，`docs/current/memory.md` 已明确「不能把这些文件等同于持久会话原文」。

判据口径因此定为：**JSONL 里有什么，就能捞回什么。**

### 2.2 与长期记忆的边界（明确排除）

**压缩 ≠ 记忆。** 用户事实、偏好、画像、跨会话关系归长期记忆系统（`MemoryProvider` + 画像投影，P6）；压缩只管**会话内的工作上下文**。

因此「关系价值」**不作为压缩的分级轴**——不是它不重要，是它不由压缩保障。这与既有不变量一致（AGENTS.md：「不得把压缩摘要、工具结果、主动消息或助手台词晋升为用户事实」）。

### 2.3 一个必须正视的隐含代价

判据的区分度很小——它会把绝大多数成功结果判成「可压」。这带来一个真实风险：

> **「捞得回来」≠「模型会去捞」。**

若把工具结果清得很狠，模型看到的是「我调用了 read_file，结果已压缩 + 地址」，它得**自己意识到**可能需要那个内容再去取。CC 敢这么做是因为它清的全是可重跑的（重读文件比翻历史更自然）；本仓若清掉**时点快照、写事件**，模型可能根本不会想到去捞。

**这不是判据错了，是判据只回答了「允不允许压」，没回答「压到什么程度该停」。** 后者由 §3.3 的保护区承担。

## 3. 手段阶梯

### 3.1 为什么按激进度排而不是按成本排

CC 的阶梯（`toolResultBudget → snip → microcompact → contextCollapse → autocompact`）按**成本**递增排。但本仓的两个零成本手段**成本相同、激进度差一个数量级**：

| 手段 | 保留量（128k 窗口） | 成本 |
|---|---|---|
| 缩短 | 约 10.4k tokens | 0 |
| 清空 | 约 50 tokens（占位串） | 0 |

**差约 200 倍**，按成本排不出顺序，因此**按激进度排**。

### 3.2 阶梯定义

| 级 | 手段 | 适用条件 | 成本 |
|---|---|---|---|
| **0** | **不动** | 落在「最近 N 轮」保护区内；或该工具标了 `resultProjection: "preserve"`；或未超单条阈值 | 0 |
| — | **保护区的边界（2026-09-27 裁定）** | **保护区只挡级 2 与级 3，不挡级 1** —— 保护区内的超阈结果仍按级 1 缩短（零成本、保留头尾），但**永不被清空、永不被写进摘要覆盖范围**。理由：级 1 与级 2 的成本相同，把级 1 也挡掉会让「1+2 压完装得下就不花 LLM」（C-4）在最常见的形态下永不触发，并新增一条「保护区内超阈结果 → 回合失败」的路径。裁定与两侧代价见[执行方案](会话压缩与存储瘦身执行方案.md)附录 C 第 1 项 | — |
| **1** | **缩短** —— 留头尾 + 占位串 + 地址 | 单条超阈值 | 0 |
| **2** | **清空** —— 正文换成占位串 + 地址（覆盖级 1 的结果） | 单条超阈值 **且 有地址 且 仅靠级 1 后仍超 `normalInputTarget`** | 0 |
| **3** | **摘要** —— 整段结构化摘要 | 1+2 压完仍超 `normalInputTarget` | 1 次 LLM |

**「装得下」的唯一判据**：请求视图的估算不超过 **`contextBudget(window).normalInputTarget`**。级 1–3 的停止条件全部用它，不另设阈值。（`hardInputLimit` 是另一道闸门——超它时先走一次性溢出恢复，见 §1.2 的 L2 行，不属本阶梯。）

**三条设计要点：**

1. **先 1 后 2，不是二选一。** 缩短是保底（留个印象），清空是加码（空间还不够时才用）。两者可分别调整。
2. **级 2 有硬前提：有地址。** 判据落地——`toolResultAddress()` 取不到地址的结果**永远不允许升到级 2**，只能停在级 1。这条是安全阀。
3. **级 3 是闸门不是替代。** 1+2 压完请求装得下时，**一次 LLM 都不花**。这是相对现状最大的收益点（现状每次压缩必然花一次摘要调用）。

### 3.3 保护区

- **N = 3 轮起步**，落地后用场景校准。定义放所属模块常量，不散落。
- **「轮」的口径**：以**用户意图轮**为单位（一条用户输入开启一轮，直到下一次用户输入为止），与上游切点的 turn 语义对齐，不按助手消息或工具调用计数。
- 保护区的意义：保住「刚才干了什么」的现场感，避免模型对着被清空的历史失去短期连续性的锚点。

### 3.4 两个标记

「压缩标记」在本方案里是两个不同的东西，都不改正文真相源：

| 标记 | 形态 | 覆盖范围 |
|---|---|---|
| **逐条标记** | 占位串本身（含量级信息与回读地址） | 单条工具结果 |
| **整段标记** | 既有的 compaction 条目（上游单事务提交） | 一次整段摘要 |

原文条目始终保留在数据根 `sessions/` 的 JSONL 里；标记只是**请求视图**里的路牌。

## 4. 地址可见性

### 4.1 无条件带地址

**所有工具结果在请求投影时都附回读地址**，不论是否被压缩、是否超阈值。

理由：这是 §1.3 问题 A 的正解。有条件给地址会让「小结果被摘要吃掉后既无内容又无地址」永久存在。

代价：每条结果多几十字符；改动所有结果的请求形态，**需重新跑受影响契约**。

### 4.2 占位串形态

```
[已压缩；原结果 <短地址>，可用 read_session_event 分页读取]
```

**唯一实现**：占位串生成只保留一处定义点（现为 [tool-output.ts:59-71](../../../src/services/context/tool-output.ts) 的 `projectToolResultText`），级 1 与级 2 共用同一份文案模板，只在正文部分不同——**禁止出现第二套文案**。

无地址时分文变体（现有 `L0_NO_ADDRESS_NOTICE` 保留）：`[已压缩；该结果的原始条目没有回读地址，中间段不可恢复]`。

### 4.3 短前缀 + 唯一性匹配

现状地址是 36 字符的 uuidv7，多轮之后模型容易抄错。

**改法**：

- 投影时给出**当前会话内的最短唯一前缀**（uuidv7 为时间有序，同毫秒窗口内的条目需要更长前缀；实现在投影期计算并缓存）
- 回读时按前缀匹配：**唯一命中才返回**；歧义时返回明确错误（提示需要更长前缀），不做任意选择
- 完全匹配（给全 36 位）永远有效

**为什么选它**：零新增状态、不需持久化、不重编号。**折叠（§7）之后地址不变**——这是它相对「会话内数字序号」与「短哈希别名」的关键优势，也是本方案跨两半的唯一交界断言（X-1）。

### 4.4 分页预算化

现状 `SESSION_EVENT_PAGE_CHARS = 8000`（[session-transcript.ts:14](../../../src/services/tool/session-transcript.ts)）是固定字符常量，注释却称「由统一预算限定」。

**改法**：

- 页大小**与 L0 同源推导**——即「读回一页」= 「读回一条满额的 L0 结果」，语义自洽：`contextBudget(window).normalInputTarget` 的同一份额
- 口径从**字符**改为 **token**，与 `projectToolResultText` 的切分口径统一（否则中文页与英文页实际大小差约 4 倍）
- 随窗口单调

回读工具已标 `resultProjection: "preserve"`，页不会被二次缩短或清空（[session-transcript.ts:38](../../../src/services/tool/session-transcript.ts) 已说明这是为「避免引用→读取→又变引用」的循环）。

## 5. 工具定义：不加字段

### 5.1 结论

**`ToolPolicy` 不新增字段。** 原议「分层：工具报类别，模块定策略」在新判据下**自然塌缩**——「能不能捞回来」由运行时决定，工具能声明的静态属性全部被它覆盖，工具侧没有新信息可报。

### 5.2 唯一需要改的是语义扩展

`resultProjection: "preserve"` 现语义为「请求视图里不再被 L0 二次缩短」。**扩展为「禁止二次处理」**，同时覆盖缩短与清空。

理由：清空引入的循环风险与缩短完全一致（清空 → 模型捞 → 又被清空 → 再捞）。回读工具当前已标 `preserve`，扩展后自动获得保护。

### 5.3 开放问题：`historyCompaction: "retain"` 的处置

**本条需要决策，方案不预设结论。**

事实：

## 7. 存储瘦身

### 7.1 方案一：日志折叠（纯删除式回收）

**只回收「确定可丢」的行，不重编号、不重写任何保留行。**

| 回收对象 | 为什么安全 |
|---|---|
| 已被 `list/delete` 的 key 的**全部 `list/append`** | key 为 `${operationId}:${responseEntryId}`，operationId 全局唯一 → **永不重用** |
| 已被 `value/delete` 的 key 的**全部 `value/set`** | 同上 |

**安全性可证明**：

```
replay(原日志) === replay(回收后日志)
```

因为「对不存在的 key 做 delete」与「append 一堆再 delete」**终态相同**。这是个**纯删除变换**——比全量折叠（需要重新生成 seq，而 seq 是条目身份的一部分）安全一个数量级，且**保留行逐字不变**。

**收益（按实测数据）**：2056 条可回收 append / 2187 行 ≈ **87%**。折叠后该文件约从 793KB 降到 100KB 量级。

**折叠时机**：

1. **会话 close 时**（最自然，成本最低，用户无感）
2. **open 前按需**：无效写入占比超阈值、或文件超 N MB → 先折叠再打开（惰性，不打断使用）
3. **压缩提交后**（本来就该做重活，顺手）

**三条安全要求（强制）**：

| # | 要求 | 理由 |
|---|---|---|
| 1 | **原子替换**（临时文件 → rename） | 中途崩溃**不能损坏原文件** |
| 2 | **不改变逻辑状态** | 折叠前后必须完全等价 |
| 3 | **可验证**：折叠前后算状态 hash 对比，不一致就放弃折叠、保留原文件 | 让折叠**可测**，不靠「感觉没问题」 |

上游已有原子重写能力可参照（`storage.js` 的 `publishFileAtomically`，目前只在检测到撕裂行时使用）。

**与上游格式的耦合（必须正视）**：折叠需要解析日志格式（`storageVersion: 1`）。这是**真实的上游内部耦合**。缓解：**版本不匹配就跳过折叠**（安全降级，不报错、不影响功能）；折叠器是纯函数 `log → log'`，可独立测试。上游升版本时本层需跟进——**记为本方案的持续成本**。

### 7.2 方案二：帧节流（FileSystem 装饰器）

**插入点**：`FileSystem` 是**注入的**（`src/services/engine/pi/session-repo.ts` 的 `createPiSessionRepo` 支持 `options.fileSystem`，默认 `TauriExecutionEnv`）。因此可以在不碰依赖的前提下插入一层装饰器。

**核心规则：只合并帧。**

同一个文件里既有可丢的帧，又有不可丢的正文 entry。无差别合并会把 entry 的持久性也推迟——**entry 提交后崩溃就丢一条消息**，不可接受。

而帧与 entry 在时间上**天然分离**（帧在流式期间连续写，entry 在流结束时一次性提交），因此规则可以很干净：

```
appendFile(path, content)
    ├─ 内容是帧（含 pi.pending.assistant_frame）？
    │      → 进缓冲；命中触发条件时合并 flush
    └─ 内容不是帧？
           → 先 flush 缓冲，然后【自身直接落盘，不进缓冲】
```

**非帧写入永远立即落盘** → entry 的持久性**完全不受影响**。只有帧被推迟，而帧丢失只意味着崩溃恢复出的半截消息短一点——**它本来就是进度快照**。

**触发条件（无定时器）**：

| # | 触发 | 说明 |
|---|---|---|
| 1 | **缓冲体积达阈值** | 累计到 N KB 立即 flush |
| 2 | **遇到非帧 append** | 先 flush 再落盘。**这是天然的 flush 点**——流式结束后必然有一次 entry 提交 |
| 3 | **读同一文件** | 先 flush 再读 |

**不需要定时器。** 条件 2 保证了缓冲总会被冲干净（每次流式都以一次 entry 提交收尾），消除了原设计中「窗口到期」带来的时序复杂度。

**正确性要求**：

| # | 要求 | 理由 |
|---|---|---|
| 1 | 帧缓冲 **FIFO** | 帧是有序的增量流，乱序就拼不出内容 |
| 2 | 读前 flush | 否则 `readAssistantFrames` 读到自己没写进去的东西 |
| 3 | 关闭 / 退出前 flush | 正常退出不该丢缓冲 |
| 4 | **失败必须留痕** | 上游 `progress.js` 用 `void write.catch(() => {})` **静默吞掉帧写入失败**；装饰器层要把这个失败变成有留痕的（遵守 AGENTS.md「有意静默必须就地留注释说明为什么」） |

**预期收益**：以实测 **124.8 次/秒** 为基线，按体积触发合并后应降到**个位数/秒**量级。**具体阈值在 W1 用该基线校准**，不凭猜。

### 7.3 被否决的备选（记录理由，避免重走）

| 备选 | 否决理由 |
|---|---|
| **丢弃 `thinking_delta`**（省 68%） | 帧的 partial 被 `resume` 用于接续同一条助手消息（`harness-slot.ts` 的「上次中断的运行，继续/丢弃」路径）。丢弃会产出缺内容的续跑消息。**且单独使用仍剩约 40 次/秒，不够。** |
| **请求层改非流式**（问题从根上消失） | 上游 `AgentHarnessStreamOptions` **没有非流式开关**（仅 transport / timeoutMs / maxRetries / maxRetryDelayMs / headers / metadata / cacheRetention / deferred），全仓 `stream: false` 零命中。在「不改依赖」约束下**此路不通**。 |
| **帧与正文分离存储** | `FileSystem` 接口只暴露 path，storage 层只有一个文件的概念，分离需要上游支持路由。不改依赖则不可行。 |
| **什么都不做，只做折叠** | 实测 124.8 次/秒（约为「值得动手」阈值的 6 倍），**不成立**。 |
| **压缩层与存储层拆成两份文档** | 两者是同一批工作：回读收益依赖存储读取成本，折叠正确性依赖地址不变。拆开会让交界断言（X-1）失去载体。 |

### 11.2 测量方法（可复现，供 W1 复用）

本节两项实测数据均由会话 JSONL 直接算出，**不需要运行应用**：

1. **必须展开事务数组**：日志里既有顶层单写行，也有批量事务数组行（一行为一个 JSON 数组）。统计必须**先展开数组**，否则会漏掉 `delete` 等写入（本次曾因此误判「零删除」，得出错误结论）。
2. **写入速率的算法**：帧的 key 为 `${operationId}:${responseEntryId}`，其中 `responseEntryId` 即该次流式最终写入的 assistant 条目 id。用「该条目的 `timestamp`」减去「帧最小 seq 之前最近一条条目的 `timestamp`」即得响应时长。
3. **帧内无 delta 级时间戳**（value 仅 `{type, contentIndex, delta}`），因此**不能**直接从帧算速率——必须用上面的锚点法。

上述方法应作为后续回归测量的**固定口径**。
