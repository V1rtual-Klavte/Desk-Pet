### 3.1 批次 1 — 数据保全与安全

#### VAR-01【阻断】`stages/{cardId}.json` 三个半写写入者

**位置**：`src/services/personality/stages-cache.ts:467-482`、`src/components/settings/AITab.vue:206-216`（两者只写 `{cardId, cardVersion, cardHash, generatedAt, isFallback, stages}`）、`src/services/personality/variable-pool.ts:448-465`（用 `{...existing, variables}` 合并写）；读侧 `variable-pool.ts:454-457`（无 `variables` → `null`）；失败顺序 `registry.ts:137-139`（先 `ensureStagesReady` 可能覆盖 → 再 `prepareVariablePool` 读到被覆盖的文件 → `savePoolToDiskStrict()` 把 initial 写死）。

**实机证据（已核实）**：`data/desk-pet/personality/stages/angelkawaii.json` 的 `cardVersion=2` 与卡片 frontmatter `version: 2` 一致，但 `stages.greetings` 缺失 → `validateStages`（`stages-cache.ts:183-192`）判 false → **下次激活必然重生成**；同一文件此刻装着 `card.亲密度=4 / card.心情="开心" / interaction.unansweredCount`。

**改法**：新增 `src/services/personality/stages-file.ts` 作为该文件的**唯一读写入口**：

```ts
// stages/{cardId}.json 的唯一读写入口。
// stages 段唯一生产者 = stages-cache；variables 段唯一生产者 = variable-pool。
export interface StagesFile { schemaVersion: number; stages?: StageFileStages; variables?: StageFileVariables }
export async function readStagesFile(cardId: string): Promise<StagesFile | null>   // 仅 PATH_NOT_FOUND 返 null
export async function updateStagesFile(cardId: string, patch: Partial<Pick<StagesFile, "stages" | "variables">>): Promise<string>
```

- `updateStagesFile` 内部 = 读 → 合并 → 写；JSON 损坏时 `log.error` 后按段重建（两段都可重建，但必须留证）。
- 删除 `stages-cache.ts` 与 `variable-pool.ts` 里所有「`JSON.stringify(<整文件>)` + `personality_file_write("stages/...")`」。
- `StageVariables` 类型（`stages-cache.ts:30-36`）删除，改从 `stages-file` 导入（消除第二份格式定义）。
- `AITab.vue:206-216` 改用 `updateStagesFile`，删本地 `invoke` 与回读解析。
- `variable-pool.ts:340-351` 的本地 `readFile/writeFile` 与 `writeFileExternal` 注入参数删除（后者全仓零注入者）。

**单一真相源落点**：`personality/stages-file.ts` —— 路径、格式、合并语义、损坏容错只此一份。

#### VAR-02【重要】人格切换失败的回滚不还原变量注册表

**位置**：`registry.ts:118-149`（调 `snapshotVariablePoolState`/`restoreVariablePoolState`）、`variable-pool.ts:84-93`（只还原 `currentCardId/pool/savePending`，`registry` 是 `:112-114` 被 `initVariablePool` 覆盖的模块级状态）。

**后果**：切换失败后池是旧卡的、注册表是失败目标卡的 → `batchWriteVars`（`:500`）按错 schema 校验；`formatPoolForPrompt`（`:265`）找不到 def，变量元数据整块消失。

**改法**：`VariablePoolRuntimeState` 补 `registry: CardVariableDef[]`、`lastDailyResetKey`、`sessionKey`（后两者见 VAR-03）；`snapshotVariablePoolState` 存 `[...registry]`，`restoreVariablePoolState` 一并还原；`destroyPool`（`:519-524`）同样清空游标。

#### VAR-03【重要】`reset: "daily"` 跨重启永不触发（并入 STATE-08）

**位置**：`variable-pool.ts:198` `lastDailyResetKey` 模块级且初始化即取当天，不持久化；`:209-235` 靠 `todayKey !== lastDailyResetKey` 判定。

**后果**：桌宠常态是当晚关闭次日启动 → 模块初始化已把键设为今天 → 判「今天已重置」→ 昨天的值原样恢复。`angelkawaii` 的 `用户今天是否夸过我`（`reset: daily`）正属此类。

**改法**：游标落进**该 Card 自己的** `variables` 段（`lastDailyResetKey: string`、`sessionKey: number`）——reset 只作用于 card 变量（`:214`），游标与它治理的数据同文件、同一次合并写；`localStorage` 明确禁用。

- 模块状态改为 `let lastDailyResetKey: string | null = null`（删「初始化即今天」的假默认）。
- `applyResetPolicies(now: Date, sessionKey: number | null): string[]`：`sessionKey === null` 时**不做 session 判定**（不能凭空认定新会话）。
- 只在注册表确实含 daily 变量时推进游标，避免无谓写盘。
- 持久化字段缺失（升级前数据）→ 视为陈旧并重置一次（daily/session 语义上允许）。
- 删除死掉的会话起点转发：`variable-pool.ts:57-66`（`sessionStartMs/setSessionStart/getSessionStart`）与 barrel 导出，随 `runtime.ts:60` 的 `lastSeenSessionStarts` 一起删；`session/manager.ts:67-72,189-190` 的 `setSessionStart` 调用同步删除。

**接口需求（归 STATE 辖区）**：`getSessionCreatedAt(sessionId): number | null`（读 `SessionMeta.createdAt`，`session/store.ts:15-18`）；「已应用」标记必须持久（建议复用 `sessions/index.json`，丢失后果仅是多重置一次，**不新建存储**）。

#### VAR-04【重要】`cardHash` 记录却从不参与失效判定

**位置**：`stages-cache.ts:194-200` 只比 `cardId`/`cardVersion`，不比 `cardHash`（`:470` 写入）。
**后果**：改卡正文（角色设定/语言风格）不升 `version:` 时沿用旧角色文案，永久陈旧，只能手动「重新生成」。
**改法**：字段改名 `cardHash` → **`sourceHash`**（诚实命名，**不做兼容读取**）；`sourceHash = SHA-256(roleSetting + "\n" + languageStyle)`，与生成输入严格同源（`buildStagesPrompt` `:227-233` 只用这两段）；哈希复用 `loader.ts:242-246` 的 `computeHash`，导出为 `hashCardText`（loader 不依赖 stages-cache，无环）。`validateStagesForCard(data, cardId, sourceHash)` **去掉 `cardVersion` 判定**（`cardVersion` 仅作元数据/诊断保留）。

#### VAR-E1【重要·复核新增】设置页展开 Card 会劫持全局变量池

**位置**：`AITab.vue:155-178`（`hydrateRuntimePreview(cardId)`），触发点 `:123-126`（`toggleCardExpand`）、`:128-134`（`selectCard`）。
**现状**：对**任意** Card 直接调用真实 `initVariablePool`，把 `currentCardId/registry/savePending` 改成预览卡且不回滚。
**后果**：展开非激活卡 → 变量池所有权被劫持 → 此后 `RUNTIME_DATA` 按**预览卡 schema** 校验，写盘写进 `stages/{预览卡}.json`。

`agent/memory/provider.ts:42-47` 的 `text.slice(0, budget * 4)` 用「4 字符 = 1 token」折算，而本仓口径是中英文分列（`budget.ts:11-14`：中文约 1 token/字符）→ **中文召回文本的实际 token 可达声明 `tokenBudget` 的 4 倍**，而预算会计只按声明值 `remaining -= budget` 扣减。
**后果**：默认空实现下无实际后果，但 **P6 接真实 provider 后这就是 CJK 场景的预算穿透点**。
**改法**：改用 `estimateContextTokens(...)` 裁剪（或按估算模块显式算），不再用字符常数；超配时按 L0 的规则显式标记而非静默截尾。

**MISS-06｜`runtime.ts:360` 的 `contextEpoch ?? 0` 两处**
未知 epoch 被写成 **0** → 快照谎称「请求视图未换代」。
**改法**：未知就不写（`snapshot.ts:151` 已按可选处理）。

**MISS-07｜`runtime.ts:507-510` 的 `state.contextError ??= error` 丢掉第二个错误**
`??=` 会把后到的错误**悄悄丢弃**（第一个错误的判定交给网关是**有意**的，保留该语义）。
**改法**：保留判定语义 + 补 `log.warn("transform_context 判定记录被更早的错误占用，本次错误仅记录:", formatError(error))`。

**MISS-08｜`engine/runtime/trace.ts:72-73,95` 观测者异常静默隔离**
**改法**：模块级去重后 `log.debug("trace listener 异常被隔离", …)`（保持不影响主链路，但可查）。

#### 批次 3 补（STATE 域）

**MISS-09｜预处理器去重状态被写在临时对象上（忙碌分支）**
`runner.ts:297` 的忙碌分支用 `preprocessStates.get(originSessionId) ?? {}` 且**没有 `set` 回**，而 `preProcess` 会**就地改写** `state.lastUserText/lastUserTime`（`preprocessor.ts:96-97`）。
**后果**：当某会话的第一次 `sendMessage` 落进忙碌分支（该会话已有由「继续中断运行 / 主动搭话 / 后台回复」等非 `dispatchMessage` 入口发起的 run）时，去重窗口不会被记录 → **30 秒内重复发送同一文本会被投递两次**（一次 steer、一次 next turn）。去重状态的所有权被拆成「runner 的 Map + 调用点默认 `{}`」两处。
**改法**：忙碌分支同样 `set` 回；更彻底的做法是把去重状态收进 preprocessor 模块、按 `sessionId` 键控，消除双所有权。

**MISS-10｜`plan-checkpoint-store.ts:23-28` 形状不合的条目静默 `return undefined`**
旧格式与损坏数据无法区分。
**改法**：保留跳过语义 + `log.warn("忽略无法解析的 checkpoint 条目", {sessionId, entryId})`。

**MISS-12｜记忆侧死导出（接口在 ≠ 链路通）**

**改法**：文档按两类分别表述，并明确「不要把 active_message 改成 custom 条目」。

### 4.3 audio effects：保留静默但补统一出口（复核结论）

`src/services/audio/effects/*.ts` 共 **32 处 `catch {}`**。`context.ts:14-20` 的论证**只覆盖一部分**：

- **覆盖成立**：每个 `play` 都是 `const ctx = await getCtx(); if (!ctx) return`，ctx 在 try **之外**取；构造失败 `:45` 有 warn；autoplay 挂起 `:28-31` 有 warn（一次）。
- **缺口 1（`:38`）**：新建 AudioContext 分支里 `resume()` 失败被吞，**且该分支没有 `suspendedReported` 检查**，`:42` 还把标志重置为 false → **只播一次音效的会话，「被自动播放策略拦截、用户听不到」永远没有日志**。
- **缺口 2（32 处本身）**：try 体内抛出的不都是 ctx 问题 —— `osc.start()` 二次调用抛 `InvalidStateError`、`exponentialRampToValueAtTime` 非法值抛 `RangeError` 是**程序 bug**，根因**不在** `getCtx()` 的留痕范围里。

**改法（保留静默语义 + 补统一留痕点）**：`context.ts` 新增一次性出口

```ts
let buildFailureReported = false
export function reportEffectFailure(error: unknown): void {
  if (buildFailureReported) return
  buildFailureReported = true
  log.warn("音效节点构建失败，该音效已跳过（后续同类失败不再重复报告）", formatError(error))
```

## 9. 验证口径与未验证边界

### 9.1 口径

- 跨模块改动 → **完整 Live Test** + 严格 Contract + **≥3 次 trial**（`pnpm run test:release`）；跳过/超时不得报通过。
- 非 unit 场景需实际或 fake Provider 响应；`entry: production` 须经 `sendMessage()`。
- **Live Test 不能并行跑**（占 1420 端口）；**macOS 锁屏**会让 WebView 约 6 秒后整体停摆，跑前必须解锁并保持点亮。
- 源码或行为契约变化必须按 SKILL 重新 analyze → generate，**不能只改 `sourceHash` 过门禁**。
- 类型/编译不能代替运行验证；Rust 单测内联在 `src-tauri/src/**`，`pnpm run test:rust` 执行；Windows 分支须看 Windows CI（本机 macOS check 不证明 Windows 分支）。

### 9.2 本方案的未验证边界（必须在实施时如实登记）

- 本方案**未运行任何测试/场景/应用**，全部结论来自源码 + `node_modules` 内上游 dist 实现的静态阅读。
- Windows 运行时行为（`bash_policy` 层 2 的 `is_system_path`、`kill_child` 的 taskkill、`paths.rs` 短名规范化）本机未编译验证。
- `pendingQueues` 播种改用 `lane.watch()` 会带来一次转录扫描 → **大会话开槽变慢的幅度需实测**。
- `harness-branch-tip-bypass`（旁路写入是否真被从 tip 链挤掉）机制成立但**未触发验证**。
- `deferred` 的 Provider 可达性：本仓 provider 不产出 deferred handle → HN-08 的挂死路径当前生产不可达（但状态机漏洞仍需修）。
- Plan 的 production 场景（PLAN-17）依赖新增的 `plan-confirm-channel.ts` 测试替身 —— 方案可行性已论证，**未实跑**。
- UI 层入口（PlanConfirm 面板、计划待处置条、ChatPanel 排队面板、「停止」按钮文案、设置页新增控件）**Live Test 宿主不渲染 UI** → 只有协议级证据，需人工查看。
- **恢复时 MCP 借用失败的显式提示**（TOOL-13 / FIX-61）：Live Test 恒 pet 且宿主不渲染 UI → **无法验证**；可做的 pet 侧代理 = `tools.skill.enabled=true` + 恢复后断言 Skill 目录/提示块可用（证明能力准备确实在恢复路径执行）。
- **RUNTIME_DATA 在「assistant 带 toolCall」回合的变量写入**（FIX-10）：原审查自认未验证，且 388 行 diff 里没有相关场景断言 → **实施前必须先补这条场景**；若成立即变量静默丢失，属「变量丢失」级别。
- **`memory-l0-address-integrity` 的用例范围**（§2.2b ④）：是否需覆盖停止/继续/丢弃路径，取决于「合成分结果长度是否超过 L0 阈值」——一条命令可核实，未核实前该场景按「长错误消息」设计。

## 10. 已评估、不实施

| 项 | 理由 |
|---|---|
| 「拦实际打开的文件」级凭据保护（OS 沙箱） | 属 seatbelt/AppContainer 职责；与 `tool-system.md:68` 的既有口径一致，明确写为非目标。间接形式（`python -c "open(...)"`）不在覆盖内 |
| 许可额度 TTL / 看门狗 | 会放开在飞的独占效果，与 `tool_permit.rs:13-14` 的设计冲突。改为从源头消除无界 I/O（TOOL-06a） |
| 许可额度的窗口销毁残留（item 2/4） | 维持归档决策「不修」，但**更正其事实前提**并把隐含不变量写进文档 |
| 并发 lane 上限 | 补上回收器后空闲槽不再累积；再加容量/LRU 等于引入第二套淘汰策略 |
| 启动孤儿扫描 | 启动即扫需为每个会话 `open()` 槽，与「低内存」冲突；未打开会话的中断操作不会自动跑起来，无正确性风险 |
| 退出钩子停止在飞运行 | 退出走托盘 `app.exit`，进程被杀后由中断恢复兜底；补钩子要与 `app.exit` 竞态，还会取消用户可能想「继续」的运行 |
| 心跳 | 三层超时兜底已够；唯一没回合定时器的 `compact()` 由摘要请求上限兜住，写进文档即可 |
| 在错误/中断路径补 `deskpetEntryId` | 上游错误分支只用 `error.message`；合成中断结果不经过任何宿主 hook；checkpoint 路径需要工具显式 `options.checkpoint=true` 而本仓 `ToolContext.onUpdate` 无该参数 → 不可达 |
| 依赖树只读的 CI 检查 | 本仓 CI 只跑双平台 `test:types`/`test:rust`；加一条 grep `node_modules` 的检查价值低且易漏 → 以文档约束为准 |
| L3 依赖闭包门禁 | 既有决策（闭包差是 barrel 噪声，收益不抵 hash 维护成本） |
| `before_run` hook 不补 | 冻结已由宿主 preflight（`runtime.ts:656-831`）等价完成，hook 注入点无额外价值；**登记为已知偏离**（FIX-11） |
| `before_run_end` 不实现 | 基线方案本身标注为可选／"—"（FIX-12） |
| `toProviderMessages` / `entryProjectors` / `resources.skills` 保持默认 | 上游默认 `convertToLlm` 已把 `custom`→user 且 `deskpetEventId` 不泄漏；不注册 projector 是**有意**的（与 MISS-14 的边界同源）（FIX-13） |
| 七阶段证据链保持 4 阶段 | `request_started` 可由 `request_prepared` 覆盖、`settled` 由 `responded` 覆盖 → 不补（FIX-14，写进 `runtime-contract.md`） |
| Harness 的 `totals` 不消费 | 逐请求 `row.usage` 已满足统计需求（FIX-15，登记为已知不消费） |
| `invocation.getMemo`/`setMemo` 持久恢复位不实现 | `replay: "never"` 已保证不重放，恢复位无消费者（FIX-16） |
