## 1. 决策：现在建设会话压缩，长期记忆整理留到下一阶段

建议下一次代码工作先完成旧 P4 的最小闭环，不等待 P6 的 SQLite/MemoryKernel 重构。两者共享稳定事件 ID、来源、版本和模型网关，但解决的问题不同：

| 工作 | 解决的问题 | 输入与输出 | 是否依赖新的长期记忆后端 |
|---|---|---|---|
| 上下文选择 | 本次请求应看哪些内容 | transcript/blocks → 请求视图 | 否 |
| 会话压缩 compaction | 旧对话过长，如何继续聊天而不失去必要语义 | 连续完整 rounds → 摘要 + 覆盖边界 + 原文尾部 | 否 |
| 长期记忆提取 capture | 哪些用户信息值得跨会话记住 | 合格来源事件 → 候选事实 | 是，需写入与来源门禁 |
| 长期记忆整理 consolidation | 如何合并、纠正、降权、过期与遗忘 | 长期条目/候选 → 版本化事实 | 是 |

压缩摘要不自动晋升为长期记忆，不能反过来依赖“先把所有事实写进记忆库”才能安全压缩。原始会话仍保留，未来 MemoryKernel 可按事件覆盖范围补提取。

## 2. 哪家的方案更适合

结论是组合已有机制：**ClaudeCode 的显式边界检查点 + OpenClaw 的近期 token 尾部与提交校验 + Hermes 的有效输入预算与轻量预清理。**

这不是三套压缩器并存，而是一套 Desk-Pet 压缩协议。摘要质量还受模型、模板、数据和预算影响；本次没有运行同一数据集做 A/B，不宣称某一家“算法准确率最高”。

| 参考 | 主要优势 | 对 Desk-Pet 的取舍 |
|---|---|---|
| ClaudeCode | 明确 cutoff、摘要与尾部独立、重启恢复验证、无效进度 ID 回退 | 采用显式 checkpoint，不照搬 UUID parent 图重链接 |
| OpenClaw | 完整切点、按 token 保留尾部、摘要验证与取消、提交后重建上下文 | 采用提交协议和 tail 预算，不复制 16K/20K 默认值 |
| Hermes | `context_length - max_tokens` 有效窗口、先裁旧工具结果、selection 不改持久化历史 | 采用预算/选择接口，不引入整个插件系统或压缩后换 sessionId |

### 2.1 CC 的“标记位”到底是什么

本地 ClaudeCode 中它是 `compact_boundary` 系统消息，**不是每条旧消息上的 `compressed=true`**。创建时携带 trigger、preTokens 和可选摘要计数等元数据。压缩结果由三个独立部分组成：

```text
boundaryMarker       从哪里开始构造新的模型上下文
summaryMessages      被覆盖历史的语义
messagesToKeep       仍需保留的近期原文
```

每次请求寻找最后一个 boundary，只取边界之后的有效上下文；发送 API 时边界元数据本身被过滤。真正负责语义压缩的是 summary，而不是 marker。

保留旧尾部时还有 `preservedSegment: { headUuid, anchorUuid, tailUuid }`。恢复逻辑检查链完整性并重新连接摘要和原文尾部；尾部必须先落盘，再持久化边界。链校验失败时不激进裁剪历史。

CC 另有 session-memory compact：利用持续维护的会话摘要和 `lastSummarizedMessageId`，减少临界时刻重新摘要的成本。已记录的 ID 在当前消息中找不到时返回空结果，由调用方回退传统 compact；恢复会话根本没有提供 ID 时，则先把最后消息视作摘要边界，再按近期原文最低保留要求扩展尾部，并非立即回退。Desk-Pet 尚无成熟的持续摘要前置条件，第一版不采用这一优化。

### 2.2 OpenClaw 的 20K 不能直接当压缩余量

本地 OpenClaw agent-core 中，`reserveTokens` 参与压缩触发与摘要输出预算；`keepRecentTokens` 决定压缩后保留的近期原文尾部。默认分别可见 16,384 与 20,000，宿主配置还可能覆盖。

`keepRecentTokens=20_000` 的意思是从后往前找一个约 20K token 的近期保留区，不是给摘要正文固定分配 20K，也不是回复输出上限。[OpenClaw 压缩说明](../../../../openclaw/docs/concepts/compaction.md)

Desk-Pet 应把 `outputReserve / compactionHeadroom / keepRecentTokens / summaryMaxTokens` 分开建模。用户设置 16K 时硬套这些大窗口值不可行；所有值来自同一预算快照并校验总和。

## 3. Desk-Pet 当前需要先修正什么

| 事实 | 风险 | 先行处理 |
|---|---|---|
| 轮末 `messages.length * 100 + recentMessages.length * 150` 估算 | 大型工具输出可能早已超限；触发太晚 | 请求前按实际序列化内容估算，回合后用 usage 校准 |
| Kernel 预留 context/4，网关输出上限最多 4096 | 大窗口下保留量相差很大 | 共用网关产出的预算快照 |
| 摘要没有覆盖事件范围 | 无法判断哪些原文可从模型视图移除 | 增加连续覆盖区、keepFrom 和上下文代际 |
| `apiRoundId` 仅有可选字段，无实际赋值；`persistPiMessage()` 仅 pushMessage 到当前 UI | 重启后没有足够工具原文与 round 身份证明完整覆盖 | 首次 checkpoint 前补稳定 append sequence、round ID 和工具事件原子持久化；UI 从其投影 |
| 事件读取按 createdAt + eventId 排序 | 同毫秒事件不一定保持真实提交顺序 | 新记录保存会话内单调序号；旧记录按确定的文件顺序兼容，不凭时间戳推断工具因果 |
| `writeCompactionSummaryToSession()` 返回 boolean，调用方不检查 | CAS 拒绝过期结果后仍可能报告成功 | 返回明确 committed/stale/failed 等结果 |
| `compactIncremental()` catch 返回 fallbackSummary，未经过相同提交路径 | fallback 被上层当作完成，实际未持久化 | 未提交结果不能叫成功；fallback 必须单独标识并通过同一校验/提交 |
| `/compact` 未传固定 target，异步后使用当前 MemoryService | 手动摘要期间切会话可能写错目标 | 启动时捕获 session/version/generation，后续禁止再取当前活动会话 |
| `compactFull()` 只取 sessionContent 前 8000 字符 | 不能代表完整会话，近期重要信息可能缺失 | 第一版不以此前缀方式作为全量摘要路径 |
| `compactMessages()` 保留 40% 消息单元 | 按条数不等于按 token；且当前无生产调用点 | 不把死代码描述为现行算法，不直接接入生产 |
| Kernel 按单消息预算选取历史 | 摘要压缩之外仍可能形成不完整工具回合 | 选择与压缩共用 round builder |

源码：[compactor](../../../src/services/engine/compactor.ts)、会话摘要写入（`session-files.ts`，已随兼容层清理删除）、[/compact](../../../src/services/engine/slash/commands/compact.ts)、[ContextKernel](../../../src/services/context/kernel.ts)、[模型网关](../../../src/services/engine/pi/model-gateway.ts)。

这些是代码与调用链审查结论，不是本轮运行复现结果。CAS 已经保护了目标会话的过期写入，缺口是上层对提交结果的解释及完整压缩协议。

## 4. 最小协议

### 4.1 追加 CompactionCheckpoint，不批量修改旧消息

以下为目标结构，尚未加到生产类型：

```ts
interface CompactionCheckpoint {
  compactionId: string
  sessionId: string
  runGeneration: number
  contextEpoch: number
  sourceTranscriptRevision: number
  expectedSessionVersion: number
  previousCompactionId?: string
  coveredEventIds: string[]
  keepFromEventId: string | null
  summaryVersion: number
  summaryKind: "companion" | "assistant"
  summary: StructuredSummary
  inputHash: string
  outputHash: string
  trigger: "manual" | "preflight" | "post_turn"
  createdAt: number
}

type CompactionOutcome =
  | { status: "committed"; checkpoint: CompactionCheckpoint }
  | { status: "skipped"; reason: string }
  | { status: "stale"; reason: string }
  | { status: "cancelled" }
  | { status: "failed"; code: string; message: string }
```

第一版以明确事件 ID 表达覆盖范围，校验它属于连续的已完成 rounds。范围较大时可改为起止事件 ID + range hash，但不能丢掉可验证覆盖关系。

这是首次提交的硬前提：先定义会话内单调 append sequence、实际赋值的 apiRoundId、工具调用/结果持久化，再构建完整 round。现有工具 trace/Plan checkpoint 不能替代工具原文事件。旧会话只有 user/assistant 文本时按可证明的文本单元兼容，不能补造缺失工具结果；无法证明的历史不生成跨越该处的 cutoff。新增字段需经现有串行写路径分配，幂等重放保持同一 ID/序号。

`compaction` SessionEvent 是已有事件种类；采用现有会话序列化和原子写入格式，摘要正文与 cutoff 同一次提交。不要另建一个 localStorage 标记，也不要直接在 UI 消息对象上加状态后认为可恢复。

摘要内存缓存和可读“摘要”区都从已提交 checkpoint 投影。完整正文不删除、不覆盖。旧会话没有 checkpoint 时完整读取，旧摘要可作为无覆盖证明的参考，不能据此跳过原文。

### 4.2 请求视图

```text
固定应用/Card/模式前缀
  + 最新合法 committed checkpoint 的摘要
  + keepFromEventId 起的原文完整 rounds（含提交后新增消息）
  + 当前输入
  + 未完成工具、Plan、队列与权限状态的独立投影
```

摘要不能恢复工具执行权限。未决确认从 Permission/Session Store 恢复为过期状态，不能从摘要里的“用户允许过”重建 grant。

多次压缩时，输入是上次摘要加新增待覆盖 rounds；记录 previousCompactionId 和完整来源。不得把旧摘要再次当成用户原话。恢复验证 source IDs、hash、cut point；损坏时回退上一合法 checkpoint 或原始历史，再做预算预检，不能直接发送超限原文。

### 4.3 原子提交时序

1. 从固定 session 捕获 transcript revision、文件版本、run generation 和可压缩范围，确保工具事件已 flush。
2. 释放文件锁，生成摘要。模型请求不得长期持有会话写锁，也不能阻塞新的用户输入持久化。
3. 校验 schema、来源、保留项、摘要 token、完整切点和压缩后预算。
4. 在会话串行提交路径里重验版本、代际和取消状态；摘要与 checkpoint 原子写入。检查和写入不得留下允许旧 generation 越过的竞态。
5. 写成功后才更新内存请求视图、contextEpoch 和完成提示。旧 PromptSnapshot 永不改写。
6. 版本冲突返回 stale，不原地覆盖，不无限重试；下一安全边界重新评估。

第一版可继续使用整文件 CAS，保守丢弃竞争结果。若快照/指标事件频繁导致摘要一直 stale，再把 transcriptRevision 与纯遥测 revision 分开；不能为了提高成功率直接取消 CAS。

## 5. 预算与算法

### 5.1 每次 Provider 请求前校验

使用总方案中的 `hardInputLimit` 与 `normalInputTarget`。估算必须包括 system、工具 schema、消息、工具参数/结果和必要协议开销。记录使用了 estimate 还是 actual，以及估算误差。

实际 usage 从 settled assistant message 获取；`onResponse` 只有 HTTP 元数据时不能凭空提供 token 统计。使用新 checkpoint 后，旧 usage 不能直接用于判断新视图，否则会反复触发压缩；记录 usage 对应的 contextEpoch。

### 5.2 三步处理

**L0：确定性清理。** 去掉 UI-only、重复运行块和可恢复的陈旧工具原文，保留状态、必要错误、出处/hash 和受限引用。复用现有 Bash spill，不为压缩另造一套文件保存。不能把仍需要的工具结果改成孤立 role=tool 摘要。

**L1：摘要连续的旧完整 rounds。** 先按 token 选尾部，再将切点移到安全边界。尾部至少包含最近完整用户意图和回应；当前输入、未完成工具批次及有未决动作的回合不得摘要掉。摘要输出有独立小预算。

**L2：有记录的请求降级。** L1 无法完成且仍超限时，第一版优先返回可解释的上下文不足结果。若后续支持只保留近期完整 rounds，必须明确记录被排除范围/缺失语义，不能伪造“压缩成功”。持久化全文始终保留。

round builder 以稳定事件和工具调用 ID 建立完整回合。现有 `groupMessageUnits()` 仅将 call/result 放在同一组，不足以证明完整 API round 的上下文连续性。缺失 result、多个工具、失败工具、steer/follow-up 都需明确定义切点。

### 5.3 陪伴摘要模板

当前摘要的 keyTech/files/tasks 偏编码场景。改为公共骨架 + 模式字段：

| 公共骨架 | 陪伴扩展 | 助手扩展 |
|---|---|---|
| 用户当前意图、已确认事实、未决问题、明确纠正、必要原文引用、覆盖来源 | 称呼与语气偏好、最近话题、共同经历、用户明确希望后续关注的事项；短期情绪带时间 | 任务目标、已完成/未完成、文件/标识符、工具结果、验证结论、下一步 |

摘要不编造事实，不将助手猜测写成用户偏好，不固化一次情绪。Card 变量继续从 VariablePool 读取，不从摘要重建亲密度、好感度等状态。权限、安全和 Plan 事实从专用 Store 投影，不让模型摘要改变它们。

摘要质量评估重点是恢复后的下一轮能否正确延续，而不是只看 JSON 格式或压缩率。对明确纠正、未回答问题和重要否定句设置必保断言。

## 6. Pi 接入与分批实施

### P4-A：事件基础、提交可靠性和会话绑定

- 统一 CompactionOutcome；严格处理 writer 的 false、取消、解析失败和 fallback。
- `/compact`、自动压缩都捕获固定目标与版本，结果只写原 session。
- 在提交第一个 checkpoint 前，补稳定 append sequence/apiRoundId 的实际赋值、工具 call/result 持久化及 flush，建立完整 round builder；不依赖活动 UI 缓存。
- 增加 checkpoint 协议及旧会话兼容，提交与可读摘要原子化。
- 暂不启用更激进的自动阈值，先验证恢复投影和成功语义。

### P4-B：请求视图与初次预检

- 复用 P4-A 已验证的 round builder 统一请求选择和摘要切点；旧全文保留。
- 共用网关输出预算，初次请求前完成必要 L0/L1。
- Kernel 只应用 committed checkpoint；静态协议和当前输入不再任意字符截断。
- 用 fake provider 验证长历史、长工具结果和模式摘要。

### P4-C：工具循环中的预算与观测

- 每次请求都经过安全预算检查，不仅 sendMessage 首次构建时检查。
- `transformContext` 按 Pi 契约不抛异常，做请求选择与安全回退；无法构造合法请求时由 Adapter 的发送前门禁停止。
- `prepareNextTurnWithContext` 可在工具批次完成、持久化 flush 后接入已提交视图；不要在 subscribe 的未等待回调里修改事实。
- 预算、取消或需要整理导致停顿时，steer/follow-up 保留持久化队列身份；不能因 shouldStopAfterTurn 先于队列消费而误标 done。
- 记录 actual usage、压缩前后 token、耗时、失败分类与 epoch，防止压缩风暴。

P4-A/B 不要求先建 MemoryKernel 或重写整个状态系统；P4-C 与总方案 ContextKernel 阶段收口。完整工具并行仍等待已有 P5 门禁，不能顺手开放。

## 7. 必需验证

代码实施前按 live/SKILL.md 分析受影响 Contract，预计涉及 memory、agent-runtime、context 构建以及工具结果；具体模块名以实际 Contract 注册表为准。

| 场景 | 必须断言 |
|---|---|
| 截止点投影 | A…N 被摘要后只发送摘要 + N+1 后原文；磁盘全文不变 |
| 事件顺序与重启 | 同毫秒多事件、工具并发完成、幂等重放都保持持久化顺序；重启后的 round 和工具内容可重建；非活动会话也写入其正确目标 |
| 工具对/完整回合 | 切点不能落在 call/result 或同批多工具之间；缺失结果保守保留 |
| 取消与 CAS | 模型返回前取消、加入新消息或换代后，旧结果不提交、不报成功 |
| 手动切会话 | A 中 /compact，切 B 后结果绝不写 B |
| 摘要失败 | 超时、空内容、非法 schema、遗漏必保项均不写 cutoff |
| writer 拒绝 | false/stale 不显示完成，fallback 不冒充 committed |
| 崩溃顺序 | 提交前失败沿用旧视图；提交后重启 projection hash 一致 |
| 连续压缩 | 覆盖进度单调、旧摘要不重复注入、usage epoch 正确 |
| 预算 | 16K/32K/128K，长中文、工具 schema、巨型结果；当前输入超额不静默截断 |
| 陪伴连续性 | 昵称/纠正/否定/待回答问题保留；情绪不变永久事实；Card 状态不由摘要覆盖 |
| 权限与来源 | 摘要不能恢复授权，active/skill/tool/recovery 不晋升用户事实 |
| 工具轮接线 | 非首次 LLM 请求也通过预算门禁；在飞队列不会丢失或提前 accepted |

先以 fake provider 运行真实 Pi/IPC 的确定性场景，再以真实 provider 做多 trial 内容延续评测。运行类型/编译检查和受影响 Live Test；跨模块后运行完整测试，发布再走严格三次 trial。没有刷新 sourceHash 的旧报告不作为通过证据。

本轮只检查文档链接、一致性和 diff；上述测试是未来实施门禁，不是本轮已通过项。

## 8. 后续与长期记忆的衔接

MemoryKernel 之后可消费 committed checkpoint 的 source event IDs，异步补提取候选，或者在即将压缩前调度有时限的 capture。capture 失败不阻止必要压缩，因为原文仍在；它不能自动获得权限或修改 Card。

持续摘要、后台预压缩可作为降低前台延迟的下一步优化，但必须保留覆盖进度、取消、CAS 和成功语义。不要在基础闭环尚未稳定时复制 CC 的全部 session-memory 策略。
