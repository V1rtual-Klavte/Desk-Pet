## 为什么推翻单一 Live 层

2026-07-24 的设计**刻意删除了 vitest 快层**（8 个 `*.test.ts` + `helpers/`），约束原文是「旧测试全部移除，不保留 mock 基础设施」，核心理念是「真 LLM 对话：不用 mock」。

此后三个月，确定性能力被一点点加回 Live Test **内部**：`entry: "unit"`（不跑模型）、`fake-provider.ts`（fauxProvider）、`confirmPolicy` / `planPolicy` 确定性应答通道。**快层已经在被重新发明，只是被关在必须先启动 Tauri WebView 的宿主的笼子里。**

代价已经量化。**口径：113 个场景文件 / 159 个场景 / 2028 处手写 `throw`**（计数方法与复核步骤见下节，不要再用别的数字）：

- CI（`.github/workflows/ci.yml`）只跑 `test:types` + `test:rust`；**159 个场景零门禁**。
- 159 个场景里 **107 个声明 `entry` 为 `unit`(77) / `runtime`(12) / 未声明(18)**，是快层候选；只有 **47 个 `production`**（另有 1 个与 runtime 混用）真的需要 L4。**候选 ≠ 可搬**——最终归属由 W3 的适配层逐个试跑裁定，不由声明猜。
- **2028 处手写 `throw new Error`**；`AssertCheck` 只是 `{type, run}`，没有断言库、没有 diff、没有结构化 expected/actual。
- 报告 3–9MB。
- `~` 下的 `.deskpet-live-test-*` 临时根已于 2026-09-29 清理（11 个 / 552MB，移入废纸篓；未走 `rm`）。

### 口径与复核

场景是**原子单位**，文件只是分组容器——一个 `.scene.ts` 可以导出多个 `SceneDef`（`变量池核心` 9 个、`计划评估与执行` 8 个、`安全等级边界` 7 个）。`test/e2e/e2e-main.ts` 的 `collectScenes()` 取模块的**全部导出**再按 `meta.caseId` 去重，所以：

- 说「113 个测试」是错的，那是文件数；场景数是 **159**。
- 说「124 个 caseId」是错的，那是把工厂形参、类型字段和字面量混在一起的字符串计数。
- 两个文件（`memory/主动消息来源`、`memory/工具成对观测`）各只有 1 行，是 `export { X as default } from "./P0快照.scene"` 的纯转发别名，**贡献 0 个场景**，属死重量，搬家时删除。

复核方法（可重复执行，不依赖本机状态）：

1. 按 Unicode 属性类匹配导出（**`\w` 不匹配中文**，用 `[\p{L}\p{N}_$]`）：`^export\s+const\s+<name>\s*(?::\s*SceneDef\s*)?=\s*(\{|<name>\s*\()`，每条计 1；`export default {` 另计 1，`export default <已计入的 const 名>` 不重复计。
2. 抽样手验：`变量池核心` 应为 9、`基础记忆契约` 应为 6。
3. **不要用 `turns: [` 交叉验证**：工厂生成的 9 个场景共用工厂体里的 **1 个** `turns:` 字面量，该数天然少算。

这是**分层缺失**，不是 E2E 写得烂。本契约的目标是把已经开始的纠正做完。

## 外部参照

pi / hermes-agent / openclaw 三家（2026-09-29 侦察）收敛到同一形状：**快层（vitest/pytest）→ 中层（fake model 走真实 agent loop）→ 慢层（真 Provider，opt-in）**。三家共同遵守的纪律是「fake model 只替换 Provider，其余走真实链路」——Desk-Pet 已经遵守，缺的是把三层拆开。

三家**都没有**覆盖率阈值，本契约也不引入。

## 目标分层

| 层 | 命令 | 运行环境 | 覆盖 | CI |
|---|---|---|---|---|
| L0 静态 | `test:types` | — | vue-tsc + cargo check | 现状保留 |
| L1 Rust 单测 | `test:rust` | cargo | `src-tauri/src/**` 内联单测 | 现状保留 |
| L2 单元 | `test:unit` | vitest · node | 纯逻辑：变量池/解析/注册表/边界 | 新增 |
| L3 集成 | `test:integration` | vitest · node + 临时数据根 + fake Provider | Pi runtime 走真 loop、真 JSONL 落盘 | 新增 |
| L4 端到端 | `test:e2e` | Tauri WebView · 真 Rust IPC | 需真 Rust 边界的场景 | 本地/发布 |
| L5 发布门禁 | `test:release` | — | `test:types` + `test:rust` + `test:unit` + `test:integration` + 严格 Contract 的 `test:e2e` | 现状保留并扩展 |

`pnpm test` 指向 L2 + L3（每 PR 必须过的那一组），不再指向 L4。可并行、无端口占用，Live Test 不能并行跑的约束随之只作用于 L4。

## 观测性：分层不得损失单一视角

分层最大的风险不是慢，是**观测性退化**：三条命令、三种输出格式、三个报告位置，用户失去「我现在到底 OK 不 OK」的单一信号。这是硬需求，不是打磨项。

- `pnpm test` **仍然是一条命令跑完全部三层**，产出**一份统一报告**。分层是内部结构，不是用户要记的三个入口。
- 统一报告沿用现有结构（`desk-pet-live/v2` → `desk-pet-test/v1`），**每个案例带 `layer` 字段**，失败时能一眼看出是哪一层的哪一类问题。
- 报告落在 `test/reports/`，**单份 JSON** 加一份自包含 HTML，不做三份。
- 终端输出先给全局一行结论，再按层展开；`pass@k` / `pass^k` 同时给**全局**与**分层**两个聚合。
- 实现方式：vitest 以 `--reporter=json --outputFile=` 产出机器可读结果，由现有 reporter 合并进统一报告，不新写一套报告格式。

### 证据强度必须分层标注

这是当前报告的一个真实缺陷：`entry: "production"` 的真实 Provider 场景与确定性场景**混在同一个 `passRate` 里**。三类证据的强度根本不同：

| 类别 | 证据强度 | 红了意味着什么 |
|---|---|---|
| L2 / L3（无模型或 fake Provider，确定性） | 强：同输入同结果 | 产品回归或测试错误，**必须定位到其中一种** |
| L4 + fake Provider | 强：确定性 + 真 Rust IPC | 同上 |
| L4 + 真实 Provider | 弱：**观测性**证据 | 可能是模型抖动，也可能真是回归；`pass^k < 1` 本身不构成回归结论 |

报告必须分开统计，不得混算。已经登记的 `variable-affection-praise` 真实 Provider 抖动项即属第三类。

## 宿主分层：IPC 适配层

`test/host/node-ipc.ts` 通过 vitest / vite 的 alias 接替 `@tauri-apps/api/{core,path,event}`，把命令分成两组：

**可等价复现**（只实现机制，把根指向 `mkdtemp` 临时数据根）：

```
file_read file_write file_append file_remove file_rename file_exists
file_list file_info file_read_binary file_write_atomic dir_create
file_canonical_path
get_runtime_paths resolve_runtime_path profile_asset_base
read_runtime_config write_runtime_config
read_session_ui_state write_session_ui_state
skill_catalog_fingerprint skill_delete
list_profiles profile_file_read profile_file_write
personality_file_read personality_file_write personality_file_list
init_memory_files log_messages report_frontend_error set_log_config
```

**Node 不可复现**（调用即抛 `UnsupportedInNodeError`，消息里带命令名）：

| 命令 | 为什么不可搬 |
|---|---|
| `bash_exec` / `bash_cancel` | Rust 层 1 硬基线 + 系统路径保护 + 凭据拦截，调用方不可关闭 |
| `mcp_spawn` / `mcp_send` / `mcp_kill` | stdio 子进程 |
| `tool_permit_acquire/release/cancel/attach/snapshot/set_max_shared_readers` | Rust 侧许可内核（`src-tauri/src/commands/tool_permit.rs`） |
| `clipboard_read` / `clipboard_write` | 桌面能力 |
| `open_windows_sim` / `close_windows_sim` / `pause_monitor` / `resume_monitor` | 窗口与显示器 |
| `app_open` / `export_profile_zip` / `restore_default_resources` | 桌面副作用 |

适配层**只实现机制，不实现策略**：不做路径裁决、不做 Bash 基线、不做许可配额。它遇到未登记命令抛错而**不返回 null**，因此不会有场景在假适配下「假装通过」。

### 适配层即自动分层器

一个场景能不能进 L3，由它跑起来自己回答：跑通了就搬，撞上 `UnsupportedInNodeError` 就留在 L4，并把原因登记进契约。这取代了靠人猜的搬迁判断。

## 跨层一致性验证

适配层是「第二个 Tauri 实现」，光有它不够。用 pi 的一致性套件思路做交叉验证：**同一份案例在 L3（Node 适配层）与 L4（真 Rust IPC）各跑一遍，结论必须一致**，不一致即适配层失真。

Desk-Pet 已经有这个资产：[会话仓库一致性.test.ts](../../../test/integration/harness-storage/会话仓库一致性.test.ts)（W2 从 L4 场景迁到 L3）已在运行 pi 官方 `@earendil-works/pi-agent-core/harness/session/testing` 的 conformance cases。目标是把这类案例抽到 `test/conformance/`，由两层分别驱动。

覆盖面先限 `JsonlSessionRepo` 的存储语义；扩展到路径解析与配置读写需先证明两层的输入域一致。

## 契约门禁跨层

- `coverage[].scenarios[]` **继续填 caseId**，caseId 空间不变。
- L2 / L3 的 caseId 锚在 vitest 测试全名**末尾**的 `[caseId]` 标记上（如 `it("拒绝未注册变量 [variable-pool-unregistered]", …)`），由 `test/host/caseid-reporter.ts` 在测试结束时收集；契约新增 `layer` 声明。
- **标记只给承担覆盖点的测试用。** 基础设施自测（守卫、收集器、渲染器、规则扫描器自身）**一律不带标记** —— 它们不构成覆盖。
- **孤儿 caseId 与重复 caseId 都是错误**，方向相反但都要报：
  - coverage point 的 `scenarios[]` 里写了、却没有任何一层的测试带着它 → `MISSING`（覆盖点落空）
  - 某层收集到 `[caseId]`、却不在任何 coverage point 里 → `ORPHAN`（制造覆盖假象）
  - 同一个 caseId 在两层里都出现 → `CROSS-LAYER`（会双重计数）
- `test:unit` / `test:integration` 各校验自己那层；`test:release` 校验全部。
- **诚实边界**：分层**不会**缩小「改一个共享文件判多个契约 STALE」的爆炸半径。真正的改善是**检查变便宜**——从「开桌面等几分钟」变成「两秒重跑」。不要把它当作对 hash 连锁失效的修复。

## DSL 的存废

`SceneDef` / `TurnDef` / `AssertCheck` DSL **只保留在 L4**，理由：只有 L4 需要在**非 Node 宿主**里声明式地枚举并执行场景。

L2 / L3 一律朴素 vitest（`describe` / `it` / `expect`），因为 vitest 的测试名、过滤、并行、报告与断言 diff 已经把 DSL 存在的理由替代掉了。`entry: "unit"` 枚举值随之删除——它是「需要一层快测试」的化石，分层之后不再成立。

`entry: "production" | "runtime"` 保留在 L4，用于区分走 `sendMessage()` 的真实产品链路与直接驱动 Pi runtime。

## 观测面：宿主窗口必须给人看

W1 之前，L4 宿主窗口对人是**不可观测**的，这不是体验问题而是功能缺失。以下为当时核对的事实，保留作问题动机：

- `live-test-main.ts` **一次都没有触碰 DOM** —— 全测试目录里唯一一处 `document.createElement` 属于无关场景。结果只走 `console.log` / `console.error`（WebView 控制台，要开 DevTools 才看得到）与 `live_test_complete` IPC 两条出口。
- `live-test.html`（W0 改名前的入口，见下表 `live-test.html` → `test-e2e.html`）里的 `<pre id="status">Live Test starting…</pre>` **从加载到进程结束永不更新**。使用者看到的就是一个白窗口。
- 结果**确实是保存的**：`live_test_complete` 交给 Rust 写入数据根的结果文件，Node 侧再复制到仓库外的报告目录，保留最近 20 份。但**没有入口、没有索引、格式是数 MB 的终端文本**，等于只有能读文件的代理和脚本能用。
- **保留策略会静默销毁证据**：报告目录在仓库外且只留 20 份，归档文档一旦按路径引用某份报告，淘汰后该引用即悬空。已实际发生过——`docs/history/` 中 4 处报告路径引用，3 处已在本次整理前被淘汰。

后果：人只能问代理「过了吗」，无法自己判断，也无法在失败时自己看是哪一条。

### 目标（W1 已实现）

1. **窗口内实时进度（已实现）**：每个 case 一行（`pending` / `running` / `pass` / `fail` / `expected failure`），顶部汇总条（已跑 / 通过 / 失败 / 剩余 / 耗时），失败立即展开断言差异与失败窗口的事件序列。
2. **报告新增 `html` 格式（已实现）**：**自包含单文件**（内联 CSS/JS、零运行时依赖），落在报告目录，双击即看。这是选型时否决 `@vitest-evals/report-ui`（会拖进 React 19 + Vite 7）之后应有的替代，不是额外功能。
3. **路径可发现（已实现）**：运行结束在窗口里显示报告的**绝对路径**并提供打开目录的入口；终端同样打印。不允许「结果存在但没人知道在哪」。
4. **快层同样受益（部分实现）**：L2/L3 沿用 vitest 原生输出；聚合入口产出的统一报告同样出 HTML —— 后半段尚未接，`pnpm test` 目前顺序跑两层，不产出合并报告。
5. 遵守项目的轻量化底线：不引入报告 UI 依赖，页面本身不成为新的常驻负担（报告渲染保持零依赖纯函数）。

**未经过一次真实 L4 运行验证**：以上落地只有代码与快层证据，L4 宿主窗口的实时进度、失败行展开与 HTML 报告尚未在真实运行中看过一次。

### 报告落位与保留策略（已实现）

报告目录已迁到 `test/reports/`，**并在 `.gitignore` 中排除**（`AGENTS.md` 规定 `.gitignore` 变更需单独授权，本契约将其列为 W1 的一项显式授权项）。迁入仓库内的收益是**可发现性**——报告与它描述的测试树在一起，不再是一个没人知道的家目录路径。

保留策略同时改为**按体积**而非只按份数：单份报告可达 11 MB，只按 20 份计数不封顶磁盘占用；启动脚本按 mtime 从新到旧累加，超过 200 MB 淘汰更旧的，最新一份始终保留。**不再让归档文档依赖报告文件路径**——引用一律写可核对标识（runId / commit / dataset 版本 / cases 与 trials 计数），不写文件名。

## Trace 与跟踪：现状与分层要求

「失败时能不能顺着链路查下去」是观测性的另一半。现状是**跟踪强、trace 弱**。

### 已经成立的：投递证据链

`engine/pi/delivery.ts` 的 `queued → context_committed → request_prepared → responded` 四阶段证据链是当前最可靠的可跟踪性：

- 证据落在**持久化快照**上（`evidenceId` = snapshotId，带 `contextEpoch`），不是内存态，**可回读、可在测试之外复查**
- 有判别式结果，`ok:false`（读取失败）与「确实没有证据」不同形——不会把读取故障当成「没发生」
- 会话条目另有稳定 `entryId` / `seq` 与运行关联

这是应保留并继续作为**首选**跟踪手段的资产。

### 已有但未接上的：运行时 trace

`engine/runtime/trace.ts` 是一个真实的观测总线：14 种 `kind`（`agent_*` / `turn_*` / `message_*` / `tool_execution_*` / `provider_*` / `prompt_snapshot`），关联字段 `runId`（必有）+ `sessionId?` / `requestId?` / `turnId?`，listener 隔离（异常与超时都不能改写 Agent loop），坏 listener 按去重留痕。设计本身是好的。

五个缺口：

1. **`traceId` 是每事件现生成的**（`createId("trace")`），不是共享关联 ID —— **不能按 `traceId` 分组**，当前是扁平事件流而非 span 树。这个名字会误导读者。
2. **trace 不进报告**：`types.ts` / `reporter.ts` / `scene-runner.ts` 里 `trace` 零命中，`AssertContext` 也不含它 —— 断言默认看不见。
3. **没有 `caseId` / `trial` 归属**：`RuntimeTraceEvent` 与 `RuntimeTraceContext` 都没有这两个字段，因此失败时**无法把 trace 关联回具体案例**。
4. **不落盘**：无 debug 导出，运行结束即消失，无法事后跟踪。
5. **每场景各自订阅**：目前只有 `估算器角色覆盖` 与 `P0快照` 两个场景调用 `captureRuntimeTrace()`，各存一个本地数组，没有共享收集器。

### 分层后的要求

1. trace 事件增加 **`caseId` + `trial` 归属**，由宿主在场景开始时注入 trace 上下文。
2. **共享收集器**取代每场景自订阅：`test/host/trace.ts` 按 `(caseId, trial)` 分桶，三层共用。
3. **失败时自动附上失败窗口的事件序列**进报告 —— 这才是「能跟踪」的实际价值，而不是让使用者自己去捞。
4. trace 随报告落盘。全量留存的体积代价先实测，默认按**失败优先**保留。
5. `traceId` 的语义二选一并在类型上写明：改成共享关联 ID（真 span 树），或改名 `eventId` 承认它是扁平事件流。**本契约倾向前者**——「一次运行的整条链路」才是使用者真正要的东西。
6. **投递证据链保持不变**，并继续作为首选跟踪手段；内存 trace 是它的补充而不是替代。

## 评测权威性：现状、缺口与补强

「这评测权威吗」不是一个态度问题，是一组可以逐条核对的性质。现状是**两面**，都要如实记。

### 已经成立的部分

- **防假绿工程扎实。** 场景作者在至少 8 处主动推理「这条断言会不会假通过」并补前置：`折叠中断`（防「文件太小根本没折叠」）、`摘要投影口径`（必须前置确认范围真的覆盖了探针结果）、`阶梯闸门` / `阶梯投影` / `地址完整性`（边界从模板推导，防「抄的模板过期而假绿」）、`standard-setup`（配置钉位存在的理由就是防门禁假通过）。
- **契约 attestation 不可绕过。** 浏览器侧不假装独立校验，只消费 Node 预检交出的证明；绕过启动脚本直接开 Tauri 会判 `stale`，拿不到一份看起来通过的报告。
- **有一手的产品缺陷捕获记录。** `计划生产闭环` 场景记录过 planner 把规划脚本直接吐给用户的真实缺陷。
- **有明确的三态分诊**：产品失败 / 场景前提失效 / 已知抖动，且裁定「预期外的失败照旧判失败」，不因已登记就放行。
- **未验证边界显式登记**，不把未接通能力说成已验证。

### 真实缺口

1. **最近一次整轮真跑的 4 条失败全部是测试侧**（`dataset.ts` 2026-09-28.2 记录：全部为场景前提失效，非产品回归）。也就是说最近一次信号 100% 是噪声。
2. **从未做过故障注入。** 全仓（含 `history/`）没有任何「故意在产品里埋缺陷、验证测试会红」的记录。**当前套件的绿等于「没红」，不等于「有牙齿」。**

### 补强：让「有没有牙齿」变成可测量

新增 `test:mutation` 层：对契约 `sourceFiles` 注入缺陷，跑快层，统计命中率。

| 手段 | 说明 |
|---|---|
| 自动变异 | 行业标准做法。TS 生态有 Stryker 及其 vitest runner；**采用前须核对其当前版本与本仓 vitest 大版本是否兼容**，本契约不预先断言可用 |
| 预定义故障注入 | 与 coverage point 一一对应的人工缺陷集，精确、可读，但需维护。**本次采用**：算子集见下 |

**为什么现在做不了、分层后才做得了**：变异测试要跑几十到上百遍完整套件。L4 一遍数分钟，做不起；L2/L3 秒级，做得起。**分层不只是跑得快 —— 它是让「这套测试到底有没有用」从态度问题变成可测量问题的前提。**

门槛位置：不进每 PR 门禁（耗时），进发布门禁或周跑；结果先作为**观测**记录，稳定后再设阈值。阈值一旦设定，按只缩不放的棘轮维护。

### 首轮观测（2026-09-29，先记录观测值，不设阈值）

实现：`scripts/mutate.mjs`（四个算子：条件反转 / 边界值偏移 / 分支删除 / 返回常数，按文件各取第一个可注入点）+ 目标清单 `test/mutation-baseline.json`，入口 `pnpm run test:mutation`（跑快层 unit + integration，一条注入一遍，约半分钟）。本轮目标先只放 2 个快层实际覆盖的文件：`src/services/personality/variable-pool.ts`、`src/services/context/budget.ts`。

**命中率 5/7 = 71.4%**（7 条有效注入，抓到 5、漏掉 2；两轮复跑数字一致）。注入全部在同一次运行内还原，`git status --short src/` 运行前后为空。**分母只覆盖 2 个文件，不是快层整体命中率** —— 扩大目标面后更新这里。

漏掉的注入（就是「这套测试没有牙齿」的具体位置）：

1. `src/services/personality/variable-pool.ts :: 返回常数`（第 144 行 `return false` → `return true`）：持久化 `VariableState` 的 `type` 与注册表不符时 `validateVarAgainstDef` 的错误放行，没有任何断言区分。
2. `src/services/context/budget.ts :: 边界值偏移`（第 90 行 `<= 0x7f` → `<= 0x80`）：ASCII 计费边界只有 U+0080 一个码点可观测，快层文本里没有控制字符 —— 命中面很窄的注入，但边界本身确实没有测试。

两条漏掉均经手工复现确认快层全绿（179/179），不是运行器假象。

口径与已知收窄（扩大目标前必读）：

- 语法解析不过的注入不计入分母（本轮 0 条）；快层跑不起来（超时/工具失败）不算抓到。
- 算子只在**代码区**匹配：已实测 `budget.ts` 的边界值偏移朴素匹配会先命中第 82 行注释里的 `tokenBudget < 1`，被掩码收窄掉；`--dry-run` 会打印这类收窄记录。
- `返回常数` 优先翻转布尔字面量（`true` ↔ `false`），`return undefined` / `return null` 这类同值改写跳过 —— 布尔上下文里不可观测的假漏不算漏。
- 本仓源码无分号，算子按 ASI 语义匹配（行尾即语句结束）；块体不止一条语句的 `if` 不猜（跳过，不计入分母）。
- 复现：先 `node scripts/mutate.mjs --dry-run` 核对注入点，再 `pnpm run test:mutation`。

## 数据集：把手写版本号升级为派生版本

现状：`dataset.ts` 的 `LIVE_DATASET_VERSION` 是**手写字符串**加一段变更日志，靠人记得 bump。忘了 bump 就会让两份不可比的报告被当成同一版本比较。

目标：

- `test/cases/` 是**类型化案例注册表**：每行 = `{ caseId, layer, module, contractId, 输入轮次, 期望不变量, tags }`。
- **同一个注册表被两层消费**：L2/L3 走 vitest 的 `describe.for` / `test.each`；L4 由它生成 `SceneDef`。这是唯一真相源，不产生第二份场景定义。
- **数据集版本 = 注册表内容的 sha256**，与 `sourceHash` 同构，取代手写版本号；变更日志交给 git。

收益：忘 bump 不再可能；报告可比性由 hash 保证而不是靠自觉；同一个 caseId 天然在两层之间保持同一份输入。

现有 `validateDataset` 的判据全部保留并继承：caseId 形状与唯一性、`module`/`contractId` 必须归属契约、每轮必须有断言、`expectFailure` 必须钉住具体分类与文案（空匹配器等于「允许任何失败」）、**unit 场景的 timeout 不得超过 `UNIT_SCENE_TIMEOUT`**（防止 unit 层偷偷做重活）。最后一条正是「unit 层不得做 IPC 重活」在数据集层的守卫，迁移时不要丢掉。

## 明确不搬

- openclaw 的 `isolate: false` 非隔离 runner（542 行，为 13k 文件规模服务，需精确单例重置登记表）
- hermes 的 per-file 子进程 + duration cache LPT 切片（21k 测试规模才回本）
- openclaw 的 558 个 YAML QA 场景 + flow DSL
- 覆盖率阈值（三家一个都没有）
- LLM-as-judge（新的花费来源）

## 风险与诚实边界

1. **L3 的实际搬迁率未知。** 按依赖分析：`取消竞态`、`许可释放补偿` 确定留在 L4——理由是**直接 invoke Rust 命令**（`bash_exec` / `bash_cancel` / `file_exists`），不是「压许可内核」（2026-09-29 审计更正：`取消竞态:134` 的原注释自述「本场景直接走 IPC、不经许可域」，它的 `sharedActive===0` 断言恒真，只能被其他场景的残留点亮）；`MCP大结果回读`、`子代理授权范围`、`工具结果存档边界`、`地址前缀解析` 待实测；其余 7 个大概率可搬。最终数字由 W3 的逐个试跑给出，不由本契约预判。
2. **适配层有维护成本。** Rust 侧新增 IPC 命令时需同步登记；未登记命令会抛错，因此不会静默漏掉，但会以场景失败的形式暴露。
3. **搬家爆炸半径。** 见下节清单，遗漏会造成静默失效（例如 `live-test.html` 的 script src 断掉、`tsconfig` 不再类型检查测试树）。

## 测试逻辑审视：不搬错的东西

**搬迁的前提是「原样正确」，而现有场景不满足这个前提。** 2026-09-29 的只读审计确认：待搬的快层场景里存在**断言无区分力**的场景——不是「可惜没测到」，而是「看起来测了、实际测的是别的东西」。搬进快层等于给它镀一层「已分层、已审查」的信用。

**这类缺陷无法靠观察通过/失败发现**：它们的共同点是**永远绿**。跑一百遍也不会红，只会让报告更好看。

### 缺陷分类法（审计口径）

| 编号 | 名称 | 判据（一句话） |
|---|---|---|
| D1 | 恒真断言 | 假设产品实现被改坏，这条断言仍然不红 |
| D2 | 断言对象错位 | 断言的是测试自己构造的期望值或 fixture，不是产品产出 |
| D3 | 只测调用不测结果 | 检查了「发生了」，没检查「发生得对不对」 |
| D4 | 期望值抄实现 | 期望值照实现写出来，是同义反复，不构成约束 |
| D5 | 前提失效 | setup 构造的输入与产品当前真实形态不符（真跑会红，但不是产品问题） |
| D6 | 超宽匹配 | 子串／正则匹配过宽，错误实现也能通过 |
| D7 | 时序脆弱 | 固定 sleep／无界等待，慢机器假红 |
| D8 | 跨场景污染 | 依赖其他场景留下的全局状态 |
| D9 | 事后合理化 | 断言是「只要不抛错就算过」，与其声称覆盖的行为无关 |
| D10 | 重复或近重复 | 同一断言在多处重复，制造覆盖假象 |

**判定方法**：读断言 → 读它断言的产品源码 → 问「把产品实现改坏（条件反转／常数替换／分支删除），这条断言还会红吗？」不会红即命中。**不允许只读断言就下结论**，必须读到产品侧。

### 已确认的结构缺陷（基础设施层，与具体场景无关）

1. **重复 caseId 检查是死代码（W1 已修）。** `collectScenes()` 在 [`e2e-main.ts`](../../../test/e2e/e2e-main.ts) 里先按 `meta.caseId` 建 Map 去重，之后才把去重后的列表交给 [`dataset.ts`](../../../test/e2e/dataset.ts) 的 `validateDataset()`，于是「caseId 重复」分支**永远不可达** —— 两个不同场景撞 caseId 时后者**静默消失**，报告照样全绿。
   **修法与一处连带事实**：改成**按对象身份收敛**（`[...new Set(scenes)]`）而非「完全不收敛」。因为 **111 个场景文件里有 96 个**把同一个 `SceneDef` 同时挂在 `export const X` 与 `export default X` 上（`P0快照.scene.ts` 还是三重导出），展平后是 **255 个对象 / 159 个不同场景**；完全不收敛会当场报 96 条假重复。按身份收敛两者兼得：同一对象只算一次，两个不同对象撞 caseId 仍被报出。
   判据：收敛后 159 个场景、`datasetErrors: []`；注入「不同对象同一 caseId」后变 160 且报出一条重复。
2. **失败通道分裂。** 扫描显示 **61 / 113 个文件在 `setup` 里写 `throw`**（判据：`setup:` 后 1200 字符内出现 `throw new`，属启发式计数）。setup 失败在报告里归因成「场景前提失效」，与「断言失败」不可区分。这不是错误（setup 本就该能失败），但它让**一半以上的失败面统计不到断言通道上**，也是 `dataset.ts` 里那 4 条「非产品回归」的温床。
3. **`entry` 有默认值，18 个场景靠省略被分类。** `scene-runner.ts` 与 `dataset.ts` 都取 `meta.entry ?? "runtime"`。至少 `tool-execution/工具联动.scene.ts` 的默认值与真实依赖不符（它的 userText 要求模型真实调用工具）。**省略不是分类**，搬迁时必须逐个显式裁定。
4. **两个纯转发别名文件**（`memory/主动消息来源`、`memory/工具成对观测`）各 1 行、贡献 0 个场景，搬家时删除。

### 搬迁门禁：每波必过

**一个场景只有先通过本模块的逻辑审视，才允许搬入快层。** 审视结论三选一，逐条登记：`照搬` / `修正后搬`（写清改什么）/ `删除`（写清为什么它不构成测试）。

不允许「先搬过去、以后再审」——搬过去的错误断言会立刻获得快层的可信度，之后再没有人回头看它。

未过审视的场景**留在 L4 原样不动**，直到本模块审视完成。审视本身是**只读**的：不修产品、不改场景，只出结论。

| 6 | L2 单元层不得 import pi runtime / 工具系统 / 会话存储（理由**不是**「L2 里 IPC 跑不了」—— 适配层能等价复现 31 条命令；而是 L2 不依赖这三样） | 可判 |

| 9 | 新增用户可见行为必须先在本层契约加 coverage point 与 caseId | 机制已保证 |
| 10 | 预期失败用显式声明，不得用「不写断言」或「允许任何失败」放过 | 机制已保证 |

可判项由 `scripts/check-test-rules.mjs` 扫描 `test/` 实施，命中即失败。它是守卫，因此**守卫自身要有测试**（照 hermes 的做法：断言「访问真实网络／真实 Provider 会抛错」这类守卫真的生效，而不是假定生效）。

规则落位：

- `test/README.md`：三层职责边界 + 完整规则表 + 各层「怎么判断该写在哪一层」
- `test/SKILL.md`：`/analyze` `/generate` `/audit` 生成测试时的硬约束与禁令
- `AGENTS.md`：全局测试段落改为三层入口，并指名 `check-test-rules.mjs`

**纪律在 W1 就位，不等 W6**：否则迁移过程本身就会按旧习惯写出一批新违规。W6 只负责把棘轮与 FLAKY 策略这类 CI 收口补齐。

`docs/history/**` 中的引用**不改**：历史内容不作为当前指令。

## 已决定：L4 不引入 WebDriver 驱动

原候选是用 vitest 或 Playwright 作为编排器经 WebDriver 驱动 Tauri（hermes 用 Playwright 驱动 Electron 的同构做法）。**否决**：Tauri 官方路径是 WebdriverIO + `@wdio/tauri-service`，而 `tauri-driver` **没有 macOS 的 WKWebView 驱动**——本项目目标平台是 Windows + macOS，这条路径覆盖不了主平台。基于文件的结果协议保留。
