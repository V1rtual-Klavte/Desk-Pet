## 背景与排查结论

用户反馈「主动消息和静默了解似乎根本没生效」，并要求**设置页每一项都按规范同步到 CONFIG**（否则导入导出/备份恢复会漏）。只读排查结论：

**一个根因同时掐死两条链**（已实测，非推测）：

```
macOS 未锁屏 → CGSessionCopyCurrentDictionary 里没有 CGSSessionScreenIsLocked 键
  → capture.rs:185 「键缺失 = 不可确认」→ observation_state 恒为 "unavailable"
      ├─ scanner.ts:219 总门禁 observationState!=="observed" → 每个主动机会被静默丢弃
      └─ scheduler.ts:77 eligibleForBatch 恒 false → 静默了解从未产出
```

**硬证据**：只读探针实测 `LOCKED_KEY_PRESENT: false`（键确实缺失），而 `IDLE_SECONDS` 查询正常（排除另一分支）｜`deskpet.log.2` 里 642 条 `state=unavailable`、**0 条 `observed`**（locked 7、suspended 2 → 事件驱动监控本身是活的）｜`memory.sqlite3` 的 `proactive_attempts/occurrences/evaluations` 全 0，而 `proactive_source_registry` 有 4 行（证明 tick 在跑、机会已生成、门禁全灭）｜`behavior/understanding.json` **从未生成**｜所有会话 JSONL 无任何主动消息。

**加重排查难度的两点**（一并修）：Node 日志级别在引导期从未应用（主动链路的 debug 证据全丢）；`proactiveBands` 曾被整份丢弃（日志 16:56–18:48 刷 30 次「档位无效」，工作区未提交的 loader 修复后消失）。

**设置侧现状**：审计设置页 35 个非 action 字段，**全部已在 `CONFIG.yaml`/`CONFIG-DEV.yaml.example` 中**。唯一违规项是「主动消息开关」——`action.toggleProactive` 按钮，真相源在宿主 SQLite `proactive_control`，**不在 CONFIG**，导入导出/备份恢复覆盖不到。另 `ai.silentAccess` 的四个数值实际被**主动消息**消费（`cooldown.ts:11`、`scanner.ts:117/125/166`），名不副实。

**现有频率机制**（回答用户「现有扫描器有定吗」——有，且是多层叠加）：主动消息共 6 层——① 唤醒（5min tick + 事件）② 机会来源（任务/rhythm 仅 9–12、18–22 点/记忆/话题/好奇/窗口上下文/变量跨档；23–9 点直接返回空）③ 准入（开关/静音/可见性/观察态/15s 新鲜度/冷却/AI 生成中/lane）④ 每日配额（成功 6 条、规划 8、表达 12、辅助 4、24000 token）⑤ 最小间隔（1h + 最多 2h 抖动）⑥ **规划器（辅助模型，可 decline）**。静默了解仅 2 层：60s tick、`MIN_BATCH_GAP_MS` 30min，另有 idle≥30min、每日 4 批、每小时 6 次读取。

**已拍板**（用户 2026-10-05，含多轮修订后的最终口径）：
- 档位 = 常量节流 + 给规划器的积极度提示；**三处档位统一为「关 / 低 / 中 / 高」四档**，独立启用开关全部并入档位；静默访问四个数值删掉收进档位；连带修日志级别/限频留痕/proactiveBands/inspector。
- **锁屏时也要能跑**：锁屏 = 「用户离开」而非「不可观察」。
- **规划器升级为带工具**：查本地 / 截图（本批不加新工具）；频率「不要太死板」。
- **主动消息不要定时**，要随机点（唤醒节拍随机化，不形成固定节拍）。
- **静默了解只以「每天最多几批」为主闸**，其余节流退为防抖/防突发。
- **MCP 与 Skill 要自带一点点真正能用的**（不是推荐清单）；旧的 MCP 五项与 Skill 三项均为用户有意删除，**不复原**。
- 本契约落 `docs/plans/active/`，进度记在未完成工作总表。

## 档位总览（三处 × **四档：关 / 低 / 中 / 高**）

共同轴：**多久跑一次 × 一天最多几次 × 每次花多少 token**。

**「关」档与独立开关的合并（用户要求加「关」后的连带简化）**：加入了「关」档就与既有的独立启用开关表达同一件事，同时保留即构成**两个定义点**（违反根 AGENTS「状态与配置不要建立第二个定义点」）。因此：

| 功能 | 改前 | 改后 |
|---|---|---|
| 主动消息 | `action.toggleProactive`（SQLite 开关）+ 频率档 | **单一下拉 `ai.proactive.frequency: off｜low｜medium｜high`** |
| 静默了解 | `ai.silentAccess.enabled`（Bool）+ 频率档 | **单一下拉 `ai.silentAccess.frequency: off｜low｜medium｜high`** |
| 记忆整理 | `ai.memory.dreaming.mode: manual｜idle` + 频率档 | **单一下拉 `ai.memory.dreaming.tier: off｜low｜medium｜high`** |

- **`off` 的语义**：不自动跑。**手动入口保留**（用户主动点击是用户动作，不是后台行为）——因此 dreaming 原来的 `manual` 档被 `off` 自然吸收，`mode` 枚举整体退役。
- **`ai.memory.enabled` 保持不动**：它是「记忆功能总闸」，另有召回/投影消费者（`runtime.ts:1773,1789`、`scanner.ts:203`），与整理频率不是一回事。
- **附带好处**：主动消息的开关本要从 SQLite 迁进 CONFIG，现在**不必迁布尔值**，直接并入档位；SQLite `proactive_control.enabled` 列仍按 Part 2.2 删除。

**下表三张表均为 `low｜medium｜high` 的取值；第 0 档「关」= 该功能完全不自动运行**：主动消息 = 不唤醒、不产生机会、不发送；静默了解 = 调度器不启动（timer 都不建）；记忆整理 = 空闲调度器早退，**手动按钮保留**。

### ① 主动消息 `ai.proactive.frequency`（**改为随机唤醒，不设定时节拍**）

| | 低 | 中 | 高 |
|---|---|---|---|
| 唤醒节拍（随机） | 每 **2–5 小时**随机一次 | 每 **30–90 分钟**随机一次 | 每 **10–30 分钟**随机一次 |
| 开口后冷却 | 3–5 小时 | 1–3 小时 | 30–90 分钟 |
| 每天最多问 LLM | 3 次 | 8 次 | 14 次 |
| 每天成功上限 | 2 条 | 6 条 | 10 条 |
| token/天 | 8000 | 24000 | 40000 |
| **最终体感** | **1–2 条/天** | **2–4 条/天** | **4–8 条/天** |

**改动要点**：现有 `tickMs`（固定 15/5/3 分钟）改为**随机唤醒区间**——每次唤醒后抽取下一个检查时刻，不形成固定节拍；事件唤醒（窗口变化 / 变量跨档 / 解锁）保留不变。**「中」不再是现状基线**（现状是固定 5 分钟 tick），这是用户明确要求的行为变更。

可开口窗口固定 09:00–23:00（23–9 点完全静默）。典型一天：低 = 上午一句、傍晚一句；中 = 10/14/19/22 点前后各一句；高 = 每 30–90 分钟可能一句（随机点，不成节拍）。

### ② 静默了解 `ai.silentAccess.frequency`

## Part 1 · 根因修复

### 1.1 `crates/native-host/src/monitor/capture.rs` — macOS 锁键判定

`CGSSessionScreenIsLocked` 是**只在锁屏时写入**的键，不能用「键是否存在」当可观察性判据：

| 探测结果 | 含义 | 结论 |
|---|---|---|
| 值为 null（键缺失） | 未锁屏（本机实测） | `Unlocked` → 继续查 idle |
| `== kCFBooleanFalse` | 显式未锁屏 | `Unlocked` → 继续查 idle |
| `== kCFBooleanTrue` | 锁屏 | `Locked` |
| 非 null 且两者都不是 | 系统行为变化 | `Unknown` + 一次性 `rust_warn!` |

- CFDictionary 不能存 null 值（存 null 等于删键），故 null 与 false 可区分；需新增 extern `static kCFBooleanFalse: CfTypeRef;`（CoreFoundation 已链接）。
- 抽纯函数 `lock_probe_state(LockProbe) -> LockState` 与 `system_activity_from(...) -> SystemActivitySample`，`#[cfg(any(target_os = "macos", test))]` 包裹 → **Windows CI 的 `cargo test --lib` 也会执行**。
- 留痕：`static MISSING_LOGGED: Once`（`rust_info!`，release 默认 INFO 可见）、`UNEXPECTED_LOGGED: Once`（`rust_warn!`）。**不得每次采样都打**。
- 注释替换 :169-170：写明理由 + 实测证据 + **风险注明**（未来系统若锁屏也不写此键，会误报 observed；这是相对「永久 unavailable」的取舍，必须明写）。
- **平台对称**：Windows 分支（:54-122）无同型 bug，**不改行为**，仅加注释说明口径对应。交付标注 **Windows 未验证**。
- 其它消费点已核对无需同步：`monitor/mod.rs:96-106` 原样透传字符串；`events.rs` 只用分布式通知 `com.apple.screenIsLocked/Unlocked` 做**唤醒**、状态仍来自采样（:173-174 注释）；消费侧按 `screen_state ∈ {observed, locked}` 放行（locked 仅拒绝截图类请求，W1 已实施；原「只判 `"observed"`」表述作废）。

### 1.2 锁屏语义：从「不可观察」改为「用户离开」

现状 `observation_state` 一个字段同时表达两件事，导致锁屏 = 两条链全停。改为**两个正交维度**：

- `screen_state`: `observed`（前台窗口可截）/ `locked`（锁屏，截图无意义）/ `unavailable`（真不可知）
- `idle_for_ms`: 保持

下游按需取用：
- **静默了解**：`screen_state ∈ {observed, locked}` 且 idle 达标即可跑；`locked` 时**跳过截图来源**，只走文件/目录/窗口快照（窗口快照是最后一次观察，需放宽 `OBSERVATION_MAX_AGE_MS` 的新鲜度判据）。
- **主动消息**：`locked` 时不因锁屏额外加严（机会生成与准入照常，受既有每日配额与最小间隔约束）；解锁事件本就唤醒扫描。

#### 档位最终体现出来的频率（2026-10-05 订正）

### 2.4 「不要太死板」：档位是基准，运行期自适应修正

档位不写成硬边界，而是**基准值**，再由运行期因素修正：

- **已有的自适应**：`store.rs:35 reply_tier_limit()` —— 昨日主动消息未被回应且未清除时，当日成功上限由 6 降到 **1**（跨天滚动）。这是现有的「回执驱动刹车」，保留并作为范式。
- **扩展方向**（实现时逐项确认可行性）：按最近互动密度、用户活跃度（presence/behavior 画像）、时段做修正；由扫描器决定「此刻值不值得问一次规划器」而不是机械按 tick 问。

### 2.5 档位如何到达 Rust（Rust 终裁，deny-first）

- 需同步 `protocol.json` 的 commands 参数 → 重生成两侧 → Rust 校验收口（请求不得把上限抬到共享常量之上）。

## Part 5 · 记忆整理 / dreaming 频率档位（用户新提）

### 5.1 认知纠正：只有一条链

**不存在第二种「记忆自动整理」**。「整理」= dreaming 三阶段（Light 收集来源 → Review 生成候选 → Publish 提交），手动与自动**共用同一管线、同一本 `memory_jobs`/预算/租约账**；唯一分支点是 `dreaming.ts:336` 的 `mode !== "idle"` 早退。所以「记忆整理档位」与「dreaming 档位」是**同一个东西**。

### 5.2 现状（四处取值一致）

| 位置 | `ai.memory.enabled` | `ai.memory.dreaming.mode` |
|---|---|---|
| `CONFIG.yaml:76-91` | `true` | `idle`（另有 `idleSeconds:120` / `minIntervalMinutes:60` / `maxDailyTokens:72000`） |
| `CONFIG-DEV.yaml.example:43-53` | `true` | 同上 |
| `schema.rs:611-621` + `DREAMING_MODE:229-238` | Bool | `FieldKind::Enum`，**只有 `manual` / `idle` 两个值** |
| `config.ts:699/705-711` | 默认 `true` | 默认 `"idle"` |

`mode` 语义：`manual` = 只有面板动作 `action.memorySweep` 能跑；`idle` = 空闲调度器自动跑（`init.ts:73` → `dreaming.ts:333-368`，15s 轮询 `IDLE_TICK_MS`；判定序：`mode==="idle" && enabled` → `!isAIGenerating()` → `now-idleSince ≥ idleSeconds` → `now-lastIdleRunAt ≥ minInterval` → 单飞 → `idleBudgetAvailable()`）。三个数值**设置窗不提供**（属「技术参数」），只能手改 CONFIG。

**本轮变更（用户加「关」档后）**：`ai.memory.dreaming.mode` 整体退役，改为 `ai.memory.dreaming.tier: off｜low｜medium｜high`。
- `off` = 空闲调度器不跑（对应原 `idle` 分支的早退）；**手动入口 `action.memorySweep` 保留**——它是用户主动动作，不是后台行为。原 `manual` 档因此被 `off` 自然吸收，「只想手动整理」= 选 `off` + 点按钮。
- `low｜medium｜high` = 原 `idle` 的自动行为，按档位表取值。
- 分支点仍是一处：`dreaming.ts:336` 的判定改为「`tier !== "off"` 才继续」+ 档位取三个数值。

| 门禁 | 现值 | 位置 |

### 5.4 建议的 dreaming 档位表（空闲阈值按用户口径上调，**「中」不再等于现状**）

### 5.5 顺带发现的两个真实缺陷（建议并入本轮）

1. **无新来源也开作业**：每次 idle 命中即创建 Review job，哪怕水位之后一条新来源都没有（快速 `empty` 返回，但白耗一次 job 创建）。**无「积压量阈值触发」**。修法方向：开 job 前先查水位之后是否有待处理来源。
2. **失败无重试 / 无 resume**：`resumeMemoryJob` 参数存在但**生产无调用者**（面板「取消/继续」未做，`未完成工作与已知缺口.md:157`）。失败后只能等下一次 idle（且吃满 minInterval）或手动再点。
3. 死代码：`config.ts:715-735 memoryConfigError`（idle 30-3600 / interval 1-1440 / daily 0-100000 范围校验）**全仓无调用者**，越界只有 `Math.max` clamp；宜删或接回校验。

## 未验证项与风险

- **Windows 分支**：本机不可编译，仅注释级差异说明；新纯函数单测会随 CI `windows-latest` 跑，但不证明链接与真实锁屏行为。交付须标注未验证。
- **macOS 锁屏路径（key=true）** 仅单测覆盖，未做真锁屏端到端；「键缺失=未锁定」是隐私相关放宽，未来系统若改变行为会失效（已在代码注释与文档写明取舍）。
- **`observation_state` → 两维度字段是跨层线协议改动**，Rust 分派 / TS 类型 / 消费者 / 契约要逐项对齐，类型检查不能证明接线正确。
- **带工具规划器会显著提高 token 消耗**，与「轻量化、节省 token」方针存在张力，需档位与预算联动并实测。
- **`crates/` 已纳入 git 跟踪**（2026-10-05 起，见文首说明）：Rust 改动 `git diff` 可见；此前「未被跟踪」的表述已失效。
- **静默了解 Live 验收**依赖 idle 达标与辅助模型配额，可能跨天。
- **2.5 的 Rust 投影存储**：W2 已按推荐做法实施（dispatcher 级运行期状态，不进 SQLite、不读 CONFIG、不回写；数值真相源仍是生成表 + CONFIG 档位），逐请求参数备选不再采用；「是否构成第二定义点」由 W2 审查复核。
- 「主动消息开关」迁移后**旧 SQLite 的开关状态随 `enabled` 列删除失效**：旧库按 `MEMORY_SCHEMA_VERSION`（3）abort，开发阶段按「旧数据视为可弃」删 `memory.sqlite3` 三件套重建，需向用户明示。
