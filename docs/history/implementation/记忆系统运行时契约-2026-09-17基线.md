# 记忆系统运行时契约

> 本文是记忆系统实施前的运行时基础契约。它先固定消息来源、会话真相源、队列、Plan、Prompt、压缩、恢复、安全、追踪和评测接口，再实现长期记忆算法。
>
> 目标不是把所有能力一次写完，而是让每一步都有持久化边界、失败语义和可观察证据。没有通过本文的门禁，不进入长期记忆自动提取、用户画像改写或 dreaming 的生产接线。
>
> **实施状态（2026-09-17 工作树）**：P0–P3 已落地；P4/P5 前置实现已补齐，集中验证以执行手册 §6.1 为准；P6（MemoryKernel、画像写入、dreaming、评测）未开始。本文仍是目标协议；逐节落地情况见 §1.1，未落地部分不得当作当前能力。
>
> 下一阶段方向以[统一内核建设方案](../design/轻量陪伴运行时与统一内核建设方案-2026-09-17基线.md)为准；长期记忆推荐 SQLite，撤销旧纯 Markdown 存储限制，会话正文继续保留 Markdown。会话压缩已按[专项方案](../../history/implementation/会话压缩建设方案.md)接线，不依赖长期记忆后端。下述未来画像/记忆“写文件”协议应理解为向版本化 MemoryStore 提交，Markdown 在迁移后成为投影；尚未迁移的当前实现不变。

## 1. 结论先行

当前文档方向正确，但原稿不能直接指导实现，原因是它把长期记忆、用户画像、dreaming、权限重审和评测留成了“后续”，同时没有定义可恢复的事件模型、Plan 身份、队列确认和最终 Provider payload。因此原稿无法保证以下问题被解决：崩溃后不丢消息、Plan 可续跑、主动消息不污染用户输入、压缩不破坏 tool pair、权限不被信任短路绕过、上下文可追踪、记忆可以评测。

本次重写采用以下原则：

1. **持久化先于投递**：用户输入、队列入列、状态变化、Plan checkpoint 和工具副作用标记都先写入会话事件，再调用 Pi 或工具。
2. **来源不可推断**：所有进入 runtime 的内容都有 `origin` 和 `MessageMeta`；禁止用 role、字符串前缀或 `isActiveMessage` 猜来源。
3. **Pi 只负责 Loop**：Pi Agent Core 负责消息循环、工具回注和 steer/follow-up；会话、Plan、记忆、权限、追踪由 Desk-Pet 持有。
4. **最终请求可复现**：每次 Provider 请求保存经过 Prompt transform、压缩和消息转换后的 `PromptSnapshot`，不能只保存 builder 的中间字符串。
5. **失败可降级**：记忆、hook、摘要、指标和日志失败不能阻塞普通回复；安全检查和持久化失败必须阻断投递并留下结构化错误。
6. **恢复不重放副作用**：`queued` 可重新投递；`running`、未知副作用和未确认工具调用一律标记为 `interrupted` 或 `unknown_side_effect`，等待人工或幂等协议处理。

## 3. 目标边界和不变量

### 3.1 本轮必须产出

- `IngressEnvelope`、`MessageMeta`、`SessionEvent`、`SessionTurnRecord`、`PlanRecord`、`QueueEntry`、`PromptSnapshot`、`TraceEvent` 的版本化类型。
- 以 `sessions/*.md` 为用户可读真相源的事件追加格式；旧会话可读，新字段缺失按兼容默认值解释。
- 单会话 AgentSlot、队列优先级、steer/follow-up 投递和重启恢复。
- Plan/子 agent 的持久化身份和步骤 checkpoint，不重放未知副作用。
- 分层 ContextKernel、最终请求快照、估算 token 与 Provider 实际 usage 的分离记录。
- 三层压缩、tool pair 保持、摘要版本和失败降级。
- 用户画像和长期记忆的投影接口、来源/污染标记、写入闸门，以及 dreaming 的最小可运行协议。
- Pi Core hook 接线、Desk-Pet 外层 hook 总线、权限/沙箱/联网/自研工具的统一审查契约。
- 离线 fake provider 的 memory eval 数据集和真实 Provider Live Test 的映射。

### 3.2 不变量

1. `requestId`、`turnId`、`runId`、`sessionId` 必须全程可关联；重试只增加 `attempt`，不新建用户事实。
2. 用户原文 `rawText` 永不被 prompt 改写覆盖；改写结果只能作为带来源的派生层。
3. `role=user` 只允许 `origin=user` 的可见用户输入；用户确认结果若需进入模型，必须引用原 user turn，不能伪造成另一条 user 消息。active、hook、recovery、memory、plan 不得使用该 role 冒充用户。
4. 任何记忆召回都带 `sourceId`、`memoryVersion`、`provenance`、`taint` 和 token 预算；召回结果不能再次作为新记忆候选。
5. 未经 Rust 最终校验的工具调用不能执行；trust 只是一条有范围的授权记录，不是跳过检查的布尔开关。
6. 每次状态转换都可重放、可去重、可审计；UI 状态和 `sessions/*.md` 不是两份竞争真相源。

## 4. Pi Agent Core 的 hook 能不能用

### 4.1 结论

**能用，而且当前版本已经提供直接可用的原始 Agent hook；但 Pi Core 不会替 Desk-Pet 提供完整的记忆、画像、dreaming、权限和崩溃恢复 hook。** 当前安装的 `@earendil-works/pi-agent-core` 为 0.85.1，公开类型声明包含以下能力：

| Pi API | 可直接用于 Desk-Pet 的职责 | 关键限制 |
|---|---|---|
| `beforeToolCall` | 参数已校验后的安全检查、确认、工具配额、审计 | 返回 `{ block: true }` 才阻断；必须有超时和 AbortSignal 处理 |
| `afterToolCall` | 脱敏、结果大小控制、错误归一化、工具结果 telemetry | 可覆盖整个 content/details，禁止把不可信结果变成 system 指令 |
| `transformContext` | API 请求前按 round 压缩、注入 MemoryProjection、过滤 UI-only 消息 | 必须返回安全 fallback；不能把快照捕获放在 builder 之前 |
| `prepareNextTurnWithContext` | turn 完成后持久化并消费 steer/follow-up，决定下一轮 context/model | `shouldStopAfterTurn` 可能先结束循环，不能依赖它之后再收队列 |
| `shouldStopAfterTurn` | 达到上下文/预算/安全终点时优雅结束当前 turn | 返回 true 后会在 drain 队列前结束；需要接受插话时不得误用 |
| `subscribe` | 生命周期事件、最终消息、工具事件、快照和 trace | 不依赖 listener promise 被等待；将持久化加入串行队列，在工具/请求/settle 前显式 flush |
| `onPayload` / `onResponse` | 记录发送给 Provider 的 payload、响应头/usage、cache 信息 | 只能记录脱敏副本，不能把密钥写入 snapshot |
| `steer` / `followUp` | 当前工具批次结束后的插话和后续任务 | `steer` 是同步入队，Desk-Pet 必须先持久化 QueueEntry |
| `toolExecution` | 控制同一 assistant message 内工具串行或并行 | 当前 runtime 保持 sequential；本分支未开放工具并行 |

### 4.2 Harness hook 的边界

Pi 包公开了 `AgentHarness`，其 `hooks`/`events` 接口由内部的 `HookRegistry`/`HarnessEventBus` 实现，提供注册、聚合、gate、错误隔离和事件投递；当前 Desk-Pet 的 [`runtime.ts`](../../../src/services/engine/pi/runtime.ts) 直接构造原始 `Agent`，所以这些 Harness hook **不会自动触发**。只有在明确采用 `AgentHarness` 并接入其 context/effect gate 后，才能使用 Harness hook；不要从当前顶层入口直接 import 这些内部实现类。

不得把下列名称当成 Pi 已有能力：`SessionStart`、`PermissionRequest`、`MemoryWrite`、`Dreaming`、`CrashRecovery`、`ProfileRewrite`。使用现有领域调用和 typed trace 表达这些动作，不为未实施的 P6 重建通用 HookBus。

### 4.3 接线规则

```text
SessionTurnStore / PlanStore / MemoryKernel / TraceStore
        -> Desk-Pet 领域调用 / typed trace（无通用 HookBus）
        -> Pi Agent（loop hooks）
             beforeToolCall -> ToolRouter + Safety
             transformContext -> ContextKernel -> PromptSnapshot
             prepareNextTurnWithContext -> queue drain
             subscribe -> event adapter
             onPayload/onResponse -> provider trace
```

Pi hook 只改变当前 loop 的行为，不拥有会话真相源。未来若引入有实际消费者的外层 hook，必须声明 `blocking` 或 `async`：安全、持久化、来源校验属于 blocking；指标、UI、dreaming candidate 属于 bounded async。任一 hook 都要有 `hookId`、超时、错误分类、重入保护、脱敏规则和 `origin/taint` 继承。

## 5. 消息、会话和持久化协议

### 5.1 输入封装

```ts
type MessageOrigin =
  | "user" | "assistant" | "tool" | "active" | "hook"
  | "queue" | "recovery" | "plan" | "memory"

interface IngressEnvelope {
  schemaVersion: 1
  requestId: string
  sessionId: string
  parentRequestId?: string
  parentTurnId?: string
  origin: MessageOrigin
  querySource: "chat" | "active_monitor" | "hook" | "queue" | "recovery" | "plan"
  rawText: string
  normalizedText: string
  receivedAt: number
  priority: "now" | "next" | "later"
  taint: "trusted_user" | "system" | "untrusted_external" | "derived"
}

interface MessageMeta {
  origin: MessageOrigin
  requestId: string
  sessionId: string
  turnId?: string
  runId?: string
  visibleToUser: boolean
  persisted: boolean
  eligibleForTranscript: boolean
  eligibleForMemory: boolean
  isMeta: boolean
  taint: IngressEnvelope["taint"]
}
```

`preprocessor` 只做 trim、slash 分类、规范化、长度和来源标记，输出 `IngressEnvelope`。去重使用持久化 `requestId`/`idempotencyKey`，禁止模块全局 `lastUserText` 作为事实来源。原文和规范化文本都保存，Prompt rewrite 只能生成另一个派生字段。

### 5.2 SessionEvent 和 SessionTurnRecord

不要用只有 user/assistant 两种 role 的结构承载所有运行状态。会话文件继续保存可读正文，同时在每个事件的 HTML comment 中保存完整 JSON：

```ts
type SessionEventKind =
  | "turn_created" | "turn_state" | "user_message" | "assistant_message"
  | "tool_call" | "tool_result" | "system_message" | "active_message"
  | "hook_message" | "plan_checkpoint" | "queue_state" | "recovery"
  | "prompt_snapshot" | "compaction" | "memory_projection" | "error"

type TurnState =
  | "queued" | "dispatching" | "running" | "waiting_tool"
  | "done" | "failed" | "interrupted" | "unknown_side_effect"

interface SessionTurnRecord {
  schemaVersion: 1
  turnId: string
  sessionId: string
  runId?: string
  requestId: string
  role: "user" | "assistant" | "tool" | "system"
  origin: MessageOrigin
  state: TurnState
  text?: string
  apiRoundId?: string
  toolCallId?: string
  parentTurnId?: string
  attempt: number
  idempotencyKey: string
  createdAt: number
  updatedAt: number
}

interface SessionEvent {
  schemaVersion: 1
  eventId: string
  sessionId: string
  turnId?: string
  kind: SessionEventKind
  origin: MessageOrigin
  payload: Record<string, unknown>
  createdAt: number
  idempotencyKey: string
}
```

状态规则：

```text
submit -> queued -> dispatching -> running -> waiting_tool -> done
queued -> failed / interrupted
dispatching -> failed / interrupted
running -> failed / interrupted / unknown_side_effect
waiting_tool -> failed / interrupted / unknown_side_effect
```

`SessionTurnStore` 至少提供 `append(event)`, `transition(turnId, state, patch)`, `appendEvent(event)`, `flush(sessionId)`, `readRecoverable(sessionId)`。实现要求：单会话写锁、事件 ID 幂等、版本号/CAS、临时文件 + rename 原子提交、启动时修复未完成临时文件。先写 `queued` 再更新 UI 和调用 Pi；回复只有在 assistant 正文和状态事件都 flush 后才标记 `done`。

### 5.3 崩溃恢复

启动顺序固定为：

1. 读取并校验 session Markdown，建立事件索引。
2. 将 `dispatching/running/waiting_tool` 转成 `interrupted` 或 `unknown_side_effect`，写入 recovery event。
3. 只选择 `queued` 且 `idempotencyKey` 未完成的用户 turn 重建 QueueEntry。
4. Plan/Step 从最近 checkpoint 恢复；副作用未知的 step 不自动重试。
5. 创建 AgentSlot，从已完成 transcript 和合法 tool result 播种，再投递 queued turn。
6. recovery 说明使用 `origin=recovery`、`role=system` 或 UI-only custom message，不得作为用户输入或长期记忆。

恢复报告必须列出 `sessionId`、恢复/跳过的 turn、未知副作用 toolCall、Plan 状态和失败原因。启动失败时保留文件，不清空用户会话。

## 6. AgentSlot、队列和 Plan

### 6.1 AgentSlot

AgentSlot 是按 `sessionId` 索引的驻留管理器，不是全局 AI 锁：

```ts
interface AgentSlot {
  sessionId: string
  getOrCreate(): Promise<Agent>
  enqueue(entry: QueueEntry): Promise<QueueAck>
  drain(): Promise<void>
  releaseWhenIdle(): Promise<void>
  dispose(reason: "session_switch" | "shutdown" | "error"): Promise<void>
}
```

当前活跃会话常驻；非活跃但运行中或队列非空时保活；空闲后可回收，下次从会话文件恢复。Agent 回调不能闭包捕获一次性 turn 参数，必须从 slot 的当前 run context 读取 session、权限、预算和来源。

### 6.2 队列

每个 session 独立队列，优先级为 `now > next > later`，同级 FIFO。QueueEntry 至少包含 `queueId`, `turnId`, `sessionId`, `requestId`, `priority`, `enqueuedAt`, `sequence`, `deliveryMode`, `ackState`。`ackState` 为 `persisted`, `reserved`, `dispatched`, `accepted`, `failed`, `requeued`, `dead_letter`。

```ts
interface QueueEntry {
  queueId: string
  sessionId: string
  turnId: string
  requestId: string
  priority: "now" | "next" | "later"
  deliveryMode: "prompt" | "steer" | "followup"
  sequence: number
  enqueuedAt: number
  ackState: "persisted" | "reserved" | "dispatched" | "accepted" | "failed" | "requeued" | "dead_letter"
  attempt: number
}

interface QueueAck {
  queueId: string
  turnId: string
  state: QueueEntry["ackState"]
  acceptedAt?: number
  errorCode?: string
}
```

处理器采用同步守卫：

```text
reserve(generation) -> recheck persisted state -> dispatch -> accepted/running -> end(generation)
```

参考 Claude Code 的 `QueryGuard.ts`、`messageQueueManager.ts`、`useQueueProcessor.ts`：旧 generation 的异步清理不能结束新 run，reserve 后必须再次读取持久化状态，避免双 drain 和漏 dispatch。

投递规则：

| Agent 状态 | 操作 |
|---|---|
| 无 Agent 或 idle | `prompt(AgentMessage)`，成功后 ack `accepted` |
| streaming 且当前工具批次未结束 | 持久化后调用 `steer(AgentMessage)`，等待下一轮确认 |
| Pi 即将自然结束 | 使用 `followUp(AgentMessage)`，不要伪装成 steer |
| 仍在 Plan admission | 保持 `queued`，Plan checkpoint 完成后 drain |
| dispatch 失败 | 保留原 turn，按退避重试，超过上限进入 dead letter 并通知用户 |

长任务重新发消息必须得到可观察回执：`queued`、`steered`、`followup`、`deferred` 或 `failed`。不能再返回忙碌文案后丢弃输入。

### 6.3 Plan 和子 agent 持久化

```ts
type PlanState = "admitting" | "running" | "paused" | "done" | "failed" | "interrupted"
type PlanStepState = "pending" | "running" | "done" | "failed" | "skipped" | "interrupted" | "unknown_side_effect"

interface PlanRecord {
  schemaVersion: 1
  planId: string
  sessionId: string
  rootTurnId: string
  state: PlanState
  agentIds: string[]
  version: number
  createdAt: number
  updatedAt: number
}

interface PlanStepRecord {
  planId: string
  stepId: string
  agentId: string
  title: string
  dependsOn: string[]
  state: PlanStepState
  attempt: number
  idempotencyKey: string
  effectClass: "read_only" | "reversible" | "external_side_effect"
  lastEventId?: string
  updatedAt: number
}
```

每次 step 状态转换、agent spawn、工具调用开始和结束都写 checkpoint。`dependsOn` 决定可并行集合，不能由执行循环忽略。重启后只恢复 `pending` 和已证明幂等的 `read_only/reversible` step；`external_side_effect` 若没有完成凭证则为 `unknown_side_effect`，需要确认或补偿。子 agent 的 transcript、权限和记忆投影带 `parentPlanId/parentStepId/agentId`，不能只存在 Pi 内存。

## 7. Prompt、画像和记忆接入

### 7.1 ContextKernel 分层

`buildPrompt()` 保留兼容入口，但内部必须返回可检查的 block 列表，而不是只有一条字符串：

```ts
type ContextLayer = "static" | "dynamic" | "profile" | "memory" | "transcript" | "ephemeral"

interface ContextBlock {
  blockId: string
  layer: ContextLayer
  source: string
  text: string
  priority: number
  tokenBudget?: number
  origin: MessageOrigin | "system"
  taint: MessageMeta["taint"]
}

interface PromptTransform {
  transformId: string
  name: string
  inputHash: string
  outputHash: string
  reason: "profile_rewrite" | "memory_recall" | "compaction" | "safety_redaction" | "budget"
  derivedFrom: string[]
  createdAt: number
}
```

固定顺序为 `static -> dynamic -> profile -> memory -> transcript -> ephemeral`。CANDY、Card、系统安全规则属于 static/profile；User.md 和用户画像属于 profile projection；长期记忆属于 memory；会话摘要和最近 API round 属于 transcript；active/hook/recovery 只能进入 ephemeral 或 UI-only。

### 7.2 完整 PromptSnapshot

快照必须在 `transformContext` 完成后、`convertToLlm` 产生最终 Provider 消息前后各记录一次，最终版本以 `onPayload` 为准：

```ts
interface PromptSnapshot {
  schemaVersion: 1
  snapshotId: string
  requestId: string
  sessionId: string
  turnId: string
  runId: string
  model: string
  provider: string
  thinkingLevel?: string
  systemBlocks: ContextBlock[]
  toolSchemas: Array<{ name: string; schemaHash: string; policyHash: string }>
  agentMessages: Array<{ id: string; role: string; origin?: MessageOrigin; contentHash: string }>
  llmMessages: Array<{ role: string; contentHash: string; toolCallId?: string }>
  transforms: PromptTransform[]
  estimatedInputTokens: number
  actualInputTokens?: number
  actualOutputTokens?: number
  cache: { sessionId?: string; prefixHash?: string; breakReason?: string }
  redactions: string[]
  createdAt: number
}
```

原始 payload 默认不落盘；保留脱敏结构、hash 和按配置采样的加密诊断副本。`estimatedInputTokens` 不得冒充 Provider usage。`onPayload` 记录实际 system、tools、messages、model、thinking 和 cache 参数后，才算“知道整个 prompt”。

### 7.3 提示词改写和用户画像

Prompt rewrite 是有界的派生过程，不修改用户原文和记忆真相源：

```text
raw user text
  -> intent/normalization transform（可选）
  -> profile projection（只读 User.md/画像版本）
  -> memory projection（带来源、污染和预算）
  -> final PromptSnapshot
```

画像写入必须走 `ProfileMemoryCandidate`，由确定性过滤、敏感信息策略、冲突检查和用户可追溯来源共同决定；模型不能直接覆盖 `User.md`。每次改写保存 `inputHash/outputHash/reason/derivedFrom`，可在评测中判断改写是否改变了用户意图。

```ts
interface ProfileMemoryCandidate {
  candidateId: string
  sourceEventIds: string[]
  target: "User.md" | "MEMORY.md"
  patch: Record<string, unknown>
  confidence: number
  policyHash: string
  status: "candidate" | "accepted" | "rejected" | "superseded"
}
```

### 7.4 MemoryKernel 和 dreaming

```ts
interface MemoryProjection {
  blocks: ContextBlock[]
  sourceIds: string[]
  memoryVersion: string
  provenance: "owner" | "agent" | "untrusted" | "system"
  taint: MessageMeta["taint"]
  estimatedTokens: number
}

interface MemoryCandidate {
  candidateId: string
  sourceEventIds: string[]
  kind: "fact" | "preference" | "goal" | "profile_change"
  confidence: number
  provenance: MemoryProjection["provenance"]
  taint: MessageMeta["taint"]
  status: "candidate" | "accepted" | "rejected" | "superseded"
}
```

记忆接入保持可替换，前置阶段用空实现验证边界：

```ts
interface MemoryProvider {
  recall(query: { sessionId: string; requestId: string; query: string; tokenBudget: number; signal: AbortSignal }): Promise<MemoryProjection[]>
}
```

当前只读端口已经接入 Runtime，写入候选、flush、具体索引和 dreaming 属于下一阶段的 `MemoryKernel`，不得塞回只读 provider 或会话 Markdown 存储。

`MemoryKernel` 的写路径是安全边界：召回和提取必须分开，提取只读 `eligibleForMemory=true` 且 `taint=trusted_user` 的 user 事件；active、hook、recovery、system、subagent 和已召回 memory 默认不产生候选。

dreaming 采用可恢复的后台任务，而不是隐式的每轮副作用：

1. Light：整理候选、去重、来源校验，不写长期事实。
2. REM：冲突、过期、敏感字段和画像变更检查，产出报告。
3. Deep：只把通过 gate 的候选原子提交到版本化 MemoryStore，保存 preimage、sourceEventIds、version 和结果。新方向推荐 SQLite，`MEMORY.md`/`User.md` 在迁移后是导出/投影；当前未迁移实现仍使用文件。

每次 dreaming 有 lease、`dreamId`、输入版本、输出版本、幂等键和失败重试；原子写失败保留 preimage，不影响前台回复。交互、system、cron/heartbeat、active、hook、subagent 会话默认不进入 deep write。

## 8. 压缩和上下文预算

本节由[会话压缩建设方案](../../history/implementation/会话压缩建设方案.md)补充实施细节。它属于 Context/Session 基础能力，可先于 P6：采用显式 checkpoint、结构化摘要和近期完整 rounds，不复制 ClaudeCode 的 UUID parent 图。`sessionId` 不随压缩变化；只有 `committed` 结果能发布新视图和完成提示，stale/cancelled/fallback 不得冒充提交成功。

### 8.1 三层策略

1. **L0 本地清理**：删除重复的 UI-only/hook 大块，把超长工具输出 spill 到受限文件，Prompt 只保留摘要、hash、路径和权限。
2. **L1 API 摘要**：按 `apiRoundId` 分组，摘要覆盖连续完整 round，记录 `summaryVersion`, `coveredEventIds`, `inputHash`, `outputHash`。
3. **L2 硬截断**：只删除最旧的完整 round，保留最近用户/assistant、未完成 tool pair、当前 Plan checkpoint 和必要的安全上下文。

禁止按消息比例切片，禁止伪造孤立的 `role=tool` 摘要。参考 Claude Code 的 grouping、micro compact、compact 和 auto compact 规则，tool call/result 必须成组；摘要失败时保留原 round，降低新请求预算或返回可解释的上下文不足错误。

### 8.2 压缩时序

```text
before request: estimate -> choose L0/L1/L2 -> persist compaction event
transformContext: apply only the committed snapshot
onPayload: capture final payload
after response: record actual usage -> optional background compaction
before memory write: flush session events and compaction version
```

已发送的 `PromptSnapshot` 不得被事后压缩改写。压缩任务有 session lock 和 generation，旧任务完成时不能覆盖新 snapshot。

补充约束：捕获快照后释放写锁再调用模型，最终在会话串行提交路径重验版本/代际；摘要与 cutoff 原子提交。预算区分输出上限、压缩触发余量、原文尾部和摘要正文。20K 只能是适合大窗口的目标/上限，16K 窗口必须缩放。失败后没有合法预算视图时停止请求，不发送超限历史。

## 9. Hook、主动消息和错误语义

### 9.1 Desk-Pet HookEvent

以下类型保留事件关联字段的设计意图，不要求重建通用 HookBus。按[总方案 §8](../design/轻量陪伴运行时与统一内核建设方案-2026-09-17基线.md#8-pi-hooks复用原生扩展点)接到 Pi 原生回调与现有领域事件；没有真实消费者的 hook 不实施。观察者、可阻断工具门禁和结果转换必须分别约定失败语义。

```ts
interface HookEvent {
  hookId: string
  name: "ingress" | "session_start" | "before_prompt" | "after_response"
    | "before_tool" | "after_tool" | "queue" | "plan_checkpoint"
    | "compaction" | "memory_candidate" | "dreaming" | "recovery" | "shutdown"
  requestId?: string
  sessionId: string
  turnId?: string
  runId?: string
  origin: MessageOrigin | "system"
  blocking: boolean
  deadlineMs: number
  payloadHash: string
  taint: MessageMeta["taint"]
}
```

Hook handler 只允许返回明确的 `allow/block/transform/defer` 结果；异常按 `hook_timeout`、`hook_rejected`、`hook_failed` 分类。blocking hook 失败关闭，async hook 超时脱离主回复链路。hook 输出超过预算必须 spill，不能直接塞进上下文。

> **2026-09-15 状态**：本节是**待重做的目标协议**。自研 `engine/runtime/hook-bus.ts` 已随提交 `cd85856` 删除（生产消费者为零，blocking/async/超时/重入能力全部由 Pi 原生 hook 覆盖），上面的 `HookEvent` 接口当前没有实现。重做前必须先有真实消费者，否则会再次得到「已接线但无人使用」的模块。

### 9.2 主动消息根因和修复

当前风险点是续跑逻辑在最后一条不是 user 时调用 `agent.prompt(input.userText)`，而 `prompt(string)` 会创建 user message。这样 active 或 hook 的文本会被 Pi 和会话层识别为用户输入。

修复验收必须同时满足：

- active 入口产生 `origin=active`, `querySource=active_monitor`, `isMeta=true`, `eligibleForMemory=false`。
- Pi 侧使用自定义 AgentMessage 经过 `convertToLlm` 转为 system/developer 或过滤为 UI-only；绝不调用 `prompt(string)` 传 active 文本。
- active 回复气泡可见，但其 user/assistant 事件都带 active parent，不计入用户事实提取。
- active、hook、recovery 在 `PromptSnapshot.agentMessages` 中仍可追踪，`llmMessages` 中的 role 由转换器明确记录。
- 回归用例检查 restart、steer、follow-up 和 compact 后都没有 `origin=active` 的 `role=user` 事件。

### 9.3 取消和错误

“不做 abort”不能成为实现约束。用户 follow-up 不打断正在执行的工具，采用 steer/queue；内部 timeout、窗口关闭、shutdown、安全拒绝和用户明确取消仍可调用 `agent.abort()`，并将当前 turn 标记为 `interrupted` 或 `unknown_side_effect`。所有错误使用结构化 `AppError`/`formatError`，持久化文本走脱敏 `summarizeError`。

## 10. 权限、沙箱、联网和自研工具

### 10.1 deny-first 权限模型

一次工具调用的顺序固定为：

```text
parse schema -> canonicalize path/command/URL -> resolve dynamic risk
  -> hard deny -> session grant (scope + expiry + capability)
  -> sandbox second gate -> user confirmation if required -> execute
```

trust grant 至少绑定 `sessionId`, `toolName`, `capability`, `path/host scope`, `policyHash`, `expiresAt` 和 `grantId`。deny 永远优先，不能由 trust 覆盖；前端模式不能把 Rust 的最终 deny 关闭。

### 10.2 工具基线

- `read/write/edit`：schema 校验、大小/行数上限、`AppPaths.validate_path()`、符号链接和父目录检查。
- `bash`：解析命令链、重定向、管道、子 shell 和环境变量；白名单按 AST/argv 判断，不能依赖子串；assistant 和 lightweight 共用 Rust 最终策略。
- `app_open`：只允许配置的文件/URL 根，规范化后重新检查，禁止任意路径和隐式外部协议。
- `net`/MCP：允许 host 列表、DNS 解析后拒绝 loopback/private/link-local/metadata IP，限制重定向次数、最终 host、TLS、超时和响应字节；每次请求记录 policyHash。
- Router：每次调用生成 `opId`，参数 schema、开始/结束、超时、取消、结果 hash、`isError` 和 provenance 都写事件；输出超过上下文预算 spill 到受限临时文件。
- 并行工具：默认 `toolExecution="sequential"`。只有同批工具完成 schema、权限和 effectClass 预检，并原子写入 launch checkpoint 后，才允许只读类别并行；每个跳过/阻断调用仍写合成结果，保证 transcript 配对。

## 11. 追踪、运行数据和上下文错误

### 11.1 TraceContext

```ts
interface TraceContext {
  requestId: string
  sessionId: string
  turnId?: string
  runId?: string
  agentId?: string
  planId?: string
  stepId?: string
  toolCallId?: string
  opId?: string
  snapshotId?: string
  compactionId?: string
  hookId?: string
}
```

TraceEvent 至少覆盖 `ingress`, `preprocess`, `queued`, `dispatch`, `prompt_start`, `payload`, `response`, `tool_start`, `tool_end`, `steer`, `followup`, `plan_checkpoint`, `compaction`, `memory_recall`, `memory_write`, `recovery`, `error`。日志和 Live Test report 使用同一组 ID。

```ts
interface TraceEvent {
  eventId: string
  type: string
  trace: TraceContext
  at: number
  durationMs?: number
  status: "start" | "success" | "failed" | "blocked" | "cancelled"
  attributes: Record<string, string | number | boolean | undefined>
}
```

### 11.2 指标定义

必须同时记录计数和耗时：

- queue：入列、等待、reserve 冲突、steer/follow-up 成功率、dead letter、恢复数。
- agent/plan：run、attempt、step 状态、未知副作用、恢复后重复率。
- context：system/transcript/memory/tools 各层 token 估算，压缩前后 token，实际 input/output/cache usage，cache break reason。
- tool：声明数、调用数、成功、失败、deny、confirm、timeout、cancel、输出 spill、并行批次。
- memory：召回命中、候选、接受、拒绝、冲突、重复写、污染传播、写入耗时。
- hook：执行数、block、timeout、错误、输出字节和主链路延迟。

所有 ratio 明确分母；估算值和 Provider usage 分字段，不用一个“上下文利用率”掩盖差异。

### 11.3 ContextError

定义 `context_budget_exceeded`, `context_pair_incomplete`, `context_transform_failed`, `context_snapshot_failed`, `context_usage_unknown`, `provider_payload_mismatch`。每个错误都包含 snapshot/compaction ID、可降级动作和是否阻断。必须能从 trace 反查“哪个 block、哪个 transform、哪次压缩”导致超限。

## 12. Memory Eval 评测集

评测先用离线 fake provider，避免真实模型不稳定掩盖协议错误；通过后再映射到 Live Test。

每个 case 使用：

```ts
interface MemoryEvalCase {
  schemaVersion: 1
  caseId: string
  suite: "persistence" | "recovery" | "prompt" | "queue" | "profile" | "dreaming" | "safety" | "budget"
  initialFiles: Record<string, string>
  inputEvents: IngressEnvelope[]
  providerScript: Array<{ response: unknown; usage?: unknown }>
  failureInjection?: "crash_before_flush" | "crash_after_tool" | "timeout" | "hook_error" | "compaction_error"
  expected: {

    forbiddenOrigins?: MessageOrigin[]
    maxInputTokens?: number
    duplicateWrites?: number

  }
}
```

最低 case 集合：

| caseId | 验证 |
|---|---|
| `memory-queue-before-dispatch` | 输入落盘后进程崩溃，重启只恢复 queued，且不重复 user turn |
| `memory-steer-during-tool` | 长工具执行期间 follow-up 入队，工具批次结束后收到 steer/follow-up 回执 |
| `memory-active-origin` | active 文本全链路保持 active，不出现 role=user 或长期候选 |
| `memory-plan-resume` | Plan/子 agent 在 step checkpoint 后崩溃，重启恢复 pending，不重放未知副作用 |
| `memory-prompt-snapshot` | 断言 onPayload 的完整 system/tools/messages 与 snapshot hash 一致 |
| `memory-profile-rewrite` | 用户画像只读投影；改写带来源且不覆盖 raw user text |
| `memory-dreaming-gate` | active、hook、subagent、untrusted 输入不能 deep write；失败不影响回复 |
| `memory-compaction-tool-pair` | 压缩保留完整 API round 和 tool pair，摘要覆盖范围可追溯 |
| `memory-safety-deny-first` | trust grant 不能绕过动态风险、路径、bash 和网络 deny |
| `memory-context-budget` | L0/L1/L2 顺序、token 预算、实际 usage 和 degradation 可解释 |
| `memory-tool-spill` | 大工具输出不占满 prompt，spill 文件受路径和权限保护 |

指标至少报告 Recall@k、Precision@k、MRR、source attribution accuracy、profile conflict rate、active contamination rate、duplicate write rate、prompt budget violation rate、recovery duplicate rate、tool safety false-allow rate 和 `pass@k/pass^k`。Contract hash 或源码 hash 变化后，旧结果自动失效。

## 13. 实施顺序和门禁

阶段完成状态以 §1.1 和[执行手册](./记忆系统重构执行手册-2026-09-17基线.md)的「当前检查点」为准；下面只保留各阶段的原始门禁定义。

### P0：契约、fake provider、快照和 trace

- 建立上述版本化类型、事件 schema、fake provider、TraceContext 和 snapshot redaction。
- 把 `onPayload/onResponse/subscribe` 接入只读记录器，先证明能看到最终 payload。
- 门禁：`memory-prompt-snapshot`、旧会话兼容、source hash 非空。
- **状态**：已通过。

### P1：Ingress、SessionTurnStore、主动消息

- 先写盘再投递；把全局 busy 拒绝改为 session queue；消除 active 的 string prompt 路径。
- 门禁：`memory-queue-before-dispatch`、`memory-active-origin`、多会话并发。
- **状态**：已通过（`memory-queue-before-dispatch` 实际 caseId 为 `queued-before-dispatch`）。

### P2：AgentSlot、steer/follow-up、Plan/恢复
