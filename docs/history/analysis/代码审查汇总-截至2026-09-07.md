# 代码审查汇总 - 截至 2026-09-07

> 本文记录截至 2026-09-07 对当前工作区的代码审查结果。它综合历史分析文档，但不以时间先后覆盖历史结论；当前行为以源码为准。

## 1. 审查范围与结论

本次逐篇阅读并交叉核对以下历史分析：

- `阶段现状-2026.7.17.md`
- `深度现状分析-2026.7.21.md`
- `记忆系统优化.md`
- `阶段现状-2026.7.21.md`
- `阶段现状-2026.8.6.md`

当前主要风险集中在三类：

1. **权限边界**：Profile 命令可绕过运行时目录，`file_list` 可读取任意目录。
2. **会话隔离与安全策略**：工具信任会跨会话残留；对话执行过程中切换会话会污染目标会话。
3. **可验证性**：Live Test 的契约过期和覆盖缺口不阻断测试，且测试环境的记忆初始化并不成立。

## 2. 当前问题

### P0 - Profile 文件命令存在路径越界与递归删除风险

**证据**：`src-tauri/src/commands/profile_cmd.rs`

- `profile_file_write()` 直接以外部传入的 `profile_id`、`relative_path` 拼接 `paths.profiles`（13-32 行）。
- 对不存在父目录，代码先 `create_dir_all()`，但未在创建后再次校验范围；绝对路径和 `..` 都可以使 `PathBuf::join()` 脱离 `profiles`。
- `profile_file_read()`（53-68 行）对用户目录和内置目录读取均未做路径校验。
- `profile_delete()`（73-78 行）直接对 `paths.profiles.join(profile_id)` 调用 `remove_dir_all()`，没有任何范围校验。
- `list_profile_files()`（135-172 行）同样将外部 profile id 直接用于用户目录和内置目录枚举。

影响：渲染层一旦能够调用命令，便可借助特制参数读取、写入或递归删除运行时目录以外的路径。这违反路径命令必须以 `AppPaths::validate_path()` 限制读写范围的项目约束。`tauri.conf.json` 当前 CSP 为 `null`，会进一步放大渲染层被注入后的影响面。

### P0 - SAFE 的 `file_list` 没有路径校验

**证据**：

- `src-tauri/src/commands/tool_exec.rs:91-118` 将传入路径直接交给 `std::fs::read_dir()`。
- `src/services/tool/local/file.ts:49-79` 将其注册为 `SAFE` 的 `file_list`，并在 pet 模式可用。
- `file_search` 也复用这个命令（81-105 行）。

影响：模型可在无需确认的情况下枚举任意可访问路径中的文件名、目录名与文件大小。该问题已在 `阶段现状-2026.7.21.md` 标出，当前仍未修复。

### P1 - “会话内信任”实际会跨会话泄漏

**证据**：

- `src/services/safety/checker.ts:73-90` 使用模块级 `Set` 保存已信任工具。
- `resetSessionTrust()` 有定义但没有调用者。
- `checkSafety()` 的 NORMAL 分支在 `sessionTrustEnabled` 开启时直接依据该全局集合跳过确认（148-152 行）。
- 新建和切换会话的 `src/services/session/manager.ts` 没有重置信任状态。

影响：用户在会话 A 对 NORMAL 工具确认一次后，会话 B 也会自动放行该工具，违背“首次确认后可会话内信任”的安全承诺。

### P1 - 会话切换期间的工具消息和记忆会写入错误会话

**证据**：

- `src/services/agent/runner.ts:65-66` 捕获了发送时的 `originSessionId`，并在最终回复返回时校验（132-145 行）。
- 但 `src/services/engine/agent-loop.ts:304` 和 `368` 在工具循环中直接写全局 `chatHistory`。
- `src/services/session/manager.ts:187-197` 切换时替换全局 `chatHistory`，并将 `MemoryService` 的活跃会话设为目标会话。
- Agent Loop 在开始和结束时调用的 `MemoryService.recordTurn()` 因此也可能对应切换后的活跃会话。

影响：正在执行工具调用时切换标签页，会把工具调用、工具结果和助手记忆写入目标会话；最终文本虽回存原会话，但会话真相源已分裂。

### P1 - Provider 请求没有真正的超时或取消机制

**证据**：

- `src/services/agent/provider.ts:98-111` 的 `fetch()` 没有 `AbortController` 或 `signal`。
- `agent-loop.ts` 的 turn timeout 只在新一轮请求前检查，不能中断已挂起的 Provider 请求。
- Plan 的复杂度判断、计划生成和子代理都复用同一 Provider 路径。

影响：网络连接或 Provider 长时间挂起时，主对话和 Plan 都可能永久处于生成中，现有 timeout 配置无法兑现。

### P1 - Live Test 不具备有效的契约门禁能力

**证据**：

- 7 个 Contract 的 `sourceHash` 都为空：`src/services/__tests__/live/contracts/*.contract.ts`。
- `contract-checker.ts:27-30` 对空 hash 显式跳过 stale 判断。
- `index.live.test.ts:55-72` 仅在 stale 时抛错；`missing`、COUNT、DEPTH、BOUNDARY、ERROR 缺口只输出日志。
- `setup.ts:8-19` 未 mock `init_memory_files`，返回的 `null` 会在 `memory/index.ts:73-75` 调用 `replace()` 时失败；catch 后却在 90 行标记为已初始化。

影响：即使源码变更、场景缺失或测试中的 MemoryService 未正常初始化，测试也可能继续执行并产出误导性结果。

本次运行 `pnpm test` 未通过：6 个 Scene 中 4 个通过、2 个变量池场景失败；真实 Provider 返回 503 后，Card stages 初始化失败，导致变量池没有预期变量。不能将当前 Live Test 标记为通过。

### P2 - Plan 的并行、依赖和逐步确认只是数据字段，不是执行语义

**证据**：

- `src/services/engine/planner.ts:16-23` 定义 `dependsOn` 与 `parallel`，生成 Prompt 也要求模型填写（123-145 行）。
- `executePlan()` 在 213 行使用普通 `for...of`，未读取两字段，所有步骤都顺序执行。
- `agent-loop.ts:144-154` 接收 PlanConfirm 的 `stepMode`，之后没有使用；`stepByStep` 不会在每步之间请求用户确认。

影响：Plan UI 和历史设计所表达的“标注依赖、可并行、逐步确认”与实际行为不一致。当前只实现了串行子代理执行及失败时可询问是否继续。

### P2 - 长期记忆自动召回与提取尚未闭环

**证据**：

- `src/services/context/builder.ts:79-85` 只注入 CANDY、User 和当前会话摘要，没有调用 `MemoryService.search()`。
- `searchMemory()` 仍是简单关键字匹配：`memory-entries.ts:76-88`。
- `forkMemorySupplement()` 有实现和导出，但没有正常 Agent Loop 调用点。
- `createNewSession()` 会归档旧会话，但 `session/manager.ts:210-243` 没有调用 `onSessionEnd()`；当前会话结束计数仅在 `/clear` 中增加。

影响：长期 MEMORY 条目不会主动进入 Prompt，普通新会话也不能推进“每两次会话结束整理”的策略。该项与 7 月两份 Memory 分析及 8 月 6 日阶段文档一致，属于持续未完成能力，不应描述为已自动记忆。

### P3 - 信息丢失与低优先级残留

- `session-files.ts:147-158` 将内存会话轮次截断为 200 字；会话文件和 `recordTurnToSession()` 也只保留 300 字。
- `compactor.ts:189-200` 将每条待压缩消息截断为 300 字，摘要可能缺少长任务的后半段事实。
- `trimToMax()`（`memory-entries.ts:121-126`）按重要度直接丢弃条目，不合并低重要度信息。
- `setSessionVars()` 只有定义和 barrel 导出，没有调用者，`session` 变量范围未实际注入。
- `idle` 和 `generating` 阶段仍没有有效主链路调用；Plan 的 `planning` 阶段则已经接通。
- 文件规模继续上升：`AITab.vue` 869 行、`ChatPanel.vue` 678 行、`variable-pool.ts` 535 行。
- 发布元数据仍不一致：`package.json` 为 `0.7.1`，`Cargo.toml` 与 `tauri.conf.json` 为 `0.1.0`。

## 4. 建议处理顺序

1. 收紧 Rust 文件边界：统一校验 Profile 参数、修复 `file_list`，为路径越界和删除边界补 Rust 测试。
2. 修复会话边界：在新建/切换会话时重置信任；将 Agent Loop 的工具消息和 Memory 写入绑定到 origin session，而不是全局活跃会话。
3. 为 Provider 请求加入可取消的 timeout，并覆盖主循环、Plan 与子代理路径。
4. 修复 Live Test 的文件系统 mock；空 hash、覆盖缺口和初始化失败必须阻断测试结果。
5. 明确 Plan 产品契约：实现依赖/并行/逐步确认，或从 Plan schema 与 UI 中移除尚未支持的能力。
6. 在完成会话恢复验证后，再接入受 token 预算限制的长期记忆召回与可审计的事实提取。
