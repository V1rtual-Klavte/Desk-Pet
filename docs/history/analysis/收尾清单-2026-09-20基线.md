### 3.1 测试基础设施

| 编号 | 状态 | 当前边界 | 完成条件 |

| `classifyTurnFailure` 的分类正则 | **已完成（归档时同步）** | 原为无边界 `/5\d\d/` 判 provider，会命中预算判定文案里估算值的数字片段 | 已由 `ab5e195` 收紧为 `\b5\d\d\b`（401/403、429 一并锚定），新增 `expectFailureKindDigitInvariance` 双向断言，6 份契约 hash 重算 |

**「Rust 单测不在门禁内」已完成**：新增 `pnpm run test:rust`（`cargo test --lib`，37 个测试，墙钟约 0.65s），接进 `test:release` 与 CI。`test:types` 保持原义（Vue 类型 + Rust 编译），没有把测试混进那个脚本名里。CI 的 job 由 `test-types` 改名 `verify`（它现在跑两个脚本），改名前后确认过 master 无分支保护、全仓无文档引用。**Windows 首跑与 CI 时长增长无本机证据**，待 CI 收口。

**「场景无法表达期望失败」已完成**：`TurnDef` 增可选 `expectFailure`（kind + message 匹配器，空匹配器在数据集预检被拒），判定走普通断言通道，因此预期之外的失败、回抛异常、跳过与超时仍照旧判失败；未声明 `expectFailure` 的回合行为完全未变。溢出恢复的两条失败路径（恢复用尽、无摘要范围 declined）已从手工证据变为门禁内场景，负向探针实测「给正常回合加声明」与「文案改错」都会 FAIL。

**L3 已决策：不加门禁。** 审计结论存档于此——从 `sourceFiles` 出发做静态 import 图 BFS，闭包外共 92 个文件，其中 **89 个被 ≥5 份契约共享**（成因是 barrel re-export 把整个模块拖进闭包，加上 `CONFIG.yaml`／`config.ts`／`logger`／`error` 一类共享骨架）。真正的"漏声明"只有 1 条（`personality-card` 经 `personality/registry.ts → stages-cache.ts → engine/pi/index.ts` 可达 `engine/pi/runtime.ts`），而那条也只是经 barrel 的偶然可达，补进去只会让 `runtime.ts` 每次变动都连带作废该契约的 hash。按共享骨架与 type-only 边豁免后门禁近乎空转，要让它"有牙"则每份契约需额外声明 30–40 个文件、hash 维护成本显著上升；**收益不抵成本，故不引入**。该审计的价值是一次性的：它证明了"闭包差"几乎全是 barrel 噪声，而不是契约普遍漏声明。

**「许可额度的窗口销毁残留」经评估后关闭：不修。** 代码层面缺口真实（窗口销毁确实没有回收通道），但**不存在任何路径能让它阻塞到谁**：能借额度的窗口任一时刻最多一个——`lib.rs` 在 `is_live_test()` 时只建 live-test 窗口就 return，不建 main，二者从不共存；窗口销毁且无后继时该 label 下再没有页面实例，也就没有竞争者；有后继的两种情形（同 label 新实例、main↔live-test 切换）分别由 `tool_permit_attach` 与进程重建覆盖；Gate 还按数据根分域。**不修还有一条纪律理由**：这条改动的主体是事件接线，而 Live Test 里唯一能借额度的窗口就是 live-test 自己（销毁它等于杀场景），构造不出"回收了"与"关掉回收会失败"的对照——为零影响缺口引入一段无法验证的接线，正撞在「类型检查不能代替运行验证」上。将来 main 若要支持"关闭后可重建"、或出现第二个能跑工具的窗口，需重估。
