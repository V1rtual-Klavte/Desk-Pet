# 深度现状分析 — 2026-07-21

> 基于 3 维度 subagent 深度代码追踪：Plan 模块 / Memory 系统 / 其他遗留问题

---

## 一、Plan 模块 — 必须实现（助手模式）

### 1.1 当前状态

Plan 模块是 **Phase 4 唯一未完成的核心功能**。原始设计中，助手模式下检测到复杂任务时，LLM 先做步骤拆解，再逐步执行。

**当前助手模式的实际流程：**

```
用户消息 → PreProcessor → refreshVariablePool()
  → buildPrompt(card+变量+工具+记忆)
  → 单次 LLM → runToolLoop(while rounds < maxRounds)
  → generateReply → 返回
```

工具循环就是普通的 `while` 循环，LLM 自己决定下一步调什么工具。**没有进度可见性、没有步骤追踪、没有复杂度门控。**

### 1.2 死代码现状

| 组件 | 状态 | 位置 |
|------|:---:|------|
| `PLANNING` AgentState | ❌ 已从 session.ts 删除 | 原在 `session.ts:15` |
| `planning` stage 文案 | ⚠️ stage 定义存在但 `getSimpleStage("planning")` 始终返回 null | `middleware.ts:53-55` |
| `planning` 表情 | ⚠️ `DEFAULT_EXPRESSIONS.planning = "business"` 已定义但从未触发 | `middleware.ts:30` |
| `planning` 状态转换 | ❌ 不存在 | 从未有代码调用 `transition("PLANNING")` |

### 1.3 原始设计意图

来自 `DES.md` / `架构方案.md`：

```
核心引擎:
  用户输入
    → ContextEngine（上下文/记忆/变量/Walk）
      → Plan（助手模式启用，LLM驱动，复杂任务拆解）   ← 缺失
        → Walk（工具调用+安全+子代理+子循环）
          → 回复
```

**触发条件（设计）：**
- 助手模式启用
- 关键词检测（"分析"、"整理"、"重构"、"修复"、"检查"、"审查"、"合并"、"总结"、"生成"、"创建"）
- 或工具链长度预计 >= 3

**行为：**
- 额外的 LLM 调用（thinkingEffort: "low"）做步骤拆解
- 向用户展示计划，可选确认/取消
- 逐步执行，每步有进度反馈
- 步骤失败时可自适应

### 1.4 当前助手模式限制（无 Plan）

| 问题 | 影响 |
|------|------|
| 无进度可见性 | 用户只看到 thinking 表情 → 瞬间结果，中间可能有 4 次工具调用但看不到 |
| 无步骤失败处理 | LLM 可自适应，但无 "第 2/4 步失败，剩余 3 步" 的概念 |
| 无用户确认门控 | 每次安全确认逐工具触发，无法 "预先确认全部 4 步" |
| 无复杂度阈值 | 即使是 "谢谢你" 也走完整 agent loop |
| 无进度事件 | `emit("deskpet-expression")` 只在最终结果触发 |

### 1.5 实现方案

```
复杂度检测 (新文件 engine/planner.ts)
  │
  ├─ 低复杂度 → 跳过 Plan → 直接 runToolLoop (当前行为)
  │
  └─ 高复杂度 → Plan 流程:
       │
       ├─ 1) 额外 LLM 调用 (low effort) → 生成步骤列表
       ├─ 2) session.transition("PLANNING")
       ├─ 3) middleware.wrap("planning") → 表情 + 文案 + 计划展示
       ├─ 4) 用户确认（执行全部 / 逐步确认 / 取消）
       ├─ 5) transition("GENERATING") + runToolLoop（含步骤上下文）
       └─ 6) 每步完成/失败 → 进度事件 + 文案更新
```

**需要修改的文件：**

| 文件 | 改动 |
|------|------|
| `engine/session.ts` | 重新添加 `PLANNING` 状态 + PRE→PLANNING→GENERATING 转换 |
| **新文件** `engine/planner.ts` | 复杂度检测 + LLM 计划生成 + 步骤解析 |
| `engine/agent-loop.ts` | 在 `refreshVariablePool()` 和 `buildPrompt()` 之间插入 Plan 阶段 |
| `personality/middleware.ts` | 修复 `planning` case 返回实际文案 |
| `personality/stages-cache.ts` | 移除 `planning` 硬编码 null |
| `personality/stages-prompt.md` | 移除 `"planning": ""` 空字符串约束 |
| `CONFIG.yaml` | 新增 `plan.enabled` / `plan.complexityThreshold` / `plan.maxSteps` |
| `components/` | 计划展示 UI（气泡或弹窗） + 确认按钮 |

**预估工作量：** 中等（300-500 行新代码，跨 4-5 个文件）

## 二、Memory 系统 — 需要大优化

### 2.1 架构现状

```
┌──────────────────────────────────────────────────────┐
│                  LLM 上下文窗口                        │
│  buildPrompt() 注入:                                   │
│  ✅ CANDY.md 全文（系统指令）                           │
│  ✅ User.md 全文（importance>=7 的用户事实）             │
│  ✅ CompactionSummary（会话摘要）    ← 唯一的动态桥梁    │
│                                                       │
│  ❌ MEMORY.md 条目（0/200 条被注入）                     │
│  ❌ Project.md / Outside.md                            │
│  ❌ 原始对话轮次（压缩后丢失）                            │
└──────────────────────────────────────────────────────┘
        ▲                              │
        │ 注入（固定）                   │ 无工具暴露
        │                              ▼
┌───────────────┐           ┌─────────────────────┐
│ context/      │           │ 工具注册表            │

        │
        ▼
┌──────────────────────────────────────────────┐
│           MemoryService (外观)                │

│                    appendMemory() ← 仅整理    │
│                    trimToMax()    ← 丢弃非合并│
│                                              │
│  session-files.ts: recordTurn()   ← 截断200字│
│                    archiveSession()           │
│                                              │
│  consolidate.ts:  consolidateWithLLM() ← 60min│

│  io.ts:           文件锁 + 读写               │
└──────────────────────────────────────────────┘
```

### 2.2 发现的 10 个问题

| # | 问题 | 严重性 | 详情 |
|---|------|:---:|------|
| 1 | **LLM 无记忆工具** | 🔴 严重 | `searchMemory`/`appendMemory` 存在但**从未注册为 ToolDef**。LLM 无法搜索或写入 MEMORY.md |
| 2 | **仅关键字搜索** | 🟠 高 | `searchMemory()` 用 `.includes()` 字符串匹配。无嵌入、无语义。搜 "喜欢猫" 找不到 "宠物偏好" |
| 3 | **长期记忆未主动注入** | 🔴 严重 | `buildPrompt()` 注入 CANDY + User + CompactionSummary，但**0 条 MEMORY.md 条目被注入**。宠物每次对话都 "失忆" |
| 4 | **无 RAG 管道** | 🟠 高 | 无嵌入生成、无向量存储、无 top-K 检索、无重排序 |
| 5 | **记忆创建是被动的** | 🟠 高 | 轻量模式: 仅在 LLM 整理时通过 newFacts 推断。助手模式: forkMemorySupplement 每轮跑，但提取由 LLM 自行判断。**用户无法说 "记住我的生日"** |
| 6 | **trimToMax() 丢弃不合并** | 🟡 中 | 满时按重要性排序→切片丢弃低重要度条目，**不做 LLM 合并**。有价值信息可能被丢弃 |
| 7 | **recordTurn 截断 200 字** | 🟡 中 | `text.substring(0, 200)` — 压缩器看不到完整用户消息，CompactionSummary 可能缺失上下文 |
| 8 | **去重脆弱** | 🟡 中 | `consolidateLocal()` 用 `content.substring(0,80)` 做去重键。稍有不同的措辞 → 不同键 → 不去重 |
| 9 | **CompactionSummary 是唯一桥梁** | 🟠 高 | 如果压缩失败，LLM 对先前对话的上下文为零。无原始对话全文回退 |
| 10 | **Project.md 同步 O(n) 扫描** | 🟢 低 | 初始化时重读每个会话文件重建索引 |

### 2.3 优化方案

#### 阶段 1：最小可行修复（工具暴露 + 自动注入）— 🔴 必须

1. **注册 `memory_search` 工具** — 在 `src/services/tool/local/` 创建 ToolDef，调用 `MemoryService.search(keyword)`
2. **注册 `memory_write` 工具** — ToolDef 调用 `MemoryService.append(content, category, importance)`
3. **自动注入 top-K 相关记忆** — 在 `buildPrompt()` 中，对用户消息运行 `searchMemory()`，将 top-3 结果追加到系统提示。无需 LLM 调用工具即可给宠物 "工作记忆"

#### 阶段 2：语义搜索 — 🟠 推荐

4. **添加嵌入搜索** — 方案选择：
   - **轻量**: 用 Web Crypto API 对每条记忆做 token-hash 向量 → 余弦相似性（暴力 200 条，免费）
   - **标准**: 调用 OpenAI `text-embedding-3-small` 在存储时生成嵌入 → 查询时 top-K 余弦相似性
   - **本地**: Transformers.js 设备端嵌入（完全离线，但加载模型有开销）

5. **混合检索** — 关键字（BM25-like）+ 语义（嵌入）→ 重新排序 → top-K

#### 阶段 3：质量改进 — 🟡 优化

6. **修复 trimToMax()** — 驱逐前尝试 LLM 合并低重要度条目，或至少优先保留 `category==="user"` 的条目
7. **修复 recordTurn 截断** — `text.substring(0, 200)` → 提升到 1000 或移除截断
8. **添加重要度衰减** — 旧条目如果未重新访问，重要度随时间衰减
9. **暴露 `memory_delete` 工具** — LLM 可以清理过时记忆
10. **增量 Project.md 更新** — 替代全量重扫描

### 2.4 与其他 AI 伴侣的差距

| 特性 | Desk-Pet 现状 | 行业标准 |
|------|:---:|:---:|
| 自动记忆检索 | ❌ 无 | ✅ 每次对话注入相关记忆 |
| 记忆创建工具 | ❌ 无 | ✅ LLM 可主动调用 |
| 语义搜索 | ❌ 关键字 only | ✅ 嵌入 + 混合检索 |
| 分层摘要 | 1 层 (CompactionSummary) | 3+ 层 (即时/每日/每周) |
| 实体提取 | 仅助手模式 LLM 判断 | 自动提取 + 结构化存储 |
| 记忆衰减 | ❌ 静态 | ✅ 时间衰减 |

**关键发现：**
- `planning` 有完整栈（阶段+中间件+文案），但从未调用 — 等 Plan 模块实现
- `timeout`/`retry` LLM 生成文案但中间件无句柄 — agent-loop 绕过了它们
- `generating` 在中间件中但**不在 StageMap 中** — 架构不一致
- `idle` 硬编码 null + 从不调用

### 3.2 情感映射不匹配

卡片模板定义了 7 个键：`smile, chu, gaoo, sleepy, shy, idle, business`
系统默认回退有 6 个键：`happy, chu, angry, sad, shy, idle`

**`business` 键在系统回退中缺失！** 所有 4 张内置卡片只定义了 `idle` 映射，其他全部回退到系统的 6 个默认值。

### 3.3 变量池 — session 范围死代码

- `pool.session` 永远为空，`setSessionVars` 导出但从未被调用
- `interaction` 范围只有 1 个变量（`unansweredCount`）
- 缺少 `interaction` 变量的重置策略（card 变量有 `reset=daily/session/never`）

### 3.4 回退链 — 3 个键从未被引用

| 键 | 状态 |
|------|:---:|
| `llmUnavailable` | ❌ 从未被调用 — provider 网络错误后应引用 |
| `concurrentRejected` | ❌ 从未被调用 — 并发锁检查后应引用 |
| `compactionFailed` | ❌ 从未被调用 — `compactIncremental` 吞掉错误 |
